# Adjutant Seamless Voice Pipeline — Deep Research Report

## 1. ChatGPT Advanced Voice Mode (AVM) — Architecture Under the Hood

**Architecture type:** Native speech-to-speech using natively multimodal models. From OpenAI's own help center: "Voice conversations are powered by natively multimodal models" and "Advanced voice leverages natively multimodal models (such as GPT-4o) to directly 'hear' and generate audio." This is fundamentally different from the older Standard Voice Mode, which was a cascade of Whisper STT → GPT-4 → TTS. AVM ingests audio tokens, reasons in a unified audio+text token space, and emits audio tokens directly — preserving emotion, accent, prosody, speaking rate, and background context that a text intermediate would discard.

**OpenAI Realtime API (the developer-exposed surface for the same model family):**
- Models: `gpt-realtime` (the GA production model launched Aug 2025), `gpt-4o-realtime-preview`, `gpt-4o-mini-realtime-preview`.
- Transports: WebSocket, WebRTC, and SIP. Per OpenAI: "You can use the Realtime API via WebRTC, session initiation protocol (SIP), or WebSocket to send audio input to the model and receive audio responses in real time."
- Audio format: PCM16 is the default, with `input_audio_format` setting `pcm16` (audio/pcm at 24,000 Hz). G.711 (mu-law/a-law) is supported per the spec for telephony bridging but PCM16 is the recommended default.
- Streaming protocol: Send audio with `input_audio_buffer.append` events containing base64-encoded PCM16 chunks; the model streams back `response.audio.delta`, `response.audio_transcript.delta`, and `response.done` server events.
- VAD / turn detection: Two modes — `server_vad` (acoustic, with tunable `threshold`, `prefix_padding_ms`, `silence_duration_ms`, `interrupt_response`, `create_response`, `idle_timeout_ms`) and `semantic_vad` (interrupts based on whether the model thinks the user is finished, has an `interrupt_response` setting). Both can preempt the assistant's audio output.
- Interruption: `input_audio_buffer.speech_started` server event triggers automatic cancellation of in-flight `response.audio.delta` chunks if `interrupt_response: true` is set.
- Latency: Practical end-of-speech to first-audio-out has been measured around 300–800ms for AVM users; OpenAI's internal published number for GPT-4o conversational latency is ~232–320ms average.

**Pricing (April 2026):**
- `gpt-realtime`: $32 per 1M audio input tokens ($0.40 cached), $64 per 1M audio output tokens. Per-minute: ~$0.06/min input, ~$0.24/min output.
- `gpt-4o-mini-realtime-preview`: cheaper but exact per-minute not consistently published; sources cite approximately 75% cheaper than full gpt-realtime.
- The GA `gpt-realtime` was a 20% price drop vs `gpt-4o-realtime-preview`.

**Implication for Adjutant:** OpenAI Realtime is forbidden — wifi gets pulled. But its protocol design (PCM16 over WebSocket, server VAD with tunable silence_duration_ms, response.cancel on barge-in) is the gold-standard reference shape to mimic locally.

## 2. Open-Source / On-Device Speech-to-Speech Equivalents

### Moshi (Kyutai)
- Full-duplex audio-text foundation model. Uses **Mimi**, a streaming neural audio codec. License: Apache 2.0.
- Theoretical latency: 160 ms (80 ms Mimi frame + 80 ms acoustic delay); practical 200 ms on L4 GPU.
- PyTorch version requires 24 GB VRAM, no quantization. **MLX version supports 4-bit, 8-bit, and bf16 quantization, tested on MacBook Pro M3.** This is the only viable path on M2.
- Repo: [kyutai-labs/moshi](https://github.com/kyutai-labs/moshi). MLX impl in `Blaizzy/mlx-audio`.
- M2 16 GB viability: 4-bit quantized should fit, but no published M2 numbers; expect 1–2x real-time on M2 Pro, possibly slower than real-time on plain M2.
- **Verdict for Adjutant: too risky for <30hr hackathon.** No proven offline, English-only, refusal-contract-preserving demo and integrating with FastAPI/pikepdf form-fill flow is custom work.

### Mini-Omni / Mini-Omni 2 (Tsinghua / GPT-Omni)
- Built on Qwen2-0.5B (24 transformer blocks, internal dim 896) + Whisper-small encoder. Total ~0.5 B params.

## 4. Streaming LLM Patterns

### Ollama streaming
- `stream=True` returns an iterator yielding `ChatResponse` chunks. Token-level streaming works for plain chat; **token-level streaming is broken when tools are bound via langchain_ollama.ChatOllama** (issue #26971).
- Direct ollama-python: `for chunk in client.chat(model='llama3.2:3b', messages=[...], stream=True): yield chunk['message']['content']`.

### llama.cpp streaming
- Direct token stream via llama-server's OpenAI-compatible `/v1/chat/completions` with `stream: true`. Faster than Ollama for raw throughput; Ollama is wrapper-with-defaults.
- Performance on Apple Silicon (Llama 3.1 8B Q4_K_M): **15–28 tok/s with Metal**, 40+ tok/s on M3 Pro. M2 16 GB plain (10 GPU cores) likely 12–20 tok/s.
- Llama 3.2 3B on M2: 40–80 tok/s decode; prefill TTFT ~2.3 s for 2660-token prompt; sub-300 ms for short prompts (<300 tokens).
- Llama 3.2 1B on M2: 100+ tok/s realistic.

### Sentence-buffer pattern (the critical move)
- Don't wait for full LLM response. Maintain a rolling buffer of token deltas. When buffer contains `[.?!]` followed by space (or `;`/`:` for long replies), flush the completed sentence to TTS. Continue accumulating subsequent tokens into the next sentence buffer.
- Pseudocode:
```python
buf = ""
async for chunk in ollama.chat(model="llama3.2:3b", messages=msgs, stream=True):
    buf += chunk["message"]["content"]
    while True:
        m = re.search(r'(.+?[.!?])(\s|$)', buf)
        if not m: break
        sentence = m.group(1).strip()
        await tts_queue.put(sentence)
        buf = buf[m.end():]
if buf.strip():
    await tts_queue.put(buf.strip())
```
- This keeps end-to-first-audio under ~600 ms even if the full response takes 3 s, because the first complete sentence usually arrives within the first 200 ms of generation.

### KV cache reuse
- Ollama auto-keeps KV cache between turns for same model, same conversation. Helps TTFT on follow-up turns (skips re-prefilling system prompt + history).
- For Adjutant: just keep the same `conversation_id` across turns; don't restart Ollama between requests.

### Speculative decoding (Llama 3.2 1B drafting Llama 3.1 8B)
- llama-speculative binary in llama.cpp. Example: `./llama-server -m Meta-Llama-3.1-8B-Instruct-Q8_0.gguf -md Llama-3.2-1B-Instruct-Q8_0.gguf -c 4096 -cd 4096 -ngl 99 -ngld 99 --draft-max 8 --draft-min 4 --draft-p-min 0.9`.
- **1.83x token-gen speedup** at draft tokens=5 (Llama 3.1 8B drafted by Llama 3.2 1B).
- Users report 90 → 180+ tok/s on long-output tasks.
- **Ollama support is in development but not GA as of issue #5800.** For hackathon: stick with Ollama + 3B if 8B is too slow, or run llama.cpp directly via `llama-server` and point Ollama-compatible code at it via base_url override.

## 5. Streaming TTS / Low-Latency TTS

- Zero-shot voice cloning from ~5 s of reference audio.
- Watermark: Resemble AI's Perth perceptual neural watermark on every output (survives MP3, edits).
- **On M2 16 GB CPU: not as fast as Kokoro.** Chatterbox is GPU-optimized; CPU fallback is slow. If you have a CUDA-class machine for the demo, Chatterbox is the quality king. On M2 only, Kokoro will feel snappier.

### XTTS-v2 (Coqui)
- Voice cloning from 6-s reference, 16 languages.
- **Streaming inference <200 ms latency on GPU.** CPU: near real-time on modern laptops, RTF ~0.3x with GPU.
- License: Coqui Public Model License (research-only for some uses; commercial ambiguity post-Coqui shutdown 2024). Use with caution.
- Maintained forks: idiap/coqui-ai-TTS.

### F5-TTS / E2-TTS (flow-matching)
- F5-TTS: non-autoregressive, Diffusion Transformer + ConvNeXt text refinement + Sway Sampling.
- **RTF 0.15 at 16 NFE (16 denoising steps), WER 2.53. With Sway sampling + EPSS: 7-step generation at RTF 0.03 on RTX 3090.**
- E2-TTS: original of the duo; F5 is the production-ready improvement.
- M2: RTF will be ~10x slower than 3090 → still under real-time but tight. Skip unless Kokoro fails.

### MeloTTS
- Multilingual, optimized for real-time CPU. MPS-aware on Apple Silicon (explicit MPS sync + cache clearing for stability). License: MIT.
- Slightly slower than Kokoro per inferless benchmark. Comparable quality.

### StyleTTS2
- High quality but encoder/diffusion-free design ≠ best streaming UX.

### OuteTTS
- **Worst latency in the comparison: 4+ minutes for 200-word inputs.** Skip.

### Apple `say` command
- Built-in macOS CLI. `say -v Samantha "hello"` or pipe `say -o out.aiff`.
- Latency: <50 ms first sample. Quality: 2010-era. Use as ultimate fallback if Python TTS fails 60s before demo.

### pyttsx3 limitations
- Wraps NSSpeechSynthesizer on macOS, espeak on Linux. Robotic. No streaming chunks (one-shot). No emotion. **Functional fallback only.**

### Streaming TTS playback in browser
- Two approaches:
  1. **MediaSource Extensions (MSE):** Server sends audio chunks (WAV or Opus) over WebSocket; client `appendBuffer` on a `SourceBuffer`. ChatGPT's web client uses this. Works with Opus/MP3 chunks; raw PCM requires WAV header tricks.
  2. **AudioWorklet + Web Audio API:** Server sends raw PCM samples over WebSocket; AudioWorklet processor schedules them into the audio graph. Lower latency (no codec decode), but requires writing an AudioWorkletProcessor `process()` method (called every 128 samples). Can use a circular buffer.
- For Adjutant in <30 hr: **WAV chunks over WebSocket → decoded with `audioContext.decodeAudioData()` → scheduled with `AudioBufferSourceNode.start(when)`** is the simplest. Each Kokoro yield ≈ one or two seconds of audio; queue them with `nextStartTime = max(audioCtx.currentTime, prevEnd)`.

## 6. Voice Activity Detection (VAD) and Turn-Taking

### Silero VAD
- **MIT license. JIT model ~2 MB. <1 ms per 30-ms audio chunk on a single CPU thread.** ONNX runtime support (`onnxruntime>=1.16.1`). 8 kHz and 16 kHz sample rates only (16 kHz preferred); ONNX opset 15 supports only 16 kHz.
- Streaming: `VADIterator` for chunk-by-chunk processing. Helpers: `load_silero_vad`, `read_audio`, `get_speech_timestamps`, `save_audio`, `collect_chunks`.
- Threshold params: `activation_threshold` (higher = fewer false positives, miss quiet speech), end-of-speech threshold auto-set 0.15 below activation (hysteresis), `min_speech_duration`, `min_silence_duration`, `prefix_padding_duration`.
- Rule of thumb: `activation_threshold=0.5`, `min_silence_duration_ms=500` for slow conversational endpoint, `300` for snappier.

```python
import torch
from silero_vad import load_silero_vad, VADIterator

model = load_silero_vad(onnx=True)
vad = VADIterator(model, threshold=0.5, sampling_rate=16000,
                   min_silence_duration_ms=500, speech_pad_ms=100)
for chunk in audio_chunks_512_samples:  # 32ms each at 16kHz
    res = vad(chunk, return_seconds=True)
    if res:
        if 'start' in res: print("user started speaking")
        if 'end' in res: print("user stopped speaking")
```

### WebRTC VAD
- Bulletproof, cheap, frame-level (10/20/30 ms frames at 8/16/32/48 kHz). Aggressiveness 0–3.
- Use as cheap pre-gate before Silero, RealtimeSTT-style: WebRTC VAD says "maybe speech" → buffer audio → Silero VAD confirms turn end.

### Pyannote
- Diarization-grade. Heavy. Overkill for single-speaker DA-31 form-fill.

### Smart Turn (pipecat-ai/smart-turn-v2 / v3)
- **Open-source semantic VAD.** Whisper Tiny + linear classifier head, ~8 M params, int8 and fp32 builds.
- Predicts whether the user has finished their turn from raw audio (not transcript). Recognizes intonation, prosody, vocal patterns indicative of completion vs mid-thought pause.
- Smart Turn v2 was Daily.co's open-source release in 2025; v3 supports 13+ languages with int8 quantization for faster inference.
- **Pipecat reference impls use `Silero VAD → smart-turn v2 → STT → LLM → TTS`.** Silero gates speech presence; smart-turn says "done thinking" vs "just paused."
- For hackathon: skip if you don't have time. Silero with `min_silence_duration_ms=600` is "good enough" baseline.

### VAP (Voice Activity Projection — Ekstedt/Krylov)
- Predicts future 2 s of voice activity for two speakers (256-class joint activation). Multi-layer transformer + CPC + cross-attention.
- Research-grade (arXiv 2401.04868). Repo: ErikEkstedt/vap_turn_taking.
- Not packaged. Skip.

### Endpoint detection rule of thumb (without smart-turn)
- Silero + 500–700 ms silence threshold = ~95% of human turn-end perception.
- For form-fill voice flow specifically: longer silence (800 ms) reduces premature interruption ("Sergeant, my date of birth is..." [pause to think]) at cost of feeling slower.

## 7. Interruption / Barge-In

### Browser side
- `getUserMedia({ audio: { echoCancellation: true, noiseSuppression: true, autoGainControl: true } })`.
- echoCancellation: works on Chrome, Firefox 46+, Safari 11+. Without it, when the bot's speaker output bleeds into the mic, you'll falsely trigger barge-in every time the bot speaks.
- For headphones-on demo: still keep echo cancellation on (defense in depth).

### Server side (Pipecat pattern)
- `PipelineParams(allow_interruptions=True)` on PipelineTask construction.
- Frame types: `UserStartedSpeakingFrame`, `UserStoppedSpeakingFrame`, `StartInterruptionFrame`, `StopInterruptionFrame`.
- Custom hook to flag client:
```python
original_handler = transport.input()._handle_user_interruption
async def handler_with_signal(frame):
    await original_handler(frame)
    if isinstance(frame, UserStartedSpeakingFrame):
        await websocket.send_text("USER_SPEAKING")
transport.input()._handle_user_interruption = handler_with_signal
```
- `Interruption Strategies`: by default any user speech immediately interrupts; you can require min word count or volume threshold.
- On interrupt: cancel in-flight LLM gen (Ollama doesn't have a native cancel; close the streaming generator), drain TTS queue, clear browser audio buffer (send `STOP_AUDIO` event → client calls `audioBuffer.stop()` and discards queued chunks).

### LiveKit pattern
- Built into VoicePipelineAgent. Set `interrupt_min_words` parameter to require N words before interrupt counts. LiveKit's turn-detection model is **text-first** (analyzes transcript only) vs Smart Turn's audio-first.

## 8. Browser-Side Architecture

### AudioWorklet vs ScriptProcessor
- ScriptProcessorNode is **deprecated** since 2014 — runs on main thread, glitchy.
- AudioWorklet runs in a separate audio rendering thread, lock-free with main thread, 128-sample callbacks. Standard since 2018.
- Code: register `AudioWorkletProcessor` subclass via `audioContext.audioWorklet.addModule('worklet.js')`, connect with `new AudioWorkletNode(audioContext, 'my-processor')`.

### MediaStream → encode → WebSocket
- MediaStream from getUserMedia → AudioContext → AudioWorkletNode → process() reads input samples → posts to MessagePort → main thread → WebSocket.send(arrayBuffer).
- For Adjutant: send raw 16 kHz mono PCM16 (matches what whisper expects). Skip Opus encoding unless bandwidth-bound (you're not — same machine).

### Playback options for streamed TTS
- **Option A — Web Audio API + AudioBufferSourceNode (recommended for hackathon):** Server sends WAV bytes or raw PCM16 chunks over WebSocket. Client decodes with `audioContext.decodeAudioData()`, schedules each buffer to play immediately after the previous one ends:
```js
let nextStartTime = 0;
ws.onmessage = async (ev) => {
  const buf = await audioCtx.decodeAudioData(ev.data);
  const src = audioCtx.createBufferSource();
  src.buffer = buf;
  src.connect(audioCtx.destination);
  const startAt = Math.max(audioCtx.currentTime, nextStartTime);
  src.start(startAt);
  nextStartTime = startAt + buf.duration;
};
```
- **Option B — MSE:** higher complexity, requires container format (Opus in WebM or AAC in MP4). ChatGPT uses this. Not worth it for offline demo.
- **Option C — Direct PCM into AudioWorklet:** lowest latency (~10 ms) but requires writing the AudioWorklet processor with a SharedArrayBuffer ring buffer.

### Push-to-talk vs continuous listening
- **For hackathon demo with judges:** continuous listening with VAD-gated turns. Push-to-talk feels like a 2014 voice assistant. Continuous-listening + visible "listening / thinking / speaking" state indicator looks like ChatGPT AVM.
- Risk mitigation: include a kill-switch button labeled "Mute mic" so the demoer can pause if a judge starts asking questions mid-conversation.

### WebSocket vs WebRTC
- **WebSocket:** simpler, plays well with FastAPI native, no extra server. Higher latency (TCP vs UDP). For local-demo loopback, latency difference is negligible (<5 ms).
- **WebRTC (LiveKit / Pipecat SmallWebRTC):** lower jitter, native echo cancellation, but requires either a SFU (LiveKit) or peer negotiation flow. Pipecat's SmallWebRTCTransport is P2P browser↔server with no extra server needed.
- **Recommendation: stick with FastAPI WebSocket for Adjutant.** It matches your existing stack. The latency penalty over WebRTC on localhost is invisible.

## 9. End-to-End Orchestration Patterns

### Pipecat vs LiveKit Agents vs custom asyncio for Adjutant

**Pipecat:**
- Pros: Has KokoroTTSService, OllamaLLMService, SileroVADAnalyzer, SmallWebRTCTransport or FastAPIWebsocketTransport — all the pieces wired. The kwindla/macos-local-voice-agents repo is a working <800 ms voice-to-voice demo on M-series.
- Cons: Pipecat's framing/Pipeline abstraction is opinionated. Integrating your existing pikepdf form-fill + RAG citation flow means writing a custom FrameProcessor that intercepts the LLM's tool-call output and triggers PDF generation — this is achievable but adds 2–4 hr.
- **Risk: Pipecat changes its API frequently.** Lock the version (e.g., `pipecat-ai==0.0.105`) and pin everything.

**LiveKit Agents:**
- Pros: Mature, Apache 2.0, supports Ollama via OpenAI-compat plugin.
- Cons: Wants a LiveKit server (even self-hosted means another container). Browser SDK is its own thing — replacing your existing FastAPI + plain JS frontend means more rewrite.
- **Verdict: more rewrite than Pipecat, fewer benefits given your starting point.**

**Custom asyncio:**
- Pros: zero framework risk. Full control over the form-fill + refusal contract code paths. Direct mapping from your existing FastAPI + faster-whisper + Ollama + Chatterbox.
- Cons: you write your own VAD loop, sentence buffer, TTS queue, interruption signaling. ~4–8 hr of careful work.
- **For Adjutant given the constraints (<30 hr, must preserve form-fill flow, must preserve refusal contract): custom asyncio is the safest path.**

### "Always-listening" pipeline (custom asyncio architecture)

```
Browser:                              Server (FastAPI):
  ┌─────────────────────┐                ┌─────────────────────────────┐
  │ getUserMedia        │                │  /ws  WebSocket             │
  │ AudioWorklet        │  PCM16 16kHz   │   ↓                         │
  │   resampler        →│ ─────────────→ │  ring_buffer (5s)           │
  │   downsampler       │                │   ↓                         │
  └─────────────────────┘                │  Silero VAD streaming       │
                                         │   - on speech_start: clear  │
  ┌─────────────────────┐                │     LLM/TTS in-flight       │
  │ AudioBufferSource  ←│ ←───────────── │   - on speech_end: flush    │
  │ Queue              ←│  WAV chunks    │     buffer to STT           │
  │ State indicator     │                │   ↓                         │
  └─────────────────────┘                │  faster-whisper small.en    │
                                         │  (or distil-whisper)        │
                                         │   ↓                         │
                                         │  Ollama llama3.2:3b stream  │
                                         │   ↓ token deltas            │
                                         │  Sentence buffer            │
                                         │   ↓ on [.!?]                │
                                         │  Kokoro TTS (chunked yield) │
                                         │   ↓ audio chunks            │
                                         │  WebSocket send             │
                                         └─────────────────────────────┘
```

### Latency budget (target end-of-speech → first audio out: <1.2 s on M2)
- Browser audio capture + WS transport: 50 ms
- Silero VAD silence detection (500 ms threshold): 500 ms (this is the user-perceived lag, but conventional voice agents include this)
- faster-whisper small.en transcription of ~3 s utterance: 200–400 ms (RTF ~0.15 on M2 with int8)
- Ollama TTFT for llama3.2:3b with cached system prompt (<1 k tokens): 150–300 ms
- First sentence buffered (first ~5 tokens × ~33 ms/tok @ 30 tok/s): 165 ms — but this overlaps with TTFT, so add ~150 ms after TTFT
- Kokoro first-chunk render of ~10-word sentence: 200–400 ms warm
- WebSocket transport + decode + schedule: 30 ms
- **Total: ~1.3–1.9 s ESV→FAO if everything is sequential. Pipelining the LLM streaming → TTS flush brings effective TTFA down to ~700–1100 ms.**
- The 500 ms VAD silence is the dominant non-compressible chunk. Smart-turn could cut this to ~200 ms.

## 10. Pipecat / LiveKit offline support specifics

### Pipecat fully-local config

```python
from pipecat.pipeline.pipeline import Pipeline
from pipecat.pipeline.task import PipelineParams, PipelineTask
from pipecat.transports.network.fastapi_websocket import FastAPIWebsocketTransport, FastAPIWebsocketParams
from pipecat.audio.vad.silero import SileroVADAnalyzer
from pipecat.services.whisper.stt import WhisperSTTService  # local faster-whisper
from pipecat.services.ollama.llm import OllamaLLMService
from pipecat.services.kokoro.tts import KokoroTTSService

transport = FastAPIWebsocketTransport(
    websocket=ws,
    params=FastAPIWebsocketParams(
        audio_in_enabled=True,
        audio_out_enabled=True,
        vad_analyzer=SileroVADAnalyzer(),
        add_wav_header=True,
    ),
)
stt = WhisperSTTService(model="small.en", device="cpu", compute_type="int8")
llm = OllamaLLMService(model="llama3.2:3b", base_url="http://localhost:11434/v1")
tts = KokoroTTSService(
    model_path="/path/to/kokoro-v1.0.onnx",
    voices_path="/path/to/voices-v1.0.bin",
    settings=KokoroTTSService.Settings(voice="af_heart"),
)

pipeline = Pipeline([
    transport.input(),
    stt,
    llm,
    tts,
    transport.output(),
])
task = PipelineTask(pipeline, PipelineParams(allow_interruptions=True))
```

This is functionally equivalent to the kwindla/macos-local-voice-agents reference impl (which uses MLX-Whisper + Gemma 3B + Kokoro with target <800 ms voice-to-voice latency).

### LiveKit fully-local config
- Spin up LiveKit server (Docker), connect Ollama via `openai.LLM(base_url="http://localhost:11434/v1", api_key="ollama")`, use `silero.VAD.load()`, use `kokoro` plugin (community-maintained, may need patching), use Whisper STT plugin.
- More moving parts than Pipecat for offline-only.

## Recommended Architectures for Adjutant — Ranked

### Architecture A — Easiest to ship in <12 hr (RECOMMENDED for SCSP demo)
**Custom asyncio + minimal new deps. Direct evolution of current Adjutant.**

Stack:
- Browser: continuous getUserMedia → AudioWorklet (resample to 16 kHz mono) → WebSocket binary frames of PCM16 → server. Echo cancellation + noise suppression on. State indicator dots: idle/listening/thinking/speaking.
- Server: FastAPI WebSocket endpoint. Per-connection async task graph:
  1. **Silero VAD** (ONNX, 16 kHz, threshold 0.5, min_silence 600 ms) buffers audio. On speech_end → push utterance to STT queue; emit `USER_DONE` to client.
  2. On user_started_speaking while bot is speaking → emit `INTERRUPT` to client (which calls `source.stop()` on the queued AudioBufferSourceNodes), cancel current LLM stream task, drain TTS queue.
  3. **faster-whisper** (keep current `small.en, int8, CPU`) or swap to **distil-whisper/distil-large-v3 via faster-whisper** for free quality+speed bump.
  4. RAG retrieval (existing) → builds prompt → **Ollama llama3.2:3b** with `stream=True`. Iterate token deltas.
  5. **Sentence buffer** flushes complete sentences to TTS queue as they form. After full response, also fire form-fill and citation rendering.
  6. **Kokoro-onnx** loaded resident (model + voices in memory at startup), `voice=af_heart` or `af_bella`. Each sentence → audio bytes → WAV-wrapped → WebSocket send.
- Refusal contract preserved: existing prompt template + tool-use rules unchanged. The RAG citation flow runs in parallel after the full sentence stream completes; PDF appears in browser via separate `/api/form-fill` POST triggered by a final `RESPONSE_DONE` WebSocket event with the JSON form-fill payload.

Build estimate: 6–10 hr.
Risk: low. Every component is in your codebase or trivially installed (`pip install silero-vad kokoro-onnx`).

### Architecture B — Best ChatGPT-feel quality (if you have 12+ hr buffer)
**Pipecat + Kokoro + Ollama + Silero on FastAPI WebSocket transport.**

Stack:
- Server: Pipecat with `FastAPIWebsocketTransport` (or `SmallWebRTCTransport` if you want WebRTC's echo handling). Pipeline: `transport.input → SileroVADAnalyzer → WhisperSTTService(small.en or distil-large-v3) → OllamaLLMService(llama3.2:3b) → KokoroTTSService(af_heart) → transport.output`.
- `PipelineParams(allow_interruptions=True)` — Pipecat handles the barge-in cancellation graph for you.
- Add a custom FrameProcessor between LLM and TTS that intercepts assistant tool-calls (form-fill JSON), forwards text-only frames to TTS, and triggers `/api/form-fill` over a side-channel.
- Browser: use Pipecat's `pipecat-ai-small-webrtc-prebuilt` if you go SmallWebRTC, or write minimal WebSocket client matching FastAPIWebsocketParams (binary PCM16 frames in, WAV out).
- Optionally add **smart-turn-v3** in front of Silero for ChatGPT-grade endpoint detection.

Build estimate: 10–14 hr.
Risk: moderate. Pipecat API churn — pin `pipecat-ai==0.0.105` (or whatever you install). Form-fill side-channel needs careful frame interception.

### Architecture C — Safest fallback if A or B breaks
**Push-to-talk with current Adjutant code, plus a minimal latency reduction.**

Stack:
- Keep existing flow. Add:
  - **Streaming LLM**: switch Ollama call to `stream=True`. Don't wait for full response.
  - **Sentence buffer**: as response streams, fire each completed sentence to **pyttsx3 or `say` command** (one shot per sentence). Audio plays through laptop speakers directly (no browser playback complexity).
  - **VAD-gated mic**: replace the push-to-talk button with a "Hold to talk" or simple Silero VAD detect-then-record.
- Skip the browser audio playback complexity entirely; let macOS's `say -v Samantha` speak through the speakers. The judges will see the response text appear word-by-word in the browser AND hear audio from the laptop.
- The form-fill PDF flow stays untouched.

Build estimate: 2–4 hr.
Risk: minimal. Mostly additive to existing code. UI feels like 2018 voice assistant but it works.
Quality penalty: not "ChatGPT-feel" — this is "demo-survives-judging."
