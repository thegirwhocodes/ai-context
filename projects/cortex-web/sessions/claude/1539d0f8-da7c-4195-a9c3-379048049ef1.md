# Can Cortex function without Google OAuth?

**Short answer: yes, three real paths. The cheapest one lets you launch to unlimited users today with ~15 files of work. But the strategic answer depends on how much friction you're willing to put on the "5-minute concierge onboarding."**

## The current lock-in

Cortex is deeply Gmail-coupled. The Explore audit found:
- **~25–35 files** reference Gmail specifically (`assistant-loop`, `email-send-policy`, `action-detector`, `relationships/drafting`, `attention/feed`, `lora/data-formatter`, plus the whole `lib/integrations/gmail.ts` adapter and its Google-only ceremony files)
- **15+ DB `CHECK` constraints** across migrations 001, 017, 025, 027 hardcode `provider IN ('gmail', …)`
- One entire ~8,000-line migration (`025_google_oauth_security.sql`) is Google-OAuth-only
- The LoRA training set assembly is Gmail-only (`gmailThreadKey`, `gmailSourceIntegrationIds`)
- Zero IMAP/SMTP/Nylas/Aurinko scaffolding exists anywhere

**So this isn't a swap — it's an "add a parallel email adapter" project.** Good news: the `RawItem` shape is generic and the ingestion pipeline is provider-agnostic, so the plumbing already supports it once you break the Gmail assumption in ~20 well-defined places.

## The five real options

### Option A — IMAP+SMTP with app passwords (Naomi supplies each tester with a 16-char password)

**How it works:** User turns on 2-Step Verification in their Google account, generates a 16-character "app password," pastes it into Cortex. Cortex reads via `imap.gmail.com:993` and sends via `smtp.gmail.com:465`. **Bypasses OAuth entirely** — no consent screen, no scope review, no CASA, no 100-user cap.

**Naomi-facing friction:** the concierge onboarding gains one extra step: "OK, now go to myaccount.google.com/apppasswords, generate a 16-char code, paste it here." For a $500/mo founder in a Zoom setup call this is fine. As of Jan 2025 Google made IMAP always-on by default, so this path is more stable now than ever.

**Also works for:** iCloud, Fastmail, Proton (any user with a Mail app password), Outlook (via `outlook.office365.com:993`). Same code path.

**Engineering cost:** ~10–15 files. Add IMAP client (`imapflow` or `node-imap`) + SMTP (`nodemailer`) adapter, relax the `provider IN ('gmail')` DB constraints, split `email-send-policy.ts`'s Gmail-only assumption, add a new `IntegrationProvider` value like `imap_smtp`. One new migration.

**Downside:** app passwords are revoked when the user changes their main password (rare but happens). Workspace admins can disable app passwords in their domain (irrelevant for consumer Gmail).

### Option B — Nylas or Aurinko (third-party unified email API)

**How it works:** Nylas/Aurinko sit in front of every user's mailbox. **They hold the Google OAuth verification, not you.** Cortex talks to Nylas's API, Nylas talks to Google/Microsoft/etc. From Google's perspective, Nylas is the verified app, not Cortex.

**Cost impact on the $299/mo product:**
- **Aurinko:** $1/account/mo (up to 1 GB), $1.50 (up to 5 GB), $2 (unlimited). At $2/user, that's 0.7% of your $299 revenue. Almost invisible.
- **Nylas Full Platform:** $15/mo including 5 connected accounts, then $2 per additional account. Higher fixed floor, roughly the same per-account cost past 5 users.

**Engineering cost:** 5–10 files. Replace `GmailAdapter` with `NylasAdapter` (or run both in parallel), keep the abstractions. Faster to ship than Option A.

**Real downside:** dependency risk. Nylas has changed pricing/architecture multiple times; Aurinko is newer but smaller. If they go down, so does every user's email. Also: they charge per-account so bulk email hoarders (like founders with 3 inboxes) cost 3x.

### Option C — Extend the Composio Outlook rail that's already half-wired

The audit found Composio already has `OUTLOOK_LIST_MESSAGES` + `OUTLOOK_SEND_EMAIL` allowlisted (`lib/composio/toolkits.ts:32`, `action-policy.ts:22`) but **nothing wires it into ingestion or the action-adapter router.**

**Effort:** ~5–8 files, per the audit. Cheapest path per file.

**But:** this only helps *Outlook* users. It doesn't solve the Gmail 100-user cap. Useful as a bonus, not a solution.

### Option D — Forward-to-Cortex + Cortex SMTP relay

User sets a Gmail forwarding filter → mail hits Cortex's inbound webhook (SendGrid Inbound Parse or Postmark). Sending happens through Cortex's own SMTP. **Zero Google OAuth.**

**Downsides:** emails you send appear "From: naomi via cortex-relay.app" unless the user configures Gmail's "Send As" with SMTP-Auth to your relay (moderate technical setup). Deliverability risk (your relay's reputation, not Google's). Doesn't get full history — only mail forwarded after setup. Not a fit for a $500/mo product.

### Option E — Just do CASA (current path)

- **$540/year** for CASA Tier 2 (or up to $1,800 depending on assessor)
- **4–12 weeks** from submission to verified
- Requires: privacy policy on your domain (you have one), OAuth consent screen with restricted scopes justified, demo video, security assessment against Cloud Application Security Assessment (CASA) Tier 2 checklist
- Once passed: unlimited users, gmail.readonly + gmail.send both work
- One team even reported passing CASA Tier 2 "in a weekend with Claude as security engineer" — the CASA checklist is well-defined and mostly a paperwork/config drill

**No engineering cost. Just calendar time and $540.**

## What I'd actually recommend

**Do both A and E in parallel.**

1. **File for CASA today.** $540 + a Naomi weekend + a few weeks of review = broad launch unlocked, no code changes, no dependency, no COGS impact. This is going to happen eventually; delaying it just delays growth. There's a Nylas post on the exact submission checklist and Google's own restricted-scope-verification page has the full requirements.
2. **Add Option A (IMAP + app password) as the "power user" path** during the CASA wait. It also becomes your permanent answer for iCloud/Fastmail/Proton/Outlook users forever after. And it's the only path that lets you honestly say "Cortex works with your existing email, whatever it is."

**Do NOT go with B (Nylas/Aurinko).** For a solo founder paying yourself back on a credit card, adding a per-user recurring cost + a critical dependency + a vendor you can't control is the wrong bet for a $299–$500/mo product. The COGS math looks fine (~$2/user) but the *operational risk* — if Nylas has an outage, every customer's Cortex goes dark simultaneously and it's not your bug to fix — is not what you want in early growth.

**Skip C** — extends only to Outlook, doesn't solve the CASA cap.

**Skip D** — the "via cortex-relay.app" thing kills the concierge feeling.
