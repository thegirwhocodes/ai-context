This exact question was already deep-researched today in an earlier session — I found a detailed memory on it and re-verified the key claims live against GitHub just now. Here's where things actually stand:

**The premise checks out, but the specific implementation (Kokoro) is blocked by an unrelated OS bug.** iOS *does* let Core ML keep running on the Neural Engine in the background while GPU/Metal is hard-blocked — that part of your framing is correct. But Kokoro-82M's CoreML port (via FluidAudio's `KokoroAneManager`, already wired up experimentally in your working tree at [KokoroAneSpeechEngine.swift](Aloud/Speech/KokoroAneSpeechEngine.swift)) crashes with `EXC_BAD_ACCESS` inside Apple's own `libBNNS.dylib`, on **any** compute-unit routing, on all iOS 26.4+ builds. I checked FluidAudio's source just now: `isBnnsCrashProneOS` shows Apple fixed this on **macOS** 26.6 but iOS is still flagged with no ceiling — confirmed by a newer issue (#844) than what's in the memory. It's not fixable from app code; three independent GitHub issues (#328/#587/#817) trace it to Apple's CoreML→LSTM→BNNS routing, including one report where the *identical binary* flipped from 40/40 pass to 0/15 crash on the same device with no identifiable trigger.

**Worse: the loophole itself has a posted expiration date.** Apple's iOS 27 release notes say plainly: "The system now restricts background access to the Neural Engine, similar to GPU usage restrictions." So even a from-scratch CoreML conversion that dodged the libBNNS bug today would lose background access in the next major iOS anyway.

I also checked PocketTTS (a different architecture FluidAudio ships, flagged in the memory as the real next question) — not a clean win either: its own docs show only one of its four submodels runs on ANE; the other two run on GPU, which likely hits the same background wall MLX does.

**The one genuinely buildable win:** your lookahead is currently 1 sentence ([Narrator.swift:320](Aloud/Speech/Narrator.swift#L320)). Rendered PCM is cheap (~96 KB/s), so buffering several minutes deep while foregrounded would make the common case — screen locks while listening — invisible without touching Metal or Core ML during the background window at all, using nothing but the `audio` background mode you already have. The existing instant fallback to the system voice stays as the safety net for whenever that buffer runs dry.

I've updated the memory with today's re-verification. Want me to implement the deeper-lookahead buffering?

Yes — and there's already a working precedent for exactly this, from a completely independent app.

**Drop FluidAudio and CoreML/ANE entirely; use ONNX Runtime's CPU execution provider instead.** I found `dfakkeldy/Echo`, a similar EPUB/audiobook reader, that hit the *identical* CoreML/ANE Kokoro wall (crashes, plus a ~20-minute on-device compile on an A14) and pivoted away from CoreML completely. Their reasoning, from a research brief in their repo:

- ONNX Runtime's CoreML execution provider can't handle Kokoro's dynamic shapes, so it falls back to plain **CPU** by construction — the model physically never touches the ANE/BNNS crash path, because it never touches CoreML at all.
- Pure CPU compute is exactly what the `audio` background mode already grants indefinitely — no GPU, no ANE, no Metal command buffers, none of the walls we hit. This is the same CPU grant your existing system-voice fallback already relies on to keep talking in the background.
- Measured RTF ≈ 0.8 (near real-time) on an **iPhone 12 Pro / A14** — a 2020 chip, weaker than anything this app targets today. On a modern device there should be real headroom.
- Model: `onnx-community/Kokoro-82M-v1.0-ONNX` (`model_fp16.onnx`, 163 MB, Apache-2.0) — I confirmed it's live on HuggingFace and covers every English/British voice ID you already list in [KokoroAneSpeechEngine.swift](Aloud/Speech/KokoroAneSpeechEngine.swift). Runtime: `microsoft/onnxruntime-swift-package-manager` (confirmed live, MIT, iOS 16 floor).

This sidesteps everything: the libBNNS crash, the iOS 27 ANE lockdown, all of it — because it's not asking iOS for a background exception, it's just CPU work the OS already lets background audio apps do.
