# Amazon Alexa — End-to-End Architecture (Cited Engineering Findings)

Every claim is followed by its source URL and a one-line authority note. Items I could only confirm on lower-quality sources are flagged **[unverified]**.

## 1. The two-stage pipeline: on-device vs. cloud, and why

- Wake-word detection runs **on the device**; only after the wake word is positively detected does the device send the request to the cloud: "Only after positively identifying the wake word does an Alexa-enabled device send your request to the cloud for further processing." — https://www.amazon.science/blog/amazon-alexas-new-wake-word-research-at-interspeech *(Amazon Science — first-party Amazon research blog; authoritative.)*
- The four foundational cloud/edge tasks Alexa was built on: (1) **wake-word detection on the device**, (2) **ASR in the cloud** ("convert audio streamed to the AWS cloud into words"), (3) **NLU** to extract meaning, (4) **TTS** to convert the textual response to spoken audio. — https://www.amazon.science/blog/alexa-at-five-looking-back-looking-forward *(Amazon Science; authoritative first-party.)*
- Classic split: wake word local; **ASR + NLU + dialog + TTS in the AWS cloud**, because cloud models are far larger/more powerful than what fits on the device. On-device models "must have small memory footprints, which means they sacrifice some processing power." — https://www.amazon.science/blog/amazon-alexas-new-wake-word-research-at-interspeech *(Amazon Science; authoritative.)*
- **Why cloud:** model size/compute. Amazon's newer on-device ASR required "compressing our models into less than 1% as much space — with minimal loss in accuracy," illustrating how much larger the cloud-native models are. — https://www.amazon.science/blog/on-device-speech-processing-makes-alexa-faster-lower-bandwidth *(Amazon Science; authoritative.)*
- **Why local (latency/bandwidth/privacy):** moving ASR on-device on supported devices (RNN-T model) reduces bandwidth — instead of "streaming encrypted audio streams to the cloud in small snippets," only a **lattice** (a graph of candidate word sequences with transition probabilities) is sent to the cloud, where "a large and powerful neural language model reranks the hypotheses." The lattice can only be sent once the user finishes speaking, since later words change earlier probabilities. — https://www.amazon.science/blog/on-device-speech-processing-makes-alexa-faster-lower-bandwidth *(Amazon Science; authoritative.)*
- On-device components in the newer architecture include: **ASR (RNN-T), end-pointing, whisper detection, speaker identification, context/biasing, and NLU**, with a cloud LM for lattice rescoring. — https://www.amazon.science/blog/on-device-speech-processing-makes-alexa-faster-lower-bandwidth *(Amazon Science; authoritative.)*
- **Encryption:** audio sent to the cloud is encrypted before transmission (general framing in the wake-word blog and on-device blog, which contrasts "encrypted audio streams"). — https://www.amazon.science/blog/on-device-speech-processing-makes-alexa-faster-lower-bandwidth *(Amazon Science; authoritative.)*

&gt; Note: There are two architectural generations here. (A) the **original/cloud-ASR** design — wake word local, raw audio streamed to cloud for ASR+NLU; (B) the **on-device-ASR** design (newer, capable devices) — ASR+NLU local, only the lattice goes up for cloud rescoring. An engineer should treat these as two deployment modes, not a contradiction.

## 2. Why the wake word must be local + always-on

- The microphone is **always listening**, but to preserve privacy/bandwidth, nothing is sent to the cloud until the local detector fires: only a positively detected wake word triggers cloud transmission. A device that streamed all audio continuously would be a privacy and bandwidth problem; the local detector is the gate. — https://www.amazon.science/blog/amazon-alexas-new-wake-word-research-at-interspeech *(Amazon Science; authoritative.)*
- The wake-word model is deliberately **small-footprint** so it can run continuously on constrained device hardware, at the cost of some accuracy — which is then recovered by a **second, larger cloud verification model**. — https://www.amazon.science/blog/amazon-alexas-new-wake-word-research-at-interspeech *(Amazon Science; authoritative.)*
- **Two-stage wake-word confirmation:** the device's small model detects a likely wake word and sends a short audio snippet to the cloud, where "a larger, more-powerful model" confirms (or rejects) it. The snippet includes "half a second of audio preceding the device's estimate of the wake word's start" to ensure complete capture. — https://www.amazon.science/blog/amazon-alexas-new-wake-word-research-at-interspeech *(Amazon Science; authoritative.)*

## 3. Alexa Voice Service (AVS) architecture — capture, buffer, stream, directive model

- **Audio format:** AVS expects **16-bit Linear PCM, 16 kHz, single channel, little-endian** — payload `format: AUDIO_L16_RATE_16000_CHANNELS_1`. — https://github.com/alexa/avs-device-sdk/issues/182 *(Official alexa/avs-device-sdk GitHub repo issue; first-party SDK, authoritative. The newer SDK also supports OPUS encoding for upstream bandwidth savings — see DeepWiki below.)*
- **Speech profiles** (acoustic/mic geometry hints): `CLOSE_TALK`, `NEAR_FIELD`, `FAR_FIELD`; sent in the Recognize event payload. — https://alexa.github.io/avs-device-sdk/namespacealexa_client_s_d_k_1_1capability_agents_1_1aip.html *(Official Alexa Client SDK API reference; authoritative.)*
- **The Recognize event:** the device's `AudioInputProcessor` (AIP) — an implementation of the `SpeechRecognizer` capability agent — captures mic audio and builds a **Recognize event** (header namespace `SpeechRecognizer`, name `Recognize`) sent to AVS. Calling `recognize()` starts the audio event; `stopCapture()` stops sending audio. — https://alexa.github.io/avs-device-sdk/classalexa_client_s_d_k_1_1capability_agents_1_1aip_1_1_audio_input_processor.html *(Official Alexa Client SDK API reference; authoritative.)*
- **Buffering / streaming pipeline:** mic input flows into a `SharedDataStream` ring buffer; a **Wake Word Engine (WWE)** monitors that stream; on detection the AIP captures from the stream, encodes (**LPCM or OPUS**), and streams it to AVS. — https://deepwiki.com/alexa/avs-device-sdk *(Third-party but SDK-derived wiki; corroborates first-party SDK structure. Treat structural claims as reliable; exact wording unverified against first-party docs.)*
- **Transport / request-response-directive model:** the device keeps a **persistent HTTP/2 connection**. A **downchannel** (DownchannelHandler) holds the long-lived connection for receiving **directives** from the cloud. The flow: AIP sends Recognize event over the Alexa Communication Library (ACL / HTTP2Transport) → AVS returns **directives** → the **Directive Sequencer (ADSL)** routes them to **capability agents** (e.g., `SpeechSynthesizer` for TTS playback, `AudioPlayer`, `Alerts`). — https://deepwiki.com/alexa/avs-device-sdk *(SDK-derived wiki; HTTP/2 + downchannel + directive-sequencer model is consistent with the official SDK component names.)*
- **Multi-turn:** AVS can return an **`ExpectSpeech` directive** telling the device to immediately reopen the mic for a follow-up turn without a new wake word; handled by the AIP. — https://alexa.github.io/avs-device-sdk/classalexa_client_s_d_k_1_1capability_agents_1_1aip_1_1_audio_input_processor.html *(Official Alexa Client SDK reference; authoritative.)*

## 4. Endpointing (end-of-utterance detection)

- The task — knowing when the user has finished — is called end-of-utterance / end-of-query / end-of-turn detection, or "end-pointing." — https://www.amazon.science/blog/alexa-scientists-address-challenges-of-end-pointing *(Amazon Science; authoritative.)*
- **Two failure modes:** **early end-points** (cutting the user off during a pause/breath) and **late end-points** (waiting too long, or treating background speech as device-directed). Both are perceived by users as latency. — https://www.amazon.science/blog/alexa-scientists-address-challenges-of-end-pointing *(Amazon Science; authoritative.)*
- **Approaches:** earliest end-pointers used **pause length**; with end-to-end ASR, models are trained with a special **end-of-speech token** the model emits as part of its hypotheses. — https://www.amazon.science/blog/alexa-scientists-address-challenges-of-end-pointing *(Amazon Science; authoritative.)*
- **Multi-signal model** (acoustic + linguistic): (1) an **LSTM acoustic classifier** over ~25 ms audio frames reading speaking rate/pitch/vowel length for finality cues; (2) an **LSTM word-based classifier** over partial ASR transcripts (e.g., an utterance ending in a preposition likely continues); (3) a **meta-features** layer using ASR-decoder silence/noise-duration signals, fused by a final classifier. — https://www.amazon.science/blog/alexa-scientists-address-challenges-of-end-pointing *(Amazon Science; authoritative.)*
- **Speculative endpointing for latency:** the on-device system uses a **speculative end-pointer tuned ~200 ms faster** than the final endpointer so downstream tasks can start earlier, with correction if the speculation is wrong. — https://www.amazon.science/blog/on-device-speech-processing-makes-alexa-faster-lower-bandwidth *(Amazon Science; authoritative; this is the one concrete latency number I found.)*
- **Two-pass / EP Arbitrator:** a first-pass endpoint is verified by a second-pass **EP Arbitrator** model to improve the early-cutoff vs. latency trade-off; reported to help "regardless of the first-pass EP model used," evaluated on transactional, conversational, and the public SLURP datasets. — https://www.amazon.science/publications/two-pass-endpoint-detection-for-speech-recognition and arXiv preprint https://arxiv.org/abs/2401.08916 *(Amazon Science publication + arXiv; authoritative. Specific percentage latency/cutoff numbers are in the full PDF, which I could not text-extract — **the exact metrics are unverified here**.)*
- **Cloud-side StopCapture:** in the cloud-ASR mode, the cloud decides the utterance ended and sends a **`StopCapture` directive** (namespace `SpeechRecognizer`, name `StopCapture`) telling the device to stop streaming. — https://github.com/alexa/avs-device-sdk (SpeechRecognizer interface; `stopCapture()`) *(Official SDK; authoritative for the directive existence and mechanism.)*

## 5. Barge-in / interruption handling

- **Barge-in behavior:** "When a customer barges in with a new request, Alexa knows to stop speaking and proceed with processing the new request." — https://www.amazon.science/blog/change-to-alexa-wake-word-process-adds-natural-turn-taking *(Amazon Science; authoritative.)*
- **Contextual barge-in:** when the interruption references what Alexa is currently saying, the system uses "the difference between the timestamps of the commencement of the interrupted speech and the interruption itself" to locate the referent in Alexa's output. — https://www.amazon.science/blog/change-to-alexa-wake-word-process-adds-natural-turn-taking *(Amazon Science; authoritative.)*
- **Acoustic Echo Cancellation (AEC) is a prerequisite for barge-in:** to let a user interrupt while the device's own loudspeaker is playing TTS/audio, AEC must subtract the device's known output from the mic signal so the recognizer doesn't hear its own voice. This is the standard duplex-processing requirement. — https://vocal.com/echo-cancellation/aec-barge-in/ *(VOCAL Technologies, a DSP/AEC vendor — domain-credible on the AEC mechanism but **not Alexa-specific; treat the "Alexa uses exactly this" link as unverified**.)* The AVS SDK community confirms AEC is expected to be implemented in the device's audio front-end, not the SDK: https://github.com/alexa/avs-device-sdk/issues/696 *(Official SDK issue tracker; authoritative that AEC is a device-side responsibility.)*
- **Natural turn-taking / device-directedness:** to allow follow-ups without repeating "Alexa," an **on-device fusion model** combines acoustic, visual (camera-based body/orientation), and linguistic cues to decide whether speech is device-directed. — https://www.amazon.science/blog/change-to-alexa-wake-word-process-adds-natural-turn-taking *(Amazon Science; authoritative.)*

## 6. Concrete numbers

# Wake Word ("Hey Cortex") — Browser vs Native: Constraints &amp; Tradeoffs

Cited bullet list for an engineering report recommendation section. Every claim has a source URL. Claims I could not anchor to an authoritative primary source are marked **[unverified]**.

## 1. Browser microphone &amp; background-tab constraints

- **getUserMedia mic access does NOT reliably persist as a continuous stream once the tab is backgrounded.** Continuous capture depends on the page staying alive and the audio graph staying active; Chrome's background-tab throttling is the governing constraint (below). [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- **HTTPS is mandatory.** `getUserMedia()` is only available in a *secure context* (HTTPS/TLS, `localhost`, or `file:///`). On plain HTTP, `navigator.mediaDevices` is literally `undefined`, so the mic cannot be accessed at all. [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- **AudioContext starts `suspended` and needs a user gesture to resume.** Browser autoplay policy means the audio graph (where you'd run wake-word inference) won't run until a user interaction resumes it — you cannot silently boot an always-listening pipeline on page load. [webrtc/samples #1028](https://github.com/webrtc/samples/issues/1028), [Chrome timer-throttling blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- **Background tabs get throttled in tiers (Chrome 88+):**
  - *Minimal* throttling if the page is visible OR "has made noises in the past 30 seconds."
  - *Standard* throttling (timers checked ~once/second) for hidden pages.
  - **Intensive throttling (timers checked once per MINUTE)** kicks in when ALL of: page hidden &gt;5 min, timer chain count ≥5, silent ≥30s, **AND WebRTC is not in use.** [Chrome timer-throttling blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- **The WebRTC / live-MediaStreamTrack exception is the key escape hatch.** A page with "a 'live' `MediaStreamTrack`" (i.e. an open mic from getUserMedia) qualifies for *standard* throttling rather than *intensive* throttling. So an open mic keeps the tab from being throttled to once-per-minute — but it does **not** exempt the tab from standard throttling, and it does **not** keep the tab alive if the OS/browser discards it, the laptop sleeps, or the user closes the tab. [Chrome timer-throttling blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- **Bottom line: a normal web page cannot do robust always-on background listening.** The tab must remain open; it does not strictly need *focus* (a held live mic track avoids the worst intensive throttling), but it is still subject to standard throttling, tab discarding, device sleep, and the user simply closing the tab. There is no web API for "keep listening after the page is gone." [Chrome timer-throttling blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88), [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- **Service workers are NOT a workaround.** Background service workers can't access the DOM/media, can be paused by Chrome at any time, and suspend when idle — live media must stay in a DOM-enabled context. **[unverified — secondary source]** [Recall.ai extension blog](https://www.recall.ai/blog/how-to-build-a-chrome-recording-extension)

## 2. Permissions / UX

- **Permission prompt is always required at least once.** "getUserMedia() must always get user permission before opening any media gathering input… Browsers may offer a once-per-domain permission feature, but they must ask at least the first time." [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- **Persistent permission is not guaranteed by spec** — it's at browser discretion; users "specifically grant ongoing permission if they choose to do so." The promise can also *neither resolve nor reject* if the user ignores the prompt. [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- **Permissions-Policy gating:** mic access is controlled by the `microphone` directive; only a top-level document of a valid origin can request it, unless an `&lt;iframe&gt;` is explicitly granted via `allow="microphone"`. [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- **Secure context (HTTPS) is a hard requirement** (restated from §1 — it's both a security and a UX gate). [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- **Audio start requires a user gesture** (AudioContext begins suspended) — so the UX flow must be "user clicks/taps → mic + audio graph start," not auto-start. [webrtc/samples #1028](https://github.com/webrtc/samples/issues/1028)

## 3. Battery / CPU cost of always-on mic + continuous NN in a tab

- **Holding a live mic keeps the tab out of deep throttling**, which by design prevents the browser from putting that tab to sleep — meaning sustained CPU and prevented power-down. This is the mechanism, not just a side effect. [Chrome timer-throttling blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- **On-device, in-browser wake word continuously runs a small neural net via WebAssembly**, processing every audio frame locally — an inherently always-on compute load. Picovoice positions this as practical *because the model is small*, implicitly because a large/cloud model would be impractical to run continuously. [Picovoice offline-in-browser blog](https://picovoice.ai/blog/offline-voice-ai-in-a-web-browser/)
- **Concrete per-watt battery figures for browser-tab wake word are not published by an authoritative primary source I could verify** — vendors assert "low power" / "superior privacy, lower latency" qualitatively but without browser-tab battery benchmarks. Treat specific battery-life numbers as **[unverified]**. [Picovoice wake-word guide](https://picovoice.ai/blog/complete-guide-to-wake-word/)

## 4. On-device vs cloud — privacy

- **Browser `SpeechRecognition` (Web Speech API) sends audio to a server by default — this is the privacy red flag.** MDN, verbatim: *"By default, using speech recognition on a web page involves a server-based recognition engine. Your audio is sent to a web service for recognition processing, so it won't work offline."* and *"Privacy: Many users are not comfortable with their speech being sent to a server."* In Chrome this service is Google's. [MDN Using the Web Speech API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API), [Chrome Web Speech blog](https://developer.chrome.com/blog/voice-driven-web-apps-introduction-to-the-web-speech-api)
- **A newer on-device option exists but is not the default.** MDN notes you can request recognition "performed locally in the browser" — but the default remains the platform/server service, and on-device availability is browser/OS-dependent. [MDN Web Speech API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API)
- **Porcupine and openWakeWord keep audio fully local.** Porcupine: *"audio never leaves the device, no microphone data transmitted, no cloud logs, no third-party data retention… works even with WiFi off."* This is exactly why a dedicated on-device wake word beats `SpeechRecognition` for an always-listening trigger: nothing is streamed to a server until *after* the wake word fires locally. [Picovoice Porcupine product](https://picovoice.ai/products/voice/wake-word/), [Picovoice offline-in-browser blog](https://picovoice.ai/blog/offline-voice-ai-in-a-web-browser/), [openWakeWord GitHub](https://github.com/dscripka/openWakeWord)
- **Why on-device wake word matters:** always-on means the mic is capturing continuously; if that stream went to the cloud it would be a continuous surveillance feed. On-device detection means only the brief utterance *after* "Hey Cortex" need ever leave the device. [Picovoice offline-in-browser blog](https://picovoice.ai/blog/offline-voice-ai-in-a-web-browser/)

## 5. What a native app unlocks (and its real limits)

- **Native unlocks true OS-level background listening via declared background modes** — something the browser fundamentally lacks. On **iOS**, continuous background audio requires the **Audio background mode** (`UIBackgroundModes: audio`) plus an `AVAudioSession`; without it, capture stops when backgrounded. [Apple AVAudioSession docs](https://developer.apple.com/documentation/AVFAudio/AVAudioSession), [Apple Developer Forums — background mic](https://developer.apple.com/forums/thread/106415)
- **iOS background mic is NOT unlimited.** It requires the explicit entitlement/background mode; "generally background apps cannot record audio while the foreground app is already reading audio from the microphone" (mic is effectively single-owner); and the standard `requestRecordPermission` prompt still applies. [Apple Developer Forums — background mic](https://developer.apple.com/forums/thread/106415), [Apple requestRecordPermission docs](https://developer.apple.com/documentation/avfaudio/avaudiosession/requestrecordpermission(_:))
- **Android requires a typed foreground service and is heavily restricted (Android 14+).** A `microphone` foreground service requires `RECORD_AUDIO` at creation or the system throws `SecurityException`. Foreground service *types are required* as of Android 14. [Android FGS types required](https://developer.android.com/about/versions/14/changes/fgs-types-required), [Android FGS service types](https://developer.android.com/develop/background-work/services/fgs/service-types)
- **Android "while-in-use" restriction is the gotcha:** `RECORD_AUDIO` is a while-in-use permission, so it's only held in the foreground. **You cannot start a microphone foreground service while the app is in the background** (SecurityException), and generally can't launch one from a `BOOT_COMPLETED` receiver — so "always-on from boot" is constrained. [Android FGS background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [Android FGS types required](https://developer.android.com/about/versions/14/changes/fgs-types-required)
- **macOS (SwiftUI/AppKit) is the most permissive of the three** for a true always-on desktop agent: a native macOS app can hold system mic access and run as a persistent/menu-bar process without the tab/throttle/background-mode constraints of browsers and mobile OSes. **[unverified — no single authoritative URL gathered; inferred from absence of the iOS/Android background-mode restrictions above. Recommend confirming against Apple's macOS AVCaptureDevice/TCC docs before publishing.]**
- **Net:** native = OS-level always-on, lower-overhead system mic access, and survival across app-background — but mobile OSes still gate it behind background modes, typed foreground services, while-in-use permission, and single-owner mic rules. It is *more* capable than a browser, not *unrestricted*. [Apple AVAudioSession docs](https://developer.apple.com/documentation/AVFAudio/AVAudioSession), [Android FGS restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

# Custom "Hey Cortex" Wake Word — Buildable Options for Web + Native

**Bottom line up front:** For a Next.js web app, the only genuinely production-ready, fully on-device, custom wake-word option is **Picovoice Porcupine Web (WASM)** — it's commercial, licensed, and has first-class React bindings. **openWakeWord** is the best open-source/free option but is **Python-first and does not officially run in-browser** (no JS port on its roadmap); browser use means either a community ONNX wrapper (unverified) or streaming audio to a Python backend. **Web Speech API cannot do wake words at all** (cloud-based, no custom keyword, ~60s session timeout, foreground-tab only). **Snowboy is dead.** Native macOS/iOS/Android get Porcupine native SDKs or openWakeWord (mobile via ONNX/tflite).

## 1. Picovoice Porcupine — recommended for the web path

**How it works**
- On-device deep-learning keyword spotting; in the browser it's powered by **WebAssembly + Web Audio API + Web Workers**, so audio never leaves the device. Models persist in IndexedDB. Requires a **secure context (HTTPS)**, except `localhost`. Source: https://picovoice.ai/docs/quick-start/porcupine-web/
- Custom keywords (e.g. "Hey Cortex") are **trained from text via transfer learning in Picovoice Console** (console.picovoice.ai) and exported as `.ppn` files — you select **WebAssembly** as the target platform for the browser build. ## 2. openWakeWord — best open-source option, but not native-browser

- **Open-source framework**, Python library running on **ONNX Runtime and TensorFlow Lite** (`pip install openwakeword`). Source: https://github.com/dscripka/openWakeWord
- **Custom training from synthetic TTS**: generate speech with open TTS (Piper/Kokoro) + negative audio (music/noise/speech); an end-to-end **Google Colab notebook trains a model in under an hour**, producing tiny (~hundreds-of-KB) ONNX models. Source: https://github.com/dscripka/openWakeWord , https://github.com/lgpearson1771/openwakeword-trainer
- **Accuracy target**: `&lt;5% false-reject` and `&lt;0.5/hour false-accept` with threshold tuning; the "alexa" model reportedly beats Porcupine on their test data (author's own benchmark — treat as such). Source: https://github.com/dscripka/openWakeWord
- **License — important split**: code is **Apache-2.0**, but **pre-trained models are CC-BY-NC-SA-4.0 (non-commercial)** because the feature-extraction backbone/training data carries NC restrictions. For commercial Cortex use you'd need to retrain/replace constrained components. (Flagging as the key legal gotcha.) Source: https://github.com/dscripka/openWakeWord

## 4. Browser Web Speech API — CANNOT serve as a wake-word engine

Hard limits, all cited — this is the most important "don't try this" finding:

- **Not on-device / privacy leak**: MDN — *"On some browsers, like Chrome, using Speech Recognition on a web page involves a server-based recognition engine. - **Session auto-stops (~60s)**: Chrome enforces a session timeout (~60 seconds) after which recognition stops and must be re-initiated; the common hack is restarting on the `onend` event, which is brittle and re-prompts/re-streams. - **Limited availability / not Baseline**: MDN — *"This feature is not Baseline because it does not work in some of the most widely-used browsers."* Effectively Chrome-centric. Source: https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition
- **Foreground/tab caveat**: continuous mic capture and recognition are tied to the page; it isn't a background OS service, and "any tab could listen forever" is exactly the abuse browsers throttle. Requires the tab open/focused with an active mic grant. (Cited concern; precise per-browser backgrounding behavior is **unverified**.) Source: https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API
- **Newer on-device knobs exist but don't fix this**: MDN documents `SpeechRecognition.processLocally`, `available()`, `install()` for on-device language packs — promising for transcription privacy, but still **no wake-word capability** and limited browser support. Source: https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition

# Wake-Word / Keyword Spotting (KWS) — Engineering Research Report

Every claim is followed by a source URL. Claims I could not pin to a primary/authoritative source are marked **[unverified]**.

## 1. Real-time on-device wake-word spotting (the always-on detector)

- A wake-word system listens continuously to an audio stream and detects predefined keywords without any latency, to provide a hands-free trigger; running it on-device avoids the latency and power cost of streaming to a server. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- Amazon's design is an **always-on, on-device detector** that prioritizes low latency and low computation; because on-device models must have small memory footprints, they sacrifice some processing power versus a server model. https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance
- The canonical small-footprint "Deep KWS" pipeline (Google, Chen/Parada/Heigold, ICASSP 2014) has three components: (i) a feature-extraction module, (ii) a deep neural net that predicts per-frame label posteriors, and (iii) a posterior-handling module that fuses frame posteriors into a confidence score. It makes a decision every 10 ms, and unlike the HMM approach it needs no Viterbi/sequence-search decoder — giving simpler implementation, lower runtime compute, smaller memory, and minimal latency. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- To save compute, the detector runs a lightweight **voice-activity detector (VAD)** first and only runs the KWS net in speech regions; in the Google system the VAD uses 13-dim PLP features + deltas/double-deltas into a 30-component diagonal-covariance GMM, smoothed by a hand-tuned state machine. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- Network families used across the field: feed-forward **DNNs** (Deep KWS) https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf ; **CNNs**, which outperform DNNs with far fewer parameters (Sainath &amp; Parada, Interspeech 2015) https://research.google/pubs/convolutional-neural-networks-for-small-footprint-keyword-spotting/ ; **CRNNs** (convolutional + recurrent) https://arxiv.org/pdf/1703.05390 ; and **depthwise-separable CNNs (DS-CNN)**, which decompose 3-D convolutions into 2-D + 1-D convolutions for far better parameter/op efficiency on microcontrollers (Zhang et al., "Hello Edge", 2017). https://arxiv.org/abs/1711.07128
- Amazon's newer on-device architecture is a **Time-Delayed Bottleneck Highway Network**, which uses highway connections to ease optimization of a deep stack and a bottleneck + time-delayed windows to cut dimensionality. https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance
- Picovoice **Porcupine** is a deep-neural-net wake-word engine designed to be compact and computationally efficient for IoT/edge, running on Arm Cortex-M (STM32, Arduino), Raspberry Pi Zero/3/4/5, Android, iOS, web browsers, and desktop OSes. https://picovoice.ai/docs/porcupine/
- **openWakeWord** runs a 3-stage pipeline on 16 kHz/16-bit PCM: (1) a melspectrogram pre-processor, (2) a shared, frozen Google speech-embedding feature model (a stack of simple conv blocks, pre-trained), (3) a small per-wake-word classifier (fully-connected or 2-layer RNN). A single Raspberry Pi 3 core can run 15–20 such models simultaneously in real time, indicating very compact models. https://github.com/dscripka/openWakeWord

## 2. Acoustic feature extraction

- **Deep KWS (Google)**: 40-dimensional **log-mel filterbank energies (LFBE)**, computed every **10 ms** over a **25 ms** window. Frames are stacked with asymmetric left/right context — the Deep KWS net uses **30 past + 10 future** frames (future frames add latency, so future context is limited); the HMM baseline used 10 past + 5 future. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- **MFCC vs filterbank**: microcontroller KWS ("Hello Edge") uses **MFCC** features — e.g. 40 MFCCs from a 40 ms frame with 20 ms stride (→ 49×40 = 1960 features per 1 s of audio), with smaller models using as few as **10 MFCC** coefficients and 20–40 ms strides. https://ar5iv.labs.arxiv.org/html/1711.07128
- (Context: log-mel filterbank energies are MFCCs without the final DCT/decorrelation step; modern neural KWS often prefers log-mel because the net can model correlated inputs, whereas MFCCs are favored where compute/memory is tightest — consistent with Deep KWS using LFBE and the microcontroller paper using MFCC. The two sources above support the per-system choice; the general rationale is **[unverified]** as a single cited statement.)
- **Trainable front-end**: Amazon replaced the handcrafted LFBE front-end with a **trainable front-end DNN** that learns features directly from a DFT representation of the audio, rather than fixed filterbanks. https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance
- **openWakeWord**: 16 kHz, 16-bit PCM; melspectrogram → frozen speech-embedding model; audio is processed in chunks that are **multiples of 80 ms** for best latency/efficiency. https://github.com/dscripka/openWakeWord
- **Sample rate** is 16 kHz across these on-device systems (Deep KWS/Google ASR pipeline operate at 16 kHz; openWakeWord explicitly requires 16 kHz). https://github.com/dscripka/openWakeWord

## 3. False-Accept (FAR) vs False-Reject (FRR) tradeoff and metrics

- The fundamental tradeoff is between **false alarms** (no keyword present but system fires) and **false rejects** (keyword present but system misses). In the HMM baseline it is tuned by the keyword/filler transition probability; in Deep KWS it is tuned by sweeping the **confidence threshold** (higher threshold → fewer false accepts, more false rejects). https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- Results are reported as a **modified ROC**: false-reject rate (Y-axis) vs false-alarm rate (X-axis), with curves per keyword averaged vertically at fixed FA rates; lower is better. A typical desirable operating point is **very low FA rate (e.g. 0.5% FA)**. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- The field also uses **AUC** (area under the FA/FR curve) as a single-number metric — Amazon reports its trainable front-end gave ~**20% relative AUC improvement** across false-alarm rates. https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance
- **False-accepts per hour** is the standard real-world FAR unit. openWakeWord targets **&lt; 0.5 false-accepts/hour** at **&lt; 5% false-reject**, evaluating FAR on the Dinner Party Corpus (~5.5 h far-field speech/music/noise) and FRR on reverberated/augmented positives. https://github.com/dscripka/openWakeWord
- Picovoice benchmarks Porcupine at **97.1% detection accuracy at 1 false alarm per 10 hours, at 10 dB SNR**; its compressed model gives 90%+ accuracy at the same 1-per-10-hours FA rate. https://picovoice.ai/blog/benchmarking-a-wake-word-detection-engine/
- Picovoice's open benchmark reports **miss rate of each engine at a fixed 1 false-alarm-per-10-hours** operating point (lower miss = better), comparing Porcupine, PocketSphinx, and Snowboy. https://github.com/Picovoice/wake-word-benchmark/blob/master/README.md

## 4. Model footprint (parameters / memory / compute)

- **Deep KWS** small net: 3 hidden layers × 128 ReLU units; because it outputs only **3–4 word labels** (vs 2,002 HMM states), it is far cheaper than an HMM-DNN — total **≤ 244M** parameters for the configuration described, vs ~373M for the HMM baseline net (the heavy cost is the output layer). https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- A larger Deep KWS config (6 hidden layers × 512 units) reaches **2.1M parameters** (vs 2.6M for the HMM baseline at that size). https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- **Microcontroller-class (DS-CNN, "Hello Edge")** — exact footprints from Table 5 (assuming 8-bit weights/activations, ~10 inferences/sec):
  - Small (≤80 KB / 6 MOps budget): **38.6 KB, 5.4 MOps, 94.4% accuracy** https://ar5iv.labs.arxiv.org/html/1711.07128
  - Medium (≤200 KB / 20 MOps): **189.2 KB, 19.8 MOps, 94.9%** https://ar5iv.labs.arxiv.org/html/1711.07128
  - Large (≤500 KB / 80 MOps): **497.6 KB, 56.9 MOps, 95.4%** https://ar5iv.labs.arxiv.org/html/1711.07128
  - The paper shows DS-CNN scaling down to microcontrollers with as little as **8 KB** memory. https://ar5iv.labs.arxiv.org/html/1711.07128
- **CNNs** generally beat DNNs at equal/smaller footprint: CNN architectures gave a **27–44% relative reduction in false-reject rate** vs a DNN within the same resource constraints. https://research.google/pubs/convolutional-neural-networks-for-small-footprint-keyword-spotting/
- **openWakeWord** custom models export to **~200 KB ONNX** classifiers on top of the shared frozen embedding. https://github.com/lgpearson1771/openwakeword-trainer
- **Porcupine** ships a standard model and a **4× smaller compressed model** for low-power use, with no added runtime footprint per extra keyword. https://picovoice.ai/docs/porcupine/ , https://picovoice.ai/blog/benchmarking-a-wake-word-detection-engine/

## 5. How wake-word models are trained and improved (data + two-pass detection)

- **Training data (Google Deep KWS)**: a general corpus of **3,000 hours** of transcribed speech ("VS" data) plus keyword-specific data — ~**2.3K positive examples per keyword** and ~**133K negatives** (anonymized voice-search queries); "okay google" had **40K** positives. Evaluation used ~1K positives + 70K negatives per keyword (a 1.4% positive ratio matching real usage). https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- **Loss/optimization**: DNN trained by **cross-entropy** on forced-aligned frame labels (labels from a 50M-param LVCSR system); optimized with **asynchronous SGD** (DistBelief), ReLU hidden units, softmax output. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- **Transfer learning**: initializing the KWS net's hidden layers from a general speech-recognition net (then fine-tuning on keyword data) yields more robust features and big gains — at 0.5% FA the transfer-learned Deep KWS got **45% relative FRR improvement** over the HMM baseline; under 10 dB babble noise, **39% relative improvement**. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- **Posterior handling**: raw frame posteriors are noisy, so they are smoothed over a window (wsmooth = 30 frames) and the confidence is the geometric mean of the max smoothed posteriors over a sliding window (wmax = 100 frames); a detection fires when confidence exceeds a threshold. https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/42537.pdf
- **Two-pass / two-stage detection — the core production pattern**:
  - *On-device first pass (cheap):* a small WWE detects "Alexa" locally. *Cloud second pass (expensive):* if the device thinks it heard the wake word, it sends a short audio snippet to a **larger, more powerful model in the cloud** for confirmation. https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance , https://developer.amazon.com/en-US/blogs/alexa/post/b136b3e7-0ba8-4589-aaf9-2a037fc4e9c9/cloud-based-wake-word-verification-improves-alexa-wake-word-accuracy-on-your-avs-product
  - The snippet includes the **half-second of audio preceding** the device's estimate of the wake-word start, so the cloud model sees the whole word. https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance
  - On a **false accept**, cloud verification fails to confirm → the device closes the audio stream and turns off the LED indicator (prevents acting on misfires and reduces uploaded audio). https://developer.amazon.com/en-US/blogs/alexa/post/b136b3e7-0ba8-4589-aaf9-2a037fc4e9c9/cloud-based-wake-word-verification-improves-alexa-wake-word-accuracy-on-your-avs-product
  - Cloud verification specifically reduces false wakes from **like-sounding words** (e.g. "ready", "Ed"). https://developer.amazon.com/en-US/blogs/alexa/post/b136b3e7-0ba8-4589-aaf9-2a037fc4e9c9/cloud-based-wake-word-verification-improves-alexa-wake-word-accuracy-on-your-avs-product
  - Security note: extracted **features (not raw audio)** can be sent and further obfuscated, hardening against man-in-the-middle/wiretap attacks. **[partly secondary-sourced — supported by the search summary above; corroborating primary doc not directly fetched]** https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance
- **Two-stage even on-device**: Amazon also adds an on-device second-stage classifier. **Monophone-based background modeling** (modeling non-keyword/background with monophone sound units) gave ~**16% relative FRR reduction** at fixed FA, ~**37% relative FA reduction** at fixed miss rate, and up to **~67% relative FA reduction** when combined with a second-stage monophone classifier. https://www.amazon.science/blog/alexa-scientists-present-two-new-techniques-that-improve-wake-word-performance , https://www.amazon.science/publications/monophone-based-background-modeling-for-two-stage-on-device-wake-word-detection

## How Alexa actually works
It's a **two-stage system**, and the key insight is that the "wait on call" part is deliberately tiny and local:

1. **On the device, always-on:** a *tiny* neural net (can be as small as 38 KB) does exactly one job — listen for the word "Alexa." **Nothing leaves the device until it fires.** That's for privacy, latency, and bandwidth. ([Amazon Science](https://www.amazon.science/blog/amazon-alexas-new-wake-word-research-at-interspeech))
2. **Only after the wake word** does it stream audio to the cloud for the heavy lifting: speech-to-text, understanding, the response, and text-to-speech. Those models are far too big to run on the device. ([Amazon Science](https://www.amazon.science/blog/alexa-at-five-looking-back-looking-forward))
3. **The pro trick:** the local detector is cheap and slightly sloppy, so a **bigger cloud model double-checks** the wake word before acting (kills false wakes like "ready"/"Ed"). Two-pass detection.

**This maps perfectly onto Cortex:** you already have the "cloud brain" (Claude + your RAG). What's missing is the small **on-device gate**.

## The honest truth about doing it in the browser
This is the part that matters most: **a normal web page cannot be a real always-on assistant.** Browsers require HTTPS + a mic-permission click, won't start audio without a user gesture, throttle background tabs, and **stop listening the moment the tab closes**. So in cortex-web you can have "Hey Cortex" working **while a Cortex tab is open and focused** — a genuinely useful demo — but not true Alexa-style background listening. That requires a **native app** (a macOS menu-bar companion is the strongest fit).

# ONBOARDING / PROGRESSIVE TRUST &amp; TIME-TO-FIRST-VALUE — Research Findings

## 1. Progressive permission / incremental OAuth scope — the winners earned scopes one at a time

- Google's own developer best-practices doc explicitly tells developers NOT to grab everything up front: "Select the smallest, most limited scopes possible," and "do not request access to data when the user first authenticates, unless it is essential for the core functionality of your app" — instead "use incremental authorization to request appropriate OAuth scopes when the functionality is needed by your application" (https://developers.google.com/identity/protocols/oauth2/resources/best-practices).
- Google ties this directly to consent conversion, not just hygiene: "Always request scopes in context to help your users understand why your app is requesting access," and warns "When requesting multiple scopes at once, users may not grant all OAuth scopes you have requested" (https://developers.google.com/identity/protocols/oauth2/resources/best-practices).
- Google's developer blog makes the conversion claim explicit: incremental authorization "improves the consent conversion for apps that use incremental authorization, which requests only one scope," and "We recommend using incremental authorization and requesting only one resource at the time your app needs it. We believe that doing this will make your account data request more relevant to the user and therefore improve the consent conversion" (https://developers.googleblog.com/google-oauth-incremental-authorization-improvement/). Note: Google asserts the inverse scope↔consent relationship but publishes no quantitative magnitude — treat the specific lift as unverified.
- COUNTERPOINT (important, well-argued): GMass argues Google's incremental authorization is "useless" in practice because the re-consent screen shows ALL previously granted scopes, not just the new one: "when you request access to scope Y, the user is told the app is asking for permissions for scope X _and_ scope Y," which "make[s] the application look poorly designed." The author calls Google's implementation "differential authorization" rather than true incremental auth (Chrome extensions show only new scopes; OAuth shows everything) (https://www.gmass.co/blog/oauth-incremental-authorization-is-useless/). Takeaway: the *strategy* of asking later is sound, but Google's UX undercuts it — design around the all-scopes re-prompt.

## 2. Permission-request UX: just-in-time / in-context beats up-front (strong evidence)

- Nielsen Norman Group is unambiguous: "Avoid asking for all permissions upfront, when the app is first installed" and "Whenever possible, initiate a permission request when the user selects a feature that requires that permission." Showing several consecutive requests at install creates "request fatigue" (https://www.nngroup.com/articles/permission-requests/).
- Framing/copy moves grant rates hard. NN/G cites research that simply providing *any* reason increased acceptance by ~12%, and a well-crafted, benefit-led rationale lifted acceptance by 81% vs. a vague explanation. Effective formula: "app would like to access your resource so that you can benefit/task"; avoid vague phrases "such as 'to offer a better user experience'" (https://www.nngroup.com/articles/permission-requests/). (The 81% figure recurs across sources as the canonical "compelling reason" lift.)
- Deferring requests to context raises grant rates: secondary UX sources cite "up to a 28% higher grant rate" for just-in-time vs. up-front, and note both Apple's HIG and Google's Android docs "explicitly recommend the just-in-time approach" (https://www.appcues.com/product-adoption-academy/mobile-app-onboarding-101/priming-users-to-grant-mobile-apps-permission). The 28% number is industry-blog-sourced — treat as directional/unverified vs. the NN/G-cited figures.
- Best practice = "priming" screen (a soft pre-prompt explaining value) BEFORE the OS hard prompt, so a denial doesn't permanently burn the permission. User-action-triggered dialogs outperform even priming screens because "users are expecting the request" (https://www.nngroup.com/articles/permission-requests/, https://goodux.appcues.com/blog/babbel-mobile-permission-priming).

## 3. Gmail / Google restricted-scope OAuth = a real, expensive friction wall

- Restricted scopes (Gmail read/modify, Drive, etc.) require passing a CASA (Cloud Application Security Assessment) audit by a Google-approved lab, then annual re-validation: "apps must be reverified for compliance and complete a security assessment at least every 12 months" (https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification).
- Cost is the headline friction. Independent developer reports: Gmail restricted-scope security assessments can run "$15,000–$75,000 or more" (https://www.gmass.co/blog/google-oauth-verification-security-assessment/; corroborated by https://medium.com/reversebits/the-50k-email-api-nightmare...). Lower CASA tiers can be cheaper ("a few hundred to a few thousand dollars"), but Gmail-grade restricted scopes sit at the high end.
- Timeline friction: restricted-scope verification commonly takes "2–6 months from start to approval," gated by Tier-2 DAST scans of production and a Self-Assessment Questionnaire (https://deepstrike.io/blog/google-casa-security-assessment-2025). Strategic implication for a personal-AI product: minimize/delay restricted scopes; lean on narrower scopes (e.g., gmail.send / metadata / compose) where possible to dodge the most expensive review tier, and don't request Gmail scope at sign-up before the user has felt value.

## 4. Superhuman's white-glove 1:1 onboarding — the canonical "earn trust with humans" play

- The model: every new user did a human-led video onboarding (initially up to 90 min = 30-min discovery + 60-min onboarding; later optimized to 30 min) where a specialist configured the app to their workflow, imported email, and trained shortcuts to inbox-zero (https://review.firstround.com/superhuman-onboarding-playbook/).
- Why: it fit their ICP (time-sensitive founders), a $30/mo price, and the goal of "no customer left behind." First Round frames it as inspired by Apple's Genius Bar / 5-star concierge experiences (https://review.firstround.com/superhuman-onboarding-playbook/).
- What it achieved (specifics): "Over 65% of new customers fully transitioned their email to Superhuman after their human-led onboarding" — more than double self-serve; "nearly 2x the activation rates versus self-serve"; and "the same 2x uplift in customer virality: Double the number of referrals per customer" (https://review.firstround.com/superhuman-onboarding-playbook/).
- The economics (the part skeptics miss): "Each fully ramped, full-time Onboarding Specialist was able to add up to $650k of topline ARR per year" (40 calls/wk × 45 wks × $30/mo × 12), against a fully-loaded cost of "$60k–$130k per specialist" plus management — i.e., high gross margin on the activity. They scaled to "dozens of Onboarding Specialists" and "tens of thousands of paying customers per year"; one specialist onboarded "over 3,900" customers (https://review.firstround.com/superhuman-onboarding-playbook/).
- Rahul Vohra's scalability argument (his recurring talking point): the misconception is that 1:1 concierge onboarding can't scale; he counters that "you only need in the region of 60 to 70 onboarding specialists" to reach roughly $100M ARR. This is the explicit thesis of the 20VC episode "How 1-1 Customer Onboarding Can Scale Efficiently to $100M ARR" (https://www.thetwentyminutevc.com/rahulvohra-2). Note: I could not retrieve the verbatim transcript quote from the episode page (it's a description, not a transcript) — the "60–70 specialists / $100M ARR" framing is well-attributed to Vohra across summaries but the exact wording should be verified against the audio before quoting directly.

## 5. Time-to-first-value / "aha moment" / activation benchmarks

- Speed bar (productivity/PLG): industry guidance now targets the aha moment "in under 5 minutes, with the best averaging 2–3 minutes," and claims "products that deliver the aha moment within the first session see 2.4x higher trial-to-paid conversion than those taking 3+ sessions" (https://productquant.dev/blog/5-minute-aha-rule-optimize-ttv/). These are blog benchmarks — directional, mark as unverified.
- Friction rule of thumb, repeatedly stated: "The more work you make a user put in before they hit their 'aha,' the less likely they'll stick around — if you can get users to their aha moment before requiring credit card info or login, do it"; and product tours "with more than four steps had below-average completion rates" (https://www.chameleon.io/blog/successful-user-onboarding, https://www.appcues.com/blog/aha-moment-guide).
- How to define activation rigorously (Lenny's Newsletter): a 3-step method — brainstorm candidate aha moments from usage data → regression to find milestones correlated with retention → "Run some experiments to see if increasing the percentage of users hitting that moment increases their retention rate." Core principle: "A good activation metric is causal for your retention, not just correlative" (https://www.lennysnewsletter.com/p/how-to-determine-your-activation). Validation heuristic from secondary sources: a 10–15 percentage-point 30-day-retention gap between users who did vs. didn't hit the candidate event within 48h signals a genuine activation event (https://www.designwithvalue.com/aha-moment).
- Famous thresholds (the "magic numbers"): Facebook "7 friends in 10 days"; Slack "2,000 messages sent" (after which retention is ~93%); Twitter "follow 30 accounts"; Dropbox "save one file to one folder" (https://www.startups.com/lexicon/activation, https://www.june.so/blog/activation-playbook). CAUTION: Mixpanel argues these are over-mythologized — "Magic numbers are an illusion" — and warns against copying another company's threshold rather than deriving your own causally (https://mixpanel.com/blog/magic-numbers-are-an-illusion/). Treat specific numbers as illustrative, not prescriptive.

## 6. Granola, Notion AI, Mem, Rewind — friction &amp; TTFV patterns

- Granola (the standout frictionless case): "Setup takes under five minutes" and it captures meeting audio "locally, on your machine, without joining the call as a bot" — "no bot announcements, no new UI to master, just a notepad that transcribes" (https://www.granola.ai/blog/how-to-use-ai-to-take-meeting-notes...). Crucial nuance for personal-AI: technical onboarding is instant but *real* value is delayed — "it took me about a week of actual calls to understand the power of the platform," because a meeting tool needs real meetings to demonstrate value (https://zackproser.com/granola).
- Granola's deliberate anti-friction / trust bet paid off in retention: during a year-long stealth they "manually onboarded ~150 users"; by Series A (Oct 2024) they had 5,000 WAU, "Half of the people who tried Granola were still active 10 weeks later," users averaged 6 meetings/week, and 57% held leadership positions. They "deliberately rejected the visible bot model... sacrificing immediate viral distribution" — which unlocked sensitive meetings (board, M&amp;A) where bots get banned, creating defensibility (https://www.startupriders.com/p/granola-growth-playbook).
- Notion: aha moment = "creating or customizing a page." It uses a personal-workspace model so "users can reach their aha moment without depending on colleagues to join" — decoupling individual activation from team adoption. Retention "correlated strongly with 'time to first note'" (https://medium.com/@agfigmaworks/tales-of-uxr-chapter-4-0ef92000a3c9). Secondary, weaker source — treat as illustrative.
- Rewind: leaned hard into trust framing to overcome the friction of capturing everything on-screen — value "Be Trustworthy," "highest standards of privacy protection regardless of a customer's location" and local/on-device positioning, because the up-front ask (record my entire screen/audio) is a massive trust hurdle (https://rewind.com/legal/privacy-notice/, https://kevinchen.co/blog/rewind-ai-app-teardown/).

## Synthesis for a personal-AI product strategy
- The winners did NOT ask for everything up front. The dominant, well-sourced pattern is: deliver a fast self-serve "aha" with the *minimum* data, then earn each additional scope in-context, framed by benefit (Google docs + NN/G converge here).
- Two distinct trust models both work: (a) Granola/Notion frictionless self-serve where value arrives in &lt;5 min of setup (even if full appreciation takes ~a week); (b) Superhuman high-touch human onboarding that buys ~2x activation + 2x referrals and is *more* scalable and high-margin than skeptics assume (~$650k ARR/specialist; ~60–70 specialists ≈ $100M ARR per Vohra).
- For Gmail/Workspace specifically: restricted-scope CASA review ($15k–$75k, 2–6 months, annual renewal) is a hard gate — architect to delay/narrow Gmail scopes, never request them at sign-up, and request them only once the user has felt value and you can frame the exact benefit.
