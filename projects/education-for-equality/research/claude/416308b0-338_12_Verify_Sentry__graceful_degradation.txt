## Verification & Resilience Report — Sabi AT Routes + Sentry

### Part (a): Sentry setup verification

**Verdict: The setup is broadly correct and will build cleanly without `SENTRY_AUTH_TOKEN`, but it has ONE critical silent no-op: the AT webhook routes will NOT send error events to Sentry, because every error path is caught and converted to XML — nothing ever reaches the auto-instrumented wrapper that calls `captureException` + flush.**

What's confirmed good:
- **DSN wiring** — `process.env.SENTRY_DSN || process.env.NEXT_PUBLIC_SENTRY_DSN` on server/edge, `NEXT_PUBLIC_SENTRY_DSN` on client. Correct.
- **`tracesSampleRate`** — `1.0` dev / `0.2` prod across all three configs. Reasonable.
- **Build without auth token** — verified in SDK source: `getBuildPluginOptions.js` sets `sourcemaps.disable = true` when the token is absent (`skipSourcemapsUpload`), and `silent: !process.env.CI` suppresses output locally. `withSentryConfig` will build cleanly; you just lose readable stack traces until a token is added. No failure.
- **`onRequestError = Sentry.captureRequestError`** in `instrumentation.ts` — correct for Next 16, catches *uncaught* server errors.
- **Serverless flush IS handled by the SDK** — verified in `wrapRouteHandlerWithSentry.js`: on a thrown error it calls `core.captureException(...)` then `responseEnd.waitUntil(responseEnd.flushSafelyWithTimeout())`, and `responseEnd.js` uses `core.vercelWaitUntil(task)`. So for errors that *propagate out of the handler*, flushing before function exit is automatic. No manual `Sentry.flush()` is needed for those.

**The critical gap (silent no-op):**
The three AT routes (`incoming`, `recording`, `events`) wrap their entire body in `try/catch` and **return a valid `NextResponse` from the catch block**. Because nothing is rethrown, the SDK's auto-wrapper never sees the error → `captureException` is never called → `waitUntil(flush)` is never scheduled. The `Sentry.setTags(...)` calls run, but with no event to attach them to, they accomplish nothing. `consoleLoggingIntegration` will forward the `console.error` lines as *logs*, but you get no *error events*, no stack traces, no alerting, no grouping. This defeats the entire point of adding Sentry to these routes.

Note also: `Sentry.setTags`/`setContext` set on the **isolation scope** are fine within one invocation, but if you only fix this by adding `captureException` you must also ensure the manual flush runs, since a hand-captured event in a serverless catch block is NOT covered by the wrapper's auto-flush. Per `@sentry/nextjs` serverless semantics, a manually-captured event needs an explicit `await Sentry.flush(timeout)` (or `vercelWaitUntil`) before the function returns, or the event is lost when the Lambda freezes.

### Part (b): Graceful degradation

Current behavior is actually already partially layered (TTS has YarnGPT→ElevenLabs→AT `<Say>` fallback, and empty/low-confidence speech triggers a re-record). The real dead-ends are: **(1) the outer catch in `incoming` hangs up vs. inviting a retry**, and **(2) the outer catch in `recording` hangs up** instead of letting the child retry, and **(3) failures inside the happy path before TTS (Supabase `createCallState`, `callSabi`/Claude, `findOrCreateStudentByPhone`) fall straight to the hard outer catch** rather than degrading.

The single highest-value, lowest-risk improvement: **make the outer catches re-record-and-retry instead of hang-up**, with softer copy. A child who hears "let's try that again in a moment" and gets another `<Record>` prompt has a path forward; a hangup is a dead end.
