## MJPEG Bandwidth Reduction Techniques

You can cut bandwidth significantly without switching protocols:

1. **JPEG quality reduction**: Drop `cv2.imencode('.jpg', frame, [cv2.IMWRITE_JPEG_QUALITY, 50])` from default 95 to 40-60. This alone can cut bandwidth 50-70% with acceptable visual quality for monitoring.

2. **Resolution reduction**: `cv2.resize(frame, (640, 480))` before encoding. Going from 1080p to 480p cuts pixel count by 75%.

3. **Frame rate reduction**: Skip frames — serve every 3rd or 5th frame. At 30fps input, serving 10fps cuts bandwidth by 66% and is still smooth for surveillance.

4. **Adaptive quality**: Monitor send buffer backlog; when it grows, automatically drop quality/resolution/framerate. Pseudocode:
   ```python
   if send_queue_size > threshold:
       jpeg_quality = max(30, jpeg_quality - 10)
       skip_frames += 1
   ```

5. **Combined effect**: 720p + quality 50 + 10fps can reduce a 5 MB/s stream to under 500 KB/s.

## The WebRTC Alternative (Best Long-Term Answer)

**WebRTC would fundamentally solve your problem** because:

- **Peer-to-peer**: Video goes directly from your machine to the viewer's browser. No tunnel relay in the middle at all for the video data.
- **H.264/VP8 compression**: 10-50x more efficient than MJPEG. A 720p stream at 30fps uses ~1-2 Mbps instead of 30-50 Mbps.
- **Sub-200ms latency**: Typically 50-250ms end-to-end on the public internet.
- **The tunnel only carries signaling**: The initial WebRTC handshake (a few KB) goes through the tunnel, then video flows P2P. Your tunnel bandwidth problem disappears.

**Python libraries that make this easy:**

- **`aiortc`** — Pure Python WebRTC implementation on asyncio. The most mature option. `pip install aiortc`.
- **`LiveStream-WebRTC-Flask-OpenCV`** — Complete working example: Flask signaling server + aiortc + OpenCV camera capture. Available at [github.com/supersjgk/LiveStream-WebRTC-Flask-OpenCV](https://github.com/supersjgk/LiveStream-WebRTC-Flask-OpenCV).

**What you still need a tunnel for with WebRTC:**
- The Flask signaling server (tiny bandwidth — just SDP offer/answer exchange)
- A STUN server for NAT traversal (Google provides free ones: `stun:stun.l.google.com:19302`)
- A TURN server as fallback if P2P fails (~10-20% of connections). Free options exist or you can self-host `coturn`.

**Caveat:** WebRTC requires rewriting your frontend from `<img src="/mjpeg_feed">` to JavaScript WebRTC API calls. It is a bigger change but eliminates the root cause.
