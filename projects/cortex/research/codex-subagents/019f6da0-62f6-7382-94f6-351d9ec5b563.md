1. **[P1] Duplicate/late webhooks can redeploy an older adapter and retire the current one.**
   [024 migration](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:3736) accepts repeated terminal webhooks for already `submitted` attempts. The [webhook route](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/app/api/lora/webhook/route.ts:133) then unconditionally marks that adapter deployed and retires every other deployed adapter at lines 143–156.
   **Scenario:** adapter A completes; later B completes and retires A; a valid retry of A’s webhook redeploys A and retires B.
   **Minimal fix:** atomically consume the terminal transition once; treat identical replays as no-ops. Deploy only an eligible `training` adapter bound to that job, and retire only lower adapter versions—never newer ones.

2. **[P1] Disconnect between webhook writes creates a zero-row success that retires a surviving adapter.**
   [updateAdapterRecord](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/app/api/lora/webhook/route.ts:177) treats a zero-row update as success. The completed flow performs multiple separate writes before retiring other adapters at [lines 133–156](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/app/api/lora/webhook/route.ts:133).
   **Scenario:** webhook reads adapter A; disconnect deletes A between the completed/deployed writes; both updates affect zero rows without error, then the route retires still-valid adapter B.
   **Minimal fix:** move terminal transition, deployment, and version retirement into one locked RPC that requires exactly one eligible target row; otherwise no-op without retiring anything.

3. **[P1] The five-minute reconciler can consume retry caps for claims it never processes.**
   The route claims 25 rows despite a 60-second limit ([cron route](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/app/api/cron/training-reconciliation/route.ts:6), lines 14–16). SQL increments every row’s attempt count when bulk-claimed ([migration](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:3519)).
   **Scenario:** 25 ambiguous requests plus a stalled dispatcher; only roughly two receive network attempts before timeout, while all 25 consume a retry. Repeated claims can dead-letter tail rows without any lookup or replay.
   **Minimal fix:** claim one row at a time, or process a bounded parallel batch guaranteed within the execution budget; increment attempts only when processing actually starts.

4. **[P1] Multi-recipient Gmail messages still fabricate per-person name provenance.**
   Runtime extraction applies the first display name in the whole `To` header to every extracted email ([identity.ts](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/lib/relationships/identity.ts:64), [helper](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/lib/relationships/identity.ts:318)).    **Scenario:** `To: Alice <a@example.com>, Bob <b@example.com>` records “Alice” as Bob’s observed name; disconnect/rebuild can restore Bob as Alice.
   **Minimal fix:** parse mailbox entries individually and bind each display name to its exact normalized address. Skip name backfill when exact pairing cannot be proven.
