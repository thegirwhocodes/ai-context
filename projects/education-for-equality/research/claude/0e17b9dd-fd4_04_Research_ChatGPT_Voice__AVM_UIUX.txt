## 0. The TL;DR you can hand a designer

ChatGPT Voice is, visually, three layered concentric translucent spheres rendered as either (a) a full-screen WebGL fragment shader (ElevenLabs' approach, OpenAI's mobile approach) or (b) three Three.js `SphereGeometry` meshes with a custom Simplex-noise distortion vertex shader and a chromatic-aberration / fresnel fragment shader (the open-source pattern that matches what ChatGPT actually ships). The orb sits centered, at roughly 40-55% of viewport width on mobile and 320-512px on web. Background is full-bleed near-black with a soft radial vignette behind the sphere. The bottom bar pins **mute → end**; on iOS it adds **video** and **screen-share** buttons in a row of four. Status text sits about 24px below the orb in a small soft-grey san-serif. Transitions are 300-500ms ease-in-out; idle scale is 1.00, peak scale during speech is around 1.15-1.35.

OpenAI's *reference* implementation (the one in `openai-realtime-console`) is much simpler: a 100×40px frequency-bar canvas, not the full sphere — that's the developer console, not what ships in ChatGPT mobile. The ChatGPT mobile app version is a private build, but every public clone (and ElevenLabs, who publicly say they modeled their orb on the same pattern) converges on the same construction.

## 1. OpenAI's own reference code — exact numbers

### 1.1 The console's audio analysis pipeline

From `/tmp/avm-research/openai-realtime-console-classic/src/lib/wavtools/lib/analysis/audio_analysis.js` and `wav_stream_player.js` and `wav_recorder.js`:

```js
const analyser = audioContext.createAnalyser();
analyser.fftSize = 8192;
analyser.smoothingTimeConstant = 0.1;
```

**This is the canonical OpenAI choice.** They use `fftSize: 8192` (yields 4096 frequency bins) and `smoothingTimeConstant: 0.1` (low — they want responsive, not smoothed, because they downsample-by-peak afterward). They use the same exact config on **both** sides — the WavRecorder (mic) AnalyserNode and the WavStreamPlayer (TTS playback) AnalyserNode. Both run at `sampleRate: 24000` (matching the Realtime API's PCM16 24 kHz output).

Decibel range for normalization: `minDecibels = -100`, `maxDecibels = -30`. Normalized output is `(v - minDecibels) / (maxDecibels - minDecibels)` clamped to `[0,1]`. This is the exact mapping ChatGPT uses to convert raw FFT bins into a 0–1 amplitude usable by the visualizer.

There's also a "voice" analysis mode that filters the 4096 bins down to the 32 Hz – 2000 Hz human-voice band (subset of musical notes C1 through B6, defined as `voiceFrequencies` in `constants.js`). The mid-range bias is what makes the orb react to *speech* and not to room hum or sibilance.

For the **AudioBuffer** (offline Safari path) version, `fftSize` is the same 8192, `smoothingTimeConstant` is the same 0.1, and they sample the FFT at `1/60 s` intervals — exactly 60 fps.

### 1.2 What the console actually renders (this is the developer-console look, NOT ChatGPT mobile)

`/tmp/avm-research/openai-realtime-console-classic/src/utils/wav_renderer.ts` — the only renderer in the repo. It draws **vertical bars**, not a sphere. Two side-by-side 100×40px canvases sit at `bottom: 4px; right: 8px` (so 4px from bottom, 8px from right of their parent). Each canvas renders 10 bars at 8px spacing, color `#0099ff` for the user-mic canvas and `#009900` for the assistant-TTS canvas. Bar height = `Math.max(1, amplitude * canvas.height)`. The render function is called from `requestAnimationFrame` and reads `wavRecorder.getFrequencies('voice')` (live FFT) every frame. The Float32Array of frequency values is downsampled by **peak** (not average) into the 10-bar bucket array — `downsamplePeaks: true`. This is essentially a tiny in-call meter that lives in the corner of the events-log panel.

Color tokens used across the whole console:

- User / "client" / mic: `#0099ff` (the OpenAI blue)
- Assistant / "server" / TTS: `#009900` (a lab-green)
- Error: `#990000`
- Body text: `#18181b`
- Muted text: `#6e6e7f`
- Hover BG: `#f0f0f0`
- Code blocks: `#ececf1`

Push-to-talk button labels: `"push to talk"` → `"release to send"`. Connect labels: `"connect"` → `"disconnect"`. Mode toggle: `manual` ↔ `vad`. These are the OpenAI-blessed strings.

The 10-bar / 100×40 console look is **not** what users see in ChatGPT mobile. It's there because the console is for developers debugging the API. The mobile orb uses the same AnalyserNode config (`fftSize 8192, smoothingTimeConstant 0.1`) but feeds those values into a sphere shader instead of bars.

### 1.3 Realtime API event order — the spec your orb has to react to

From the `transitive-bullshit/openai-realtime-api` events.ts mirror (which mirrors the official spec):

**Server-emitted events (in the order they fire during one voice turn):**

1. `session.created` — websocket established, defaults loaded
2. `session.updated` — your `updateSession({ turn_detection, voice, instructions })` ack
3. `conversation.created` — once per session
4. *(user starts speaking)* `input_audio_buffer.speech_started` — VAD detected speech (this is your **listening → user-active** state trigger; carries `audio_start_ms`, `item_id`)
5. *(user stops speaking)* `input_audio_buffer.speech_stopped` — VAD detected end-of-speech
6. `input_audio_buffer.committed` — buffer flushed to server
7. `conversation.item.created` — user item appended
8. `conversation.item.input_audio_transcription.completed` — Whisper transcript ready (carries `transcript` string)
9. `response.created` — model started thinking (this is your **thinking** state trigger)
10. `response.output_item.added`
11. `response.content_part.added`
12. `response.audio_transcript.delta` — captions stream in
13. `response.audio.delta` — first PCM chunk arrives (this is your **speaking** state trigger; the chunk plays through WavStreamPlayer)
14. … many more `audio.delta` and `audio_transcript.delta` events …
15. `response.audio.done` — TTS chunk stream complete
16. `response.audio_transcript.done`
17. `response.content_part.done`
18. `response.output_item.done`
19. `response.done` — full turn complete (this is your **speaking → idle/listening** trigger)
20. `rate_limits.updated`

**Client-emitted events:**
- `session.update`
- `input_audio_buffer.append` (every PCM16 chunk from the mic)
- `input_audio_buffer.commit` (manual mode only)
- `input_audio_buffer.clear`
- `conversation.item.create`
- `conversation.item.truncate` (used during interruption — this is the magic of barge-in: you truncate the assistant's in-flight audio item at the sample-offset where the user started speaking)
- `conversation.item.delete`
- `response.create`
- `response.cancel`

**The interruption (barge-in) flow** — this is critical and your spec asked about it specifically. When the user speaks while the assistant is mid-response:

1. `input_audio_buffer.speech_started` fires while you are still streaming `response.audio.delta` chunks into WavStreamPlayer.
2. Client calls `wavStreamPlayer.interrupt()` — returns `{trackId, offset}` (the sample offset in the currently playing track).
3. Client calls `client.cancelResponse(trackId, offset)` which under the hood sends `conversation.item.truncate` + `response.cancel`.
4. Server stops emitting deltas. Visually, you instantly drop back to the **listening** state.

In the `openai-realtime-console-classic` ConsolePage.tsx (lines 472-478) this is exactly what they do on `conversation.interrupted`. **Your orb's interruption animation should be: snap-shrink to 0.95 scale over ~120ms with the speaking color crossfading to the listening color over the same 120ms.** No fancy explosion. Just a clean, fast cut.

### 2.1 Geometry — three concentric translucent spheres

From `voiceorb/app.js` lines 21-142, this is the **state machine** that drives every layer:

```js
const states = {
  idle: {
    layers: [
      { color: 0x434FCF, opacity: 0.2, scale: 1.00, rotationSpeed: { x: 0.001, y: 0.002, z: 0 } },
      { color: 0x434FCF, opacity: 0.2, scale: 0.85, rotationSpeed: { x: -0.002, y: 0.003, z: 0.001 } },
      { color: 0x434FCF, opacity: 0.4, scale: 0.70, rotationSpeed: { x: 0.003, y: -0.002, z: -0.001 } },
    ],
    audioLevel: 0.15, audioFrequency: 0.2, timeSpeed: 0.015,
    pulsate: false, chromaticAberration: 0.8,
  },
  listening: {
    // same three layers, color 0x434FCF (blue/purple)
    audioLevel: 0.6, audioFrequency: 0.7, timeSpeed: 0.022,
    pulsate: true, pulsateMode: 'audio-reactive',
    pulsateMin: 0.02, pulsateMax: 0.25, chromaticAberration: 1.2,
  },
  thinking: {
    // color 0x8747F7 (vivid violet)
    audioLevel: 0.45, audioFrequency: 0.5, timeSpeed: 0.020,
    pulsate: true, pulsateMode: 'thinking',
    pulsateMin: 0.0, pulsateMax: 0.15, chromaticAberration: 0.8,
  },
  speaking: {
    // color 0xFF1893 (bright magenta-pink)
    audioLevel: 0.8, audioFrequency: 0.9, timeSpeed: 0.027,
    pulsate: true, pulsateMode: 'cadence',
    pulsateMin: 0.05, pulsateMax: 0.22, chromaticAberration: 1.5,
  },

```

So three layers, scales **1.00 / 0.85 / 0.70** (this answers your "rest vs max radius" question — rest is 1.00 of the bounding radius, the inner two layers sit at 85% and 70% of the outer; during speech, the *outer* layer pulses up to roughly 1.22× of its rest, so peak ≈ 1.22 × 1.00 = 1.22, which means the orb pulses by about ±15-25% of its rest size).

Each layer rotates *independently* on x/y/z at the speeds shown. Speeds are tiny — `0.001` to `0.006` radians per frame at 60 fps. The rotation directions are intentionally opposite between layers so the surface creates a constantly shifting moiré.

Geometry resolution: `new THREE.SphereGeometry(layerConfig.scale, 80, 80)` — **80×80 segments**. Enough for smooth fresnel without burning GPU.

Materials: `THREE.ShaderMaterial`, `transparent: true`, `side: THREE.DoubleSide`, `blending: THREE.NormalBlending`, `depthWrite: false`. The disabled depth-write is critical — without it the three transparent layers z-fight.

Camera: `THREE.PerspectiveCamera(75, w/h, 0.1, 1000)`, positioned at `z: 5`. With three spheres of radii 1.00 / 0.85 / 0.70 that means the orb takes up roughly the middle 50% of the viewport vertically. Renderer: `setPixelRatio(Math.min(devicePixelRatio, 2))` — they cap DPR at 2 to keep retina sharp without 3× cost on high-DPI phones.

### 2.2 The vertex shader — Simplex-noise displacement plus sine waves

From `voiceorb/app.js` lines 145-248. The key block (lines 226-243):

```glsl
vec3 pos = position;

// Wave distortion - flowing patterns
float wave1 = sin(pos.y * 2.5 + time * 1.5 + layerOffset) * cos(pos.x * 2.0 - time * 1.2);
float wave2 = sin(pos.x * 3.0 - time * 1.8 + layerOffset) * cos(pos.z * 2.5 + time * 1.5);
float wave3 = sin(pos.z * 2.8 + time * 1.6 + layerOffset) * cos(pos.y * 2.3 - time * 1.3);

// Noise-based organic distortion
float noise1 = snoise(pos * 1.2 + time * 0.3 + layerOffset);
float noise2 = snoise(pos * 2.0 - time * 0.2 + layerOffset * 0.5);

// Combine distortions - reduced intensity
float distortion = (wave1 + wave2 + wave3) * 0.008;
distortion += (noise1 * 0.008 + noise2 * 0.007);

// Audio reactivity
distortion *= (0.3 + audioLevel * 0.6);

// Apply distortion along normal
pos = pos + normal * distortion;
```

**This is the formula for the wobble.** Three orthogonal sine waves at frequencies 2.0–3.0, plus two octaves of Simplex noise at frequencies 1.2 and 2.0, all at a base intensity of `0.007–0.008` (so the displacement is ~1% of the radius — it's a wobble, not a deformation). `audioLevel` scales the entire distortion: silence = 0.3× base distortion; full volume = 0.9× base distortion. The `layerOffset` (per-layer constant `index * 2.0`) makes the three layers wobble out-of-phase with each other.

Note `0.6 - dot(...)` is the standard Simplex noise falloff. The full Simplex noise function (Stefan Gustavson's port) is in lines 155-218 — copy it verbatim, you won't get a better implementation.

### 2.3 The fragment shader — fresnel + chromatic aberration + holographic rainbow

From the same file, lines 250-335. The recipe is:

1. Compute view direction in object space: `normalize(cameraPosition - vPosition)`.
2. **Fresnel:** `pow(1.0 - abs(dot(viewDirection, normalize(vNormal))), 2.0)`. Edges glow, center is matte.
3. **Chromatic aberration:** convert base color to HSV, shift the red channel hue by `+aberrationAmount * 0.15` and the blue channel by `-aberrationAmount * 0.15`, recombine. `aberrationAmount = chromaticAberration * fresnel` so the aberration is **edge-only**, which is what gives ChatGPT's orb the rainbow-fringe shimmer along the silhouette.
4. **Holographic rainbow:** generate a rainbow color from `vec3(rainbowShift, 0.8, 1.0)` in HSV where `rainbowShift = normal.x * 0.5 + normal.y * 0.2 + normal.z * 0.1 + sin(...)`, then mix it with the chromatic-aberrated base by `holographicIntensity = fresnel * 0.6 + 0.2`. Rainbow is mostly visible at edges.
5. **Position-based brightness wobble:** `1.0 + sin(pos.x * 3.0 + time) * 0.1 + sin(pos.y * 2.5 - time * 0.8) * 0.1`. ±10% brightness modulation that breathes.
6. **Shimmer:** `sin(pos.x * 8.0 + pos.y * 6.0 + time * 2.0) * 0.04 + 0.96` — high-frequency 4% modulation that gives the surface a "live" feel.

If you implement only one effect from this list, do the **fresnel + chromatic aberration**. That alone is what makes the orb look "alive" instead of "ball-shaped."

### 2.4 The pulsate logic — three modes for three states

```js
// LISTENING — react to mic amplitude
volumeScale = Math.min(1.0, audioLevel * 2.5);
if (volumeScale < 0.1) volumeScale = volumeScale * 2;  // quiet boost
targetScale = 1.0 + state.pulsateMin + (volumeScale * (state.pulsateMax - state.pulsateMin));

// THINKING — gentle sine breathing
const thinkingPulse = (Math.sin(time * 1.5) + 1.0) / 2.0;  // 0..1, period ~4.2s
targetScale = 1.0 + 0.0 + (thinkingPulse * 0.15);  // 1.00 .. 1.15

// SPEAKING — react to TTS audio amplitude
cadenceIntensity = getSpeakingAudioLevel();  // from playback AnalyserNode
targetScale = 1.0 + 0.05 + (cadenceIntensity * 0.17);  // 1.05 .. 1.22

// SMOOTHING — exponential approach
const smoothing = (isMicReactive ? 0.25 : 0.15);
currentScale += (targetScale - currentScale) * smoothing;
```

So your radius mapping is **linear in normalized amplitude** (not log, not sqrt), with a smoothing factor of 0.15 for synthesized states and 0.25 for live mic — that's a 6-frame and 4-frame lag respectively at 60fps, which keeps the orb from jittering on every phoneme but still feels reactive. This matches the "smooth interpolation for natural movement" comment.

Pulsate ranges in plain English: idle = 1.00 (no pulse). Listening = 1.02 to 1.25. Thinking = 1.00 to 1.15. Speaking = 1.05 to 1.22. **Maximum total scale ≈ 1.25**, so reserve at least 25% padding around the orb's bounding box.

### 2.7 Mic AnalyserNode setup (from the same `voiceorb/app.js`)

```js
analyser.fftSize = 512;             // smaller than OpenAI's console (8192)
analyser.smoothingTimeConstant = 0.3;  // also smaller than console's 0.85 default
audioLevel = sum / dataArray.length / 255;     // global average
audioFrequency = dataArray.slice(10, 40).reduce((a,b)=>a+b, 0) / 30 / 255;  // mid bins for vocal range
```

The clone uses `fftSize: 512` and `smoothingTimeConstant: 0.3` — much more responsive than your current Adjutant settings (`fftSize: 256, smoothingTimeConstant: 0.85`). For sphere visualization specifically, **use 512 and 0.3**. The 0.85 you currently have washes out all phoneme-level detail and makes the orb feel sluggish. Bins 10-40 (i.e. roughly 350 Hz – 1.4 kHz at 24 kHz sample rate) are the vocal formant band — that's the right slice to drive `audioFrequency`. Audio level is the global mean. Keep both.

The Medium voice-orb article (Dan Jackson) uses `fftSize: 1024` and a manual 0.15 smoothing-factor envelope follower in JS instead: `levelRef.current += (norm - levelRef.current) * 0.15`. With normalization `Math.min(1, Math.max(0, (avg - 16) / 90))` — the `16` is the noise floor in 0-255 space, `90` is the dynamic range to map to 1.0. This is an alternative that works equally well. Pick one approach (AnalyserNode smoothing OR manual envelope follower) — don't double-smooth.

### 2.8 ElevenLabs production orb — the WebGL2 fragment-shader approach

`/tmp/avm-research/elevenlabs-packages/packages/convai-widget-core/src/orb/Orb.ts` — they take a different path. Instead of three Three.js spheres with vertex distortion, they do **one full-screen quad** with a single fragment shader that draws **seven animated ovals in polar coordinates**, plus two noisy concentric rings, all run through a 4-color ramp (`black → uColor1 → uColor2 → white`). It's more performant than Three.js and is the better architecture if you want pixel-tight control.

Key numbers from `Orb.ts`:
- Canvas size capped at **512×512** regardless of CSS size: `canvas.width = Math.min(512, size.inlineSize)`. Above 512 they don't gain visual quality and they save GPU time. **Use 512×512 max.**
- WebGL2 context with `depth: false, stencil: false` (no depth buffer needed for a single full-screen quad).
- Default colors: `updateColors("#2792DC", "#9CE6E6")` — a teal blue / cyan pair.
- Volume → speed math: `targetSpeed = 0.2 + (1 - Math.pow(output - 1, 2)) * 1.8`. So at silence (output=0), speed is `0.2 + (1 - 1) * 1.8 = 0.2`; at full output (output=1), speed is `0.2 + 1 * 1.8 = 2.0`. **10× speed-up under load.**
- Speed only ratchets up immediately, never decays sharply: `if (this.targetSpeed > this.speed) this.speed = this.targetSpeed;` — so the orb gets fast on a loud syllable and stays fast briefly. Decay is implicit through the next-frame logic (smoother than a snap).
- Color is converted sRGB → linear with `Math.pow(c, 2.2)` before passing to the shader. **You must do this gamma-correction step or your colors will look washed out.**
- They use a 7-element `uOffsets` array of random values in `[0, 2π]` — these are the per-oval phase offsets that make the seven ovals breathe at different rates. Initialize once with `new Float32Array(7).map(() => Math.random() * Math.PI * 2)`.

The actual fragment shader (`OrbShader.frag`):
- Operates in polar coords: `vec2 uv = vUv * 2.0 - 1.0; float radius = length(uv); float theta = atan(uv.y, uv.x);`
- Seven ovals with centers at `0, 0.5π, 1.0π, 1.5π, 2.0π, 2.5π, 3.0π` (mapped around the polar circle), each animated by `0.5 * sin(uTime / 20.0 + uOffsets[i])` — 20-second base period, but with random phase per oval so the overall motion has no obvious cycle.
- Each oval's size is sampled from a Perlin noise texture (loaded from `https://storage.googleapis.com/eleven-public-cdn/images/perlin-noise.png`): `a = noise * 1.5; b = noise * 4.5;` — tall narrow ovals.
- Two concentric noisy rings (`sharpRing` and `smoothRing`) blended with screen-mode.
- Final 4-color ramp: `{ black, uColor1, uColor2, white }` — gives the orb an interior gradient with light highlights and dark shadows.

This produces a totally different visual aesthetic — flatter, more "iridescent gradient sphere" than Three.js's "wobbly orb." ChatGPT's mobile app looks closer to the Three.js version. ElevenLabs' widget looks closer to this. Both are valid.

## 3. ChatGPT-specific design choices (from public teardowns)

Confirmed from PCMag, TechCrunch, 9to5Mac, AI Forward Marketer, and learnprompting.org coverage:

- **Background:** full-bleed near-black. No gradient. The orb itself provides all the color. Some screenshots show a very faint radial vignette behind the orb but it's barely visible.
- **Orb position:** vertically centered, slightly above the optical center (about 40-45% from top). Status text sits ~24px below.
- **Bottom bar:** four circular buttons in a horizontal row, evenly spaced. From left to right on the iOS app: **video** (camera icon, off by default) → **screen-share** (rectangle-with-arrow icon) → **mute** (mic icon, toggles slash when muted) → **end call** (red circle with white "X" or telephone-down icon). Web version is just **mute** and **end**.
- Button shape: circular, ~56-64px diameter, semi-translucent dark fill (`rgba(255,255,255,0.08)` over the black bg), 1px subtle border, white icon at 24px.
- **Mute state:** orb desaturates to a low-opacity grey-blue, scale freezes at 1.0, status changes to muted indicator.
- **Idle → active opening transition:** the orb materializes via fade-in (~400ms) plus scale from 0.6 to 1.0 (cubic-out). Status text fades in afterward. 9to5Mac specifically describes it as "morphs into a fluid sky-like blue and white animation" when entering voice mode.
- **End-of-turn behavior:** when `response.done` fires, orb snaps back to idle color over ~300ms. Scale stays where it was and decays via the same exponential-smoothing loop.
- **Interruption (barge-in):** the orb instantly snaps from speaking-pink back to listening-blue. Audio cuts off mid-syllable. There is no separate "interrupt" animation — the state-change visualization IS the feedback.
- **"Thinking" before audio:** there's almost no visible "thinking" gap because the Realtime API typically delivers the first `response.audio.delta` within 200-500ms of `response.created`. So in practice you see listening-blue → very brief thinking-violet (200ms) → speaking-pink. Some implementations skip the thinking state entirely and just go listening → speaking, and that feels fine.
- **Recent integrated mode** (TechCrunch / 9to5 reporting): OpenAI also offers a non-orb "in-chat" voice mode where the orb becomes a small inline indicator instead of a full-screen takeover. For a operator console like Adjutant, the takeover orb is the right pattern.

## 5. Recommended Adjutant implementation

Given your `<canvas id="voice-orb" width="320" height="320">`, your existing WebSocket events (`USER_DONE / TRANSCRIPT / BOT_SPEAKING_START / BOT_SPEAKING_END`), and your amber/black/mono operator-console aesthetic:

### State mapping (your events → orb states)
| Your event             | Triggers state | Color             |
|------------------------|----------------|-------------------|
| WebSocket connected, idle | `idle`       | `#1A0F00` ring on `#000` (dim amber) |
| Mic open, no speech    | `listening`    | `#FFB000` (amber) |
| `USER_DONE` received   | `thinking`     | `#FF6A00` (deep orange) |
| `BOT_SPEAKING_START`   | `speaking`     | `#FFD24A` (bright wheat-amber) |
| `BOT_SPEAKING_END`     | back to `listening` (mic stays hot) | |
| User speaks while bot speaking | `listening` (interruption) | snap-shrink to 0.95 over 120ms |

### Numbers to use
- **Canvas:** 320×320 (your current size is right for an operator panel; or scale to 480×480 if you have room)
- **DPR cap:** `Math.min(devicePixelRatio, 2)` 
- **Geometry:** 3 spheres at radii `1.00 / 0.85 / 0.70`, each `SphereGeometry(r, 80, 80)`
- **Camera:** PerspectiveCamera 75°, `z=5`
- **AnalyserNode (mic + bot output, separate):** `fftSize: 512, smoothingTimeConstant: 0.3` — *upgrade from your current 256/0.85*
- **Mid-band slice:** bins 10-40 for vocal energy
- **Smoothing:** `currentScale += (target - currentScale) * 0.25` for live audio, `* 0.15` for synthesized breathing
- **Pulse ranges:** idle 1.00 only; listening 1.02-1.25; thinking 1.00-1.15 with `sin(t * 1.5)` breath; speaking 1.05-1.22
- **State color crossfade:** instant hex swap (the noise masks it); add 300ms `easeInOutCubic` lerp if you want polish
- **Material:** `THREE.ShaderMaterial`, `transparent: true, side: DoubleSide, depthWrite: false, blending: NormalBlending`
- **Vertex shader:** Simplex-noise + 3 sine waves per displacement formula in section 2.2, with `audioLevel * 0.6` scaling
- **Fragment shader:** fresnel `pow(1.0 - dot(view, normal), 2.0)` + chromatic aberration `±0.15 * fresnel * chromaticAberration` + edge-only holographic rainbow + 4% shimmer + ±10% position breathing
- **Background:** keep your near-black; add `radial-gradient(circle at 50% 45%, rgba(255,176,0,0.06) 0%, transparent 60%)` behind the canvas to suggest a soft amber halo

### Bottom bar (matches your existing markup)
Your current `start / mute / fallback push-to-talk` already maps cleanly. The ChatGPT-equivalent layout would be:

```
[ MUTE ]   [ END ]      ← centered, two buttons, ~64px circular each
```

Your existing `cbtn cbtn--primary` and `cbtn cbtn--ghost` classes should work — just round them to 50% border-radius and stack vertically in the canvas-takeover layout.

### Status text
Pin **24px below the orb**. 14px mono (matches your `mono telemetry chrome`). Strings:
- `idle` → `STANDBY` 
- `listening` → `LISTENING`
- `thinking` → `PROCESSING…`
- `speaking` → `RESPONDING`
- `muted` → `MUTED`
- on interruption → flash `INTERRUPTED` for 600ms then back to `LISTENING`

500ms debounce on label changes, 200ms ease-out crossfade with 8px translate-up entry — exactly matches ElevenLabs' `StatusLabel.tsx`.

### Opening transition (when user clicks start)
Orb materializes: fade in (opacity 0→1 over 400ms), scale up (0.6→1.0 over 400ms cubic-out), color from grey to listening-amber. Status text fades in 200ms after orb starts.

### Closing transition (end button)
