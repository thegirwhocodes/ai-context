## Locking, replay and concurrency

The safe lock order is:

```text
acceptance run row
→ source rows in UUID order
→ iMessage transition/finalize locks
→ canonical 025 reset
```

This gives the required behavior:

- Concurrent resets serialize on the run row; the loser observes `reset_at` and returns `0`.
- A lost-response retry is idempotent.
- Seed writes and reset serialize through the same run-row lock.
- A live ingestion claim either finishes before reset obtains the source lock, or becomes stale after the source is fenced.
- If a committed `processing` batch exists, finalization must fail and roll back the entire reset. The compatibility function must not set the delete GUC directly or bypass the processing-claim check.
- The accepted `set_config(..., true)` fence values remain transaction-local. [Row-lock behavior](https://www.postgresql.org/docs/current/explicit-locking.html), [trigger transaction behavior](https://www.postgresql.org/docs/current/trigger-definition.html)
