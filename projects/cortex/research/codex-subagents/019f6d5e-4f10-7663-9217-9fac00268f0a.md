## Code-owned release blockers

1. **Critical: OAuth account-linking CSRF.**
   The HMAC-signed state contains `userId`, provider, redirect URI and nonce, but the nonce is neither persisted nor consumed, and the state is not bound to the initiating browser/session: [google-oauth-state.ts](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/lib/integrations/google-oauth-state.ts:17). Both public callbacks trust `state.userId` without authenticating the current Cortex session: [Gmail callback](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/app/api/integrations/gmail/callback/route.ts:8), [Calendar callback](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/app/api/integrations/calendar/callback/route.ts:8).

   An attacker can create a legitimate state for their Cortex account, give that authorization URL to another Google user, and link the victim’s Google account to the attacker’s Cortex account. Production must require a matching authenticated Cortex session, bind state to that session/browser, store and consume a one-time nonce, reject replay, and test mismatched/missing sessions.

2. **OAuth disclosure is insufficient immediately before consent.**
   Connect buttons give only short descriptions such as “Read and draft in your voice”: [integrations UI](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/app/(dashboard)/integrations/page.tsx:94), [onboarding](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/app/onboarding/page.tsx:316). They do not disclose the specific Gmail/Calendar data accessed, storage, third-party processing, personal-model use, or write actions immediately before redirecting to Google.

   Google currently requires an in-product disclosure immediately before consent explaining accessed data and how it is used/shared. A privacy policy alone is insufficient. [Google Workspace API User Data Policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy?hl=en)

3. **Calendar scope minimization is unresolved.**
   Current scopes are `calendar.readonly` plus `calendar.events`: [google-calendar.ts](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/lib/integrations/google-calendar.ts:20). The code uses `calendar.readonly` for calendar-list and free/busy operations, but Google offers narrower endpoint scopes:

   - `calendar.calendarlist.readonly`
   - `calendar.freebusy`
   - Retain `calendar.events` for event reads and approved writes

   See the official [CalendarList scope options](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list) and [Freebusy scope options](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query). Do not submit the existing broad Calendar scope set without resolving and documenting this.

4. **Verification documentation and runtime readiness are materially out of sync.**

   - [.env.example](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/.env.example:47) labels shared credentials “Gmail OAuth,” provides only the Gmail callback fallback, and omits `GOOGLE_OAUTH_STATE_SECRET`.
   - [readiness.ts](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/lib/config/readiness.ts:17) checks variable presence, not canonical production origins, exact redirect registrations, scope configuration, publishing status or verification.
   - [google-oauth-verification.md](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/docs/google-oauth-verification.md:112) does not make the restricted-scope/CASA obligation explicit.

   - Existing state tests cover signatures, expiry and provider mismatch, but not session binding or replay: [google-oauth-state.test.ts](/Users/naomiivie/cortex/.worktrees/cortex-integration-held/tests/google-oauth-state.test.ts:13).
