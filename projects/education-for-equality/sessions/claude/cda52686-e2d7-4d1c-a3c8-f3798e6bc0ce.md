## ADR-001: Confirm the Cortex Reference Architecture

**Status:** Accepted (confirming existing build)
**Date:** 2026-06-27
**Deciders:** Naomi

### Context

You asked whether we're building Cortex with the right architecture. The platform now spans two deployed apps ([cortex-web-one.vercel.app](https://cortex-web-one.vercel.app) and [voice-email-app.vercel.app](https://voice-email-app.vercel.app)), 50+ API routes, 7 migrations, a full LoRA training pipeline, billing, developer API, and GDPR-clean delete — built over March → June 2026 with you + Claude + a Codex agent collaborating.

### Decision

**Keep the current architecture.** The Anthropic-native + Next.js + Supabase + per-user LoRA stack is the correct path. Don't refactor to a framework (LangGraph/CrewAI/Mastra) and don't collapse the two apps into one yet.

### What's correct (and why)

| Layer | Built as | Why it's right |
|---|---|---|
| **Auth + multi-tenant** | Clerk + Supabase RLS, AES-256 encrypted OAuth tokens | Cheapest path to per-user isolation; RLS gives you GDPR per-row deletes for free |
| **Ingestion** | OAuth → fetch → chunk → embed (`all-MiniLM-L6-v2`, 384-dim) → pgvector | 384-dim is the right size — fits IVFFlat, cheap to embed on CPU, plenty for personal corpus |
| **RAG** | `match_cortex_documents` RPC, recency-weighted, source-filterable | Standard pgvector pattern, scales to 100K+ docs/user before you'd need a dedicated vector DB |
| **User Profile** | Sonnet 4.6 over sent+received emails → `cortex_profiles.profile_text` | Right model for one-shot deep analysis, cached as a stable system-prompt prefix on every later call |
| **Memory** | `cortex_memory` (categorized, priority-ranked) + `cortex_open_loops` + `assistant-memory.ts` cross-session | More sophisticated than Anthropic's `memory_20250818` tool — keep it |
| **Personal LoRA** | Qwen3-4B + QLoRA r=8/α=16 + RunPod training + LoRAX serving + monthly retrain cron | Matches [PERSONAL_LLM_RESEARCH.md](/Users/naomiivie/cortex/PERSONAL_LLM_RESEARCH.md) recommendations exactly; cost is $0.22–1.44/user; adapter is ~16-20 MB; LoRAX serves thousands per GPU |

### 4 Real Concerns — Worth Acting On

**1. 🟡 The LoRA pipeline was built but never validated end-to-end.**
You have ~15 sent emails. The eval harness gates at 100, the March research says 500 minimum and 2,000–5,000 recommended. So the personal-model layer — the *single biggest architectural bet* — has never actually run a forward pass on a deployed adapter. The pipeline being green-on-paper isn't the same as green-on-real-tokens. **Recommendation:** do a "dry-run" training on the 15 examples just to validate the loop (RunPod payload shape, adapter upload to S3, webhook callback, LoRAX deployment, router preference). Quality will overfit hard and be bad — that's fine; the point is to prove infrastructure end-to-end, not to use the adapter.

**2. 🟡 The query complexity classifier is regex-based — directly violates your own rule.**
[lib/lora/router.ts:91-118](/Users/naomiivie/cortex/cortex-web/lib/lora/router.ts#L91) classifies queries as simple/medium/complex with hardcoded regex patterns (`/draft.*(?:email|reply|message)/`, `/analyze|compare|explain/`, etc). Your standing rule from session efd7d7d2: *"DON'T JUST WRITE AN ALGORITHM AROUND THIS!!!"* This is exactly the kind of thing that should be a 50-token Haiku call ("rate this query 1-5 on style-vs-reasoning"). It's cheap, it's correct in spirit, and it'll route better. Small but it's the *symbolic* bit — if the brain has an algorithm at its decision boundary, you're already drifting.

**3. 🔴 The roots layer is much thinner than the March vision.**
Original Layer 1: Gmail, Calendar, Instagram, GroupMe, WhatsApp, iMessage, Notes, Plaid. Today live: Gmail + Calendar (both broken — see below). GroupMe has an import endpoint but no UI flow. WhatsApp/iMessage/Instagram/Apple Notes are local-file-export-then-import only. Plaid is unbuilt. **The personal model and auto-spheres and "what do I have today?" all underperform because the brain only sees one channel.** This isn't an architecture bug, it's a feature backlog — but it's worth naming because the *quality of every downstream layer is bottlenecked by ingestion breadth.*

**4. 🟡 Production deploy is partially fake — two compounding gaps.**
- Clerk is on a `pk_test_` dev instance (`premium-gelding-57.accounts.dev`). Real users see that ugly URL on every sign-in.
- `GOOGLE_REDIRECT_URI` in Vercel still points to `localhost:3000` — production Gmail OAuth literally cannot complete. Combined with Google's Testing-mode 7-day refresh-token expiry, this is why Gmail sync froze at 2026-03-18 and the assistant keeps talking about March.
- `CLERK_WEBHOOK_SECRET`, RunPod, LoRAX, S3, Stripe envs all missing in production — readiness returns 503.

Architecturally fine. Operationally it means the live app can't onboard a real second user. Run `audit:production` in [DEPLOYMENT_RUNBOOK.md §11](/Users/naomiivie/cortex/DEPLOYMENT_RUNBOOK.md).

### 2 Places Cortex Has Drifted From the Original Vision

Both flagged in [MARCH_ORIGINAL_LORA_PLAN_GAP_REVIEW.md](/Users/naomiivie/cortex/research/MARCH_ORIGINAL_LORA_PLAN_GAP_REVIEW.md), worth restating:

- **"Local-first / on-device" became "cloud-first."** March vision had MLX-on-Mac fine-tuning ("data never leaves the device"). Current build is Hetzner/RunPod cloud + Supabase. That's a reasonable tradeoff for a one-person team, but you owe yourself a decision: do we ever bring it on-device, or have we accepted cloud-first permanently? It affects the privacy pitch and the iPhone-app story.
- **Voice was meant to be core Cortex, not a separate app.** The split into Sage Mail is good engineering hygiene (fast iteration, clean seam), but the cortex-web shell has no voice surface at all right now. The "Cortex talks to you" promise from the raw transcription notes is only delivered in one corner. Decide whether Sage Mail eventually folds back in or whether they stay as two products — that affects what you market.
