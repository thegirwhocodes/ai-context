## Findings

### 1. How Africa's Talking authenticates its webhooks — authoritative facts

AT's behavior is fundamentally different from Twilio. Per AT's own help center:

- **No HMAC request signing.** AT does **not** sign outbound webhook/callback POSTs. Their official guidance ("How can I ensure the POST request to my callback URL is coming from Africa's Talking?") says only: *"We only allow access to a POST request with the correct username and API key combination"* — i.e. that refers to **your** requests **to AT**, not AT's requests to you. There is **no signature header to verify** on inbound callbacks. (The `X-AT-Signature` / HMAC-SHA256 story that surfaces in web-search summaries is a hallucination — it is generic webhook-security boilerplate pulled from unrelated vendors' docs, not from any AT page. The actual AT article explicitly does not mention signatures or secret tokens.)
  - Source: https://help.africastalking.com/en/articles/5947646-how-can-ensure-that-the-post-request-to-my-callback-url-is-coming-from-africa-s-talking-and-not-some-other-place

- **No published webhook source-IP allowlist.** AT does not publish a stable, documented set of egress IPs for its HTTP callback servers. The only IP-whitelisting AT documents is for **SIP trunks**, and there it is **your PBX's IP** that you give to AT — not AT's IP given to you. So an IP allowlist for the HTTP webhook is not officially supported and would be guesswork that risks blocking real traffic.
  - Sources: https://help.africastalking.com/en/articles/6049012-what-do-i-need-to-set-up-a-sip-trunk-connection (SIP trunk: "You share your trunk's (PBX) IP address for whitelisting"); https://help.africastalking.com/en/articles/2206161-how-do-i-configure-my-callback-url (callback config — no IP/token/security details at all).

- **The callback URL itself is effectively the only shared secret AT gives you.** You set the voice callback URL in the AT dashboard (Voice → Phone Numbers → Actions → Callback URL). AT does not require any fixed URL shape, so you can put an unguessable token in it.

**Conclusion:** The only verification mechanism that is (a) under your control, (b) documented-compatible, and (c) zero risk of false-rejecting real AT calls is a **secret token baked into the callback URL** you register in the AT dashboard. An IP allowlist is unsafe (AT publishes no list). Signature verification is impossible (AT doesn't sign).

### 3. Recommended approach — fail-open secret-token gate (SAFEST high-value option)

A shared secret token in the callback URL, checked in middleware, **fail-open (log/flag, do not block) for the pilot**. This is the only option with effectively zero false-rejection risk, because the token is something *you* put in the AT dashboard URL — every real AT call will carry it by construction, and you control it.

- Store `AT_WEBHOOK_TOKEN` (a long random string) in env.
- Register callback URLs in the AT dashboard with `?at_token=<token>` appended (and the in-code `NEXT_PUBLIC_APP_URL`-derived `callbackUrl`s also get it).
- Middleware checks for the token on `/api/sabi/at/*` and `/api/sabi/sms/incoming`. **During the pilot it only logs a warning + Sentry flag on mismatch — it does NOT reject.** Flip a single env flag (`AT_WEBHOOK_ENFORCE=1`) to switch to hard 403 once you've confirmed from logs that 100% of real traffic carries the token.

**Risk rating for false-rejection of real AT calls: essentially zero while fail-open (it never rejects); LOW even after enforcement is enabled** — the only way a real call gets rejected is if you forget to add the token to a dashboard callback URL, which the fail-open logging phase is designed to catch first.

This deliberately avoids: IP allowlists (HIGH false-reject risk — no published list), and aggressive rate limiting as the primary gate (MEDIUM risk — a classroom with shared phones could legitimately burst).

### Exact edits

**New helper file** — `/Users/naomiivie/Education for Equality/curriculum-app/lib/voice/at-auth.ts`:

```ts
import * as Sentry from "@sentry/nextjs";
import type { NextRequest } from "next/server";

/**
 * Africa's Talking does NOT sign its webhook POSTs (no HMAC / no signature
 * header) and does NOT publish a stable set of source IPs for HTTP callbacks.
 * Their own guidance is that the callback URL is effectively the shared secret.
 * So we gate on a secret token carried in the callback URL query string
 * (?at_token=...), which we register in the AT dashboard.
 *
 * Pilot posture: FAIL-OPEN. We log + flag mismatches but do not block, so a
 * misconfigured dashboard URL can never reject a real child's call. Set
 * AT_WEBHOOK_ENFORCE=1 to switch to hard rejection once logs confirm every
 * real call carries the token.
 */
export function verifyATWebhook(req: NextRequest): {
  ok: boolean;
  enforce: boolean;
} {
  const expected = process.env.AT_WEBHOOK_TOKEN;
  const enforce = process.env.AT_WEBHOOK_ENFORCE === "1";

  // No token configured → nothing to check (don't break existing setups).
  if (!expected) return { ok: true, enforce: false };

  const provided =
    req.nextUrl.searchParams.get("at_token") ||
    req.headers.get("x-at-token") ||
    "";

  const ok = provided.length > 0 && timingSafeEqual(provided, expected);

  if (!ok) {
    console.warn(
      `[AT auth] webhook token ${provided ? "mismatch" : "missing"} on ${req.nextUrl.pathname} (enforce=${enforce})`
    );
    Sentry.captureMessage("AT webhook token failure", {
      level: enforce ? "error" : "warning",
      tags: {
        "at.auth": provided ? "mismatch" : "missing",
        "at.path": req.nextUrl.pathname,
        "at.enforce": String(enforce),
      },
    });
  }

  return { ok, enforce };
}

// Constant-time string compare (avoids importing node:crypto into edge mw).
function timingSafeEqual(a: string, b: string): boolean {
  if (a.length !== b.length) return false;
  let mismatch = 0;
  for (let i = 0; i < a.length; i++) {
    mismatch |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return mismatch === 0;
}
```
