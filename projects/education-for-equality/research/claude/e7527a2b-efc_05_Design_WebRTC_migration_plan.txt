## Implementation Plan: MJPEG to WebRTC Migration via aiortc

### Architecture Overview

The migration replaces the two MJPEG HTTP streaming routes (`/video/signing`, `/video/speaking`) with WebRTC peer connections negotiated over the existing SocketIO transport. Everything else stays identical: camera threads, frame buffers, ASL detection loop, speech listener, all SocketIO events.

The core challenge is that aiortc is asyncio-based while Flask+SocketIO runs in threaded mode. The solution is a dedicated asyncio event loop running in its own daemon thread, with thread-safe bridges to the existing frame buffers.

**(a) AsyncIO event loop in a background thread:**

```python
import asyncio
from aiortc import RTCPeerConnection, RTCSessionDescription, RTCIceCandidate
from aiortc.contrib.media import MediaStreamTrack
from av import VideoFrame

# Dedicated asyncio loop for aiortc
_rtc_loop = asyncio.new_event_loop()
_peer_connections = set()  # Track for cleanup

def _run_rtc_loop():
    asyncio.set_event_loop(_rtc_loop)
    _rtc_loop.run_forever()

threading.Thread(target=_run_rtc_loop, daemon=True).start()
```

This loop runs forever in a daemon thread. All aiortc operations are scheduled onto it using `asyncio.run_coroutine_threadsafe(_rtc_loop, coro)`.

**(b) Custom VideoStreamTrack classes:**

These subclass `MediaStreamTrack` and override `recv()` to return frames from the existing thread-safe buffers. Each call to `recv()` must return an `av.VideoFrame` with correct timestamps.

```python
class SigningVideoTrack(MediaStreamTrack):
    kind = "video"

    def __init__(self):
        super().__init__()
        self._start = time.time()
        self._frame_count = 0

    async def recv(self):
        # Pace at ~30fps
        self._frame_count += 1
        target_time = self._start + self._frame_count / 30
        wait = target_time - time.time()
        if wait > 0:
            await asyncio.sleep(wait)

        # Read from existing buffer (thread-safe via lock)
        with _signing_lock:
            frame = latest_annotated_frame if latest_annotated_frame is not None else latest_raw_frame

        if frame is None:
            # Black frame fallback
            frame = np.zeros((480, 640, 3), dtype=np.uint8)

        # Convert BGR (OpenCV) -> RGB -> av.VideoFrame
        rgb = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)
        video_frame = VideoFrame.from_ndarray(rgb, format="rgb24")
        video_frame.pts = self._frame_count
        video_frame.time_base = fractions.Fraction(1, 30)
        return video_frame
```

An identical `SpeakingVideoTrack` class reads from `latest_speaking_frame` (with `_speaking_lock`). In single-camera mode, it falls back to `latest_raw_frame` just like the current `_speaking_camera_thread` does.

**(c) SocketIO signaling handlers:**

Three new SocketIO events handle the WebRTC negotiation:

```python
@socketio.on('webrtc_offer')
def handle_offer(data):
    """Client sends SDP offer, server creates answer with video tracks."""
    feed = data.get('feed')  # 'signing' or 'speaking'
    sdp = data['sdp']

    async def _create_answer():
        pc = RTCPeerConnection()
        _peer_connections.add(pc)

        @pc.on("connectionstatechange")
        async def on_state():
            if pc.connectionState in ("failed", "closed"):
                _peer_connections.discard(pc)

        # Add the appropriate video track
        if feed == 'signing':
            pc.addTrack(SigningVideoTrack())
        else:
            pc.addTrack(SpeakingVideoTrack())

        offer = RTCSessionDescription(sdp=sdp['sdp'], type=sdp['type'])
        await pc.setRemoteDescription(offer)
        answer = await pc.createAnswer()
        await pc.setLocalDescription(answer)

        return {
            'sdp': pc.localDescription.sdp,
            'type': pc.localDescription.type,
        }

    future = asyncio.run_coroutine_threadsafe(_create_answer(), _rtc_loop)
    answer = future.result(timeout=10)  # Block Flask thread until done
    emit('webrtc_answer', {'feed': feed, 'sdp': answer})


@socketio.on('webrtc_ice')
def handle_ice(data):
    """Client sends ICE candidate."""
    # With aiortc, ICE candidates are typically bundled in the SDP.
    # This handler exists for trickle ICE if needed.
    pass


@socketio.on('disconnect')
def on_disconnect_cleanup():
    # Peer connections are cleaned up via connectionstatechange callbacks
    pass
```

Key design decision: The `future.result(timeout=10)` call blocks the Flask SocketIO handler thread until the asyncio coroutine completes. This is safe because SocketIO with `async_mode='threading'` allocates a thread per event, and WebRTC negotiation takes milliseconds. The alternative (callback-based) would be more complex for no benefit.

Add a `connectWebRTC(feed, videoElementId)` function:

```javascript
function connectWebRTC(feed, videoElementId) {
    const pc = new RTCPeerConnection({
        iceServers: [{ urls: 'stun:stun.l.google.com:19302' }]
    });

    pc.ontrack = (event) => {
        const el = document.getElementById(videoElementId);
        if (el) el.srcObject = event.streams[0];
    };

    // We only receive video, but must add a transceiver to get it
    pc.addTransceiver('video', { direction: 'recvonly' });

    pc.createOffer().then(offer => {
        return pc.setLocalDescription(offer);
    }).then(() => {
        // Wait for ICE gathering to complete (simplifies exchange)
        return new Promise(resolve => {
            if (pc.iceGatheringState === 'complete') {
                resolve();
            } else {
                pc.onicegatheringStatechange = () => {
                    if (pc.iceGatheringState === 'complete') resolve();
                };
            }
        });
    }).then(() => {
        socket.emit('webrtc_offer', {
            feed: feed,
            sdp: {
                sdp: pc.localDescription.sdp,
                type: pc.localDescription.type,
            }
        });
    });

    socket.on('webrtc_answer', (data) => {
        if (data.feed === feed) {
            pc.setRemoteDescription(new RTCSessionDescription(data.sdp));
        }
    });

    return pc;
}
```

Key design decisions in this JS:
- **Wait for ICE gathering to complete before sending the offer.** This avoids trickle ICE, which simplifies the signaling to a single offer/answer exchange. aiortc also gathers all candidates before responding.
- **`addTransceiver('video', { direction: 'recvonly' })`** tells the browser we want to receive video but not send any. This is critical -- without it, the offer won't include a video media section.
- **`autoplay playsinline muted`** on the video elements ensures the browser plays the stream without user interaction (Chrome requires `muted` for autoplay).

The current tab switching code (lines 752-758) does nothing special for video. With WebRTC, streams continue flowing even when the tab panel is hidden via `display: none` -- this is one of the key advantages over MJPEG.

### Potential Issues and Mitigations

1. **VP8 encoding CPU load.** aiortc encodes VP8 in software. At 640x480@30fps, this uses roughly 15-25% of one core per stream. With 4 peer connections, that is up to 4 encode threads. Mitigation: reduce resolution or framerate for additional connections, or share a single encode and fan out (requires custom relay track, not worth the complexity for a demo).

2. **`fractions.Fraction` import.** The `time_base` on `av.VideoFrame` must be a `fractions.Fraction`, not a float. Missing this causes a runtime error.

3. **Color space.** OpenCV frames are BGR. `av.VideoFrame.from_ndarray` with `format="rgb24"` expects RGB. The `cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)` conversion is mandatory.

4. **ICE gathering timeout.** The JS waits for ICE gathering to complete before sending the offer. On some networks, this can take several seconds. The 10-second timeout in `future.result(timeout=10)` on the server side accommodates this.

5. **Multiple `webrtc_answer` listeners.** Each call to `connectWebRTC` adds a new `socket.on('webrtc_answer')` listener. Since each checks `data.feed === feed`, this works, but with 4 connections for 2 feeds, both signing connections will both try to process the same answer. Fix: use a unique connection ID (e.g., `data.conn_id`) in the signaling messages. Add a `conn_id = str(uuid4())` on the client, pass it in the offer, and echo it back in the answer. Then filter on `conn_id` instead of `feed`.

6. **macOS camera permissions.** No change from current -- the app already accesses cameras via OpenCV.

7. **Localhost operation.** WebRTC to localhost works out of the box. aiortc generates host ICE candidates (127.0.0.1), and the browser accepts them. No STUN needed for this case, but including STUN is harmless and enables LAN/remote access.
