## Claude · 2026-03-30T22:22:34.324Z

Based on [SABI_SECURITY.md](7.%20Legal%20&%20IP/SABI_SECURITY.md), here's the layered defense — a hacker would have to break through **every single layer**, not just one:

### Layer 1: They can't get in
- **SSH is key-only** — no password to guess or brute-force. They'd need to physically steal the private key from your laptop (`~/.ssh/id_ed25519`)
- **fail2ban** — already caught 70+ brute-force attempts and banned 8 IPs. 5 failed attempts = auto-banned
- **Only 3 ports open** (22, 80, 443) — Docker containers (port 8000, 11434) are bound to `127.0.0.1`, invisible from the internet

### Layer 2: They can't see anything useful in transit
- **All traffic is TLS 1.2/1.3 encrypted** (Let's Encrypt) — no plaintext to intercept
- HTTP auto-redirects to HTTPS

### Layer 3: They can't call the API
- **API key required** on every AI endpoint (`/stt`, `/tts`, `/llm`, `/process-turn`)
- **Rate limiting** — even if they somehow got the key, 30 req/min cap on expensive endpoints
- **AT webhook verification** — voice endpoints only accept requests from Africa's Talking's known IP ranges, forged webhook calls get 403'd

### Layer 4: Even if they got on the server, they can't find secrets
- **Docker secrets on tmpfs** — API keys live at `/run/secrets/` inside the container (in-memory filesystem, never written to disk)
- Secret files are `chmod 600` (root-only readable)
- Keys never appear in `docker inspect`, process listings, or environment variables

### Layer 5: They can't get meaningful user data anyway
- **Supabase Row Level Security (RLS)** — database queries are access-controlled per-row
- Server uses a **service role key** (stored only on server, never exposed to clients)
- Students are identified by **phone number, not personal names** — no PII like real names stored
- **No call recordings** — audio is processed in real-time for STT, then temporary files auto-clean after 24 hours
- Each caller can only access their own session — no way to query another student's data through the voice API

### The bottom line

It's not one lock — it's **10 locks in sequence**. To steal user data, an attacker would need to:

1. Get your SSH private key (steal your laptop)
2. Bypass fail2ban
3. Break TLS encryption
4. Guess the API key
5. Bypass rate limiting
6. Find Docker secrets in tmpfs memory
7. Get the Supabase service role key
8. Bypass Row Level Security
9. And even then, all they'd get is phone numbers — no names, no recordings

**One known gap to still fix:** The Vercel `/api/sabi/*` routes are unprotected (no auth, no rate limit) — that's a credit-burn risk, not a data theft risk, but it's still open from session `ff1faa52`.

### Implementation — How will you ensure consistent student engagement and overcome potential barriers to regular usage?

Three mechanisms. First, **Sabi calls the child, not the other way around.** Our flash-callback model means the child beeps (₦0 cost), and Sabi calls back within seconds.
