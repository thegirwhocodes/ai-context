## Claude · 2026-08-05T17:00:41.434Z

"That" = why Apple's model, even though it's fast and good, can't just plug into Sabi. Here's the explanation:

**"On-device, no cloud API" means there's no endpoint to call.** Groq, Gemini, Google Chirp — you send them an audio file over the internet and they send text back. Apple's `SpeechTranscriber` doesn't work that way. It only runs *inside* Apple's Swift frameworks, on an Apple-Silicon chip, on a device running iOS 26 / macOS 26. Apple never exposes it as a network service. So there is literally no URL Sabi's server could POST a clip to.

**Sabi's brain lives on a Linux box (Hetzner).** The call audio lands there, and there it calls an STT. Apple's model can't be installed on Linux and can't be reached over the network — so from where Sabi actually runs, it's unreachable. Full stop.

**The only way to use it live** would be to run a **Mac as a dedicated "STT node":** a little Swift service on an always-on Apple-Silicon Mac that takes a clip → runs SpeechTranscriber → returns text, with Hetzner shipping every turn's audio to that Mac and back. Why that's not worth it:
- It's *another* always-on machine — a Mac mini or cloud Mac costs money, and your own laptop can't be the production phone line. That fights the exact thing you're trying to do (stop paying for a box).
- Extra network hop = more latency, on the one thing that's already latency-critical.
- Apple tuned it for **clean, close-mic dictation** (memos, meetings) — not noisy 8kHz Nigerian-kid telephony, which is the hard case where even Whisper/Google fall apart. No reason to expect it wins there.

**Where it *is* genuinely useful to you — and fits "no server":** run it **on your Mac, offline, to label call clips for free.** Drop the recorded "couldn't-hear" wavs into it, get transcripts, hand-correct them → that's your fine-tune/eval dataset, built at zero cost with no server running.
