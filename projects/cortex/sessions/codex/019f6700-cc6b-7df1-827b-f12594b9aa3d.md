### How synchronization should work

1. `SessionStart` pulls the private repository and injects a small `RECOVERY.md`.
2. `UserPromptSubmit` exports the exact current transcript using `session_id` and `transcript_path`.
3. `PostCompact` points directly to that session’s exported file—not whichever session is newest.
4. `Stop` requests a background synchronization.
5. A locked launchd job batches commits every 15–30 minutes, rebases, and retries push conflicts.
6. A local redactor and secret scanner must pass before anything is staged.
7. GitHub Actions provides a second check for secrets, oversized files, broken indexes, and invalid structure.

## Codex · 2026-07-16T17:30:02.289Z · final_answer

These are the kinds of data that stay out of GitHub:

- **Raw transcripts:** The original `.jsonl` session files used internally by Codex and Claude. They contain much more than the visible conversation, including metadata and system events.
- **Reasoning:** Private model working data used to produce an answer. This is different from explanations intentionally shown in the conversation.
- **Tool payloads:** Commands sent to tools and their complete results—for example terminal output, file contents, database results, and API responses. These can be enormous or contain sensitive information.
- **Attachments:** Images, documents, audio, and other files attached to a conversation. The recovery archive may note that an attachment existed, but it does not upload the underlying file.
- **Credentials:** Passwords, API keys, access tokens, cookies, private keys, `.env` values, and similar authentication information.

GitHub receives a much smaller, human-readable record containing the visible user messages, visible assistant answers, task identifiers, timestamps, and project association—with sensitive patterns redacted.

The raw local files remain on your laptop because Codex and Claude need them for the sidebar and native resume functionality. They are excluded from GitHub for privacy, security, and storage efficiency.

## Codex · 2026-07-16T17:31:13.441Z · final_answer

Agent and subagent work is handled in layers:

- **Main agent conversation:** The visible user messages and assistant responses are saved as redacted recovery records.
- **Subagent final reports:** The result handed back to the main agent is saved. This preserves conclusions, findings, and recommendations.
- **Subagent scratch work:** Internal reasoning, every intermediate step, raw searches, command output, and full tool responses are not uploaded.
- **Code and documents produced:** These belong in the relevant project’s GitHub repository—not the `ai-context` repository.
- **Durable research or decisions:** Important findings can be saved as curated memory/research files in `ai-context`, including their originating session ID.

So GitHub preserves **what an agent accomplished and handed off**, but not its entire private working trace. If a subagent discovers something important but neither reports it nor writes it into a project or curated research file, that intermediate information may not be recoverable.
