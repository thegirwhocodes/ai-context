## Codex · 2026-07-02T19:01:07.948Z · final_answer

That caveat is not really a broken-job problem. It’s expected RunPod behavior.

RunPod’s docs say async `/run` results are only available from `/status` for **30 minutes after completion**; `/runsync` results are even shorter-lived, **1 minute, 5 minutes max**. So a job from **June 30, 2026** returning `404 job not found` on **July 2, 2026** is normal. Source: [RunPod send API requests docs](https://docs.runpod.io/serverless/endpoints/send-requests).

The fix is: **don’t use RunPod `/status` as historical proof. Persist the terminal job result ourselves.**

For Cortex, the right durable proof is already mostly in Supabase:

- `training_job_id`
- `status`
- `adapter_file_path`
- `adapter_file_size_bytes`
- `training_started_at`
- `training_completed_at`
- `deployed_at`
- `error_message`

To make this airtight for future runs, I’d add one small improvement: store the full terminal RunPod/webhook summary in the adapter row or a `cortex_lora_training_events` table when `/api/lora/webhook` fires. For example:

```ts
runpod_status: "COMPLETED",
runpod_output: {
  adapter_path,
  adapter_size_bytes,
  cost_usd,
}
```

Then the board caveat becomes:

> RunPod `/status` expired as expected after 30 minutes; durable proof is Supabase terminal webhook row + R2 object HEAD + live serving smoke.

For the existing v5 job, there’s nothing to “recover” from RunPod’s `/status` API now. The clean fix is to update the board wording from “caveat” to “expected retention behavior,” because we already have the stronger proof: DB deployed row, R2 object exists, and RunPod inference serves adapter v5.
