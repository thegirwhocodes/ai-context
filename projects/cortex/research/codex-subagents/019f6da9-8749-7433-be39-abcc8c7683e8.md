# Codex subagent report: Hilbert

Merge-blocker: **YES**. No P0s; five concrete P1s.

## Findings

1. **[P1] Authenticated RLS can bypass WhatsApp lifecycle and registration CAS.**
   The account policy permits `FOR ALL` operations on user-owned rows ([014_whatsapp_core.sql:560](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/014_whatsapp_core.sql:560)); integrations have the same policy ([001_initial_schema.sql:349](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/001_initial_schema.sql:349)). Migration 023 restricts RPC execution but never revokes authenticated table writes ([023_whatsapp_phone_registration.sql:237](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:237)).

   **Scenario:** Under normal Supabase authenticated grants, a user directly changes their revoked integration to `active` and its retained account to `lifecycle_active=true`, `connected`, `registered`, and `subscribed`. The action adapter trusts exactly those fields and decrypts the retained token ([whatsapp-action-adapter.ts:153](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-action-adapter.ts:153)), defeating disconnect and provider-confirmed registration. Direct generation edits can also invalidate the new CAS guarantee.

   **Minimal fix:** Revoke account/integration writes from `anon` and `authenticated`; expose only read-safe columns and route lifecycle mutations through service-only RPCs. Add database enforcement for control columns.

2. **[P1] Both webhook paths acknowledge in-flight work as a completed duplicate, causing permanent event loss after a crash.**
   Instagram returns `NULL` for active leases and completed claims alike ([015_messaging_roots.sql:576](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/015_messaging_roots.sql:576)); callers count either as a duplicate ([process-events.ts:57](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/instagram/process-events.ts:57)) and return 200 ([route.ts:199](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/webhooks/meta/instagram/route.ts:199)). WhatsApp similarly retries only `failed`; existing `processing` is a duplicate ([whatsapp-webhook.ts:201](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-webhook.ts:201)) and receives 200 ([route.ts:61](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/webhooks/meta/whatsapp/route.ts:61)).

   **Scenario:** A worker claims an event and dies before releasing/completing it. The provider retries while the claim is still `processing`; Cortex acknowledges that retry. The lease later expires with no delivery left to reclaim it.

   **Minimal fix:** Return distinct `acquired`, `busy`, `completed`, and `reconciliation` dispositions. ACK only durable completion; enqueue durable lease recovery or return a retryable HTTP response for `busy`. WhatsApp also needs tokenized CAS lease ownership/expiry.

3. **[P1] In-flight WhatsApp webhook finalizers can rewrite disconnected tombstones and block reassignment globally.**
   Account lookup does not capture lifecycle generation ([whatsapp-webhook.ts:139](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-webhook.ts:139)); completion/failure updates use only account ID and user ID ([whatsapp-webhook.ts:409](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-webhook.ts:409)). Disconnect first sets `lifecycle_active=false` and `connection_state=disconnected` ([023_whatsapp_phone_registration.sql:207](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:207)), while global phone uniqueness is based on `connection_state`, not `lifecycle_active` ([014_whatsapp_core.sql:376](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/014_whatsapp_core.sql:376)).

   **Scenario:** A webhook resolves an active account; disconnect fences it; the webhook then sets the tombstone back to `connected` or `degraded`. It remains lifecycle-inactive but globally reserves the phone number, preventing a legitimate tenant claim.

   **Minimal fix:** Carry lifecycle generation through processing and CAS all account/integration finalizers on generation, `lifecycle_active=true`, and active integration status. Base active-phone uniqueness on the lifecycle invariant and repair inconsistent tombstones.

4. **[P1] An approved WhatsApp send can cross the disconnect fence.**
   The adapter loads/decrypts an active target and later performs the provider call without a lifecycle-generation lease ([whatsapp-action-adapter.ts:80](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-action-adapter.ts:80), [whatsapp-action-adapter.ts:166](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-action-adapter.ts:166)). Proposals do not seal a generation ([whatsapp-action-producer.ts:45](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-action-producer.ts:45)). Disconnect does not coordinate with action execution ([disconnect/route.ts:39](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/integrations/whatsapp/disconnect/route.ts:39)).

   **Scenario:** Execution loads the token, then disconnect completes, then execution resumes and calls `/messages`. WABA unsubscribe does not revoke the token’s send permission.

   **Minimal fix:** Seal lifecycle generation into proposals and acquire a per-account execution lease/lock immediately around provider calls. Disconnect must take the same lock and invalidate or await outstanding sends before returning.

5. **[P1] WABA-wide subscription ownership is neither serialized nor durably reconciled.**
   Subscribe performs a WABA-wide POST before local finalization ([subscribe/route.ts:172](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/integrations/whatsapp/subscribe/route.ts:172)). Disconnect separately checks for active siblings and then performs a WABA-wide DELETE ([disconnect/route.ts:59](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/integrations/whatsapp/disconnect/route.ts:59)); compensation repeats that TOCTOU pattern ([subscribe/route.ts:258](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/integrations/whatsapp/subscribe/route.ts:258)). DELETE failures are recorded locally but not queued, and disconnect still returns success ([disconnect/route.ts:68](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/integrations/whatsapp/disconnect/route.ts:68)).

   **Scenarios:** Tenant B subscribes another phone on the same WABA after tenant A’s sibling check but before A’s DELETE; A removes B’s webhook subscription after B becomes locally connected. Separately, a transient DELETE failure leaves the WABA subscribed indefinitely; another disconnect attempt returns 404 because the account is already lifecycle-inactive.

   **Minimal fix:** Maintain a durable WABA-level desired-subscription generation/refcount and serialize all POST/DELETE decisions under a database lock. Persist cleanup jobs with retry/backoff and audited operator recovery; reconcile or re-subscribe if ownership changes around DELETE.
