## Why your peers can paste and you can't

TDM Studio's Workbench is a **browser-based Jupyter** running on a ProQuest VM. Pasting into it depends entirely on your **browser's Clipboard API permission** for `tdmstudio.proquest.com` — there is no TDM-specific paste setting. If your peers can paste and you can't, the difference is almost certainly one of these:

1. **You're using Safari, they're using Chrome.** Safari's Clipboard API is the most restrictive on Mac — it only permits paste during a "direct user gesture" and silently blocks programmatic paste calls Jupyter sometimes makes. Chrome 66+ and Edge 79+ have full async Clipboard API support; Safari does not. ([Apple Community thread](https://discussions.apple.com/thread/256201902))
2. **Site clipboard permission is set to Deny/Ask in your browser.** Chrome and Safari both store this per-site, and once denied it stays denied silently.
3. **macOS Screen Recording / Accessibility permission** for your browser is off. macOS Sequoia/Sonoma started gating clipboard reads behind these for some browser builds.
4. **A clipboard manager is intercepting** (Maccy, Paste, Raycast, Alfred clipboard history, Magnet, etc.) — these are a known cause of paste failures into web-Jupyter, especially on Mac. ([Maccy clipboard sync issue](https://github.com/p0deje/Maccy/issues/948))
5. **Jupyter's Mac Cmd→Ctrl key remap quirk.** Long-standing Jupyter bug: in some versions, Cmd+V into a code cell registers as plain "v". ([jupyter/notebook #4138](https://github.com/jupyter/notebook/issues/4138))

## Workarounds, ranked by what to try first

**1. Switch to Chrome (or Edge) — this fixes 80% of cases.**
Open `tdmstudio.proquest.com` in Chrome. If paste works there, it was Safari's Clipboard API. Done.

**2. Grant the site clipboard permission explicitly.**
- Chrome: click the lock icon in the URL bar → **Site settings** → set **Clipboard** to **Allow** → reload.
- Safari: Safari → Settings → **Websites** tab → **Clipboard** in the sidebar → set `tdmstudio.proquest.com` to **Allow** → reload. ([Apple support](https://discussions.apple.com/thread/254282820))

**3. Quit any clipboard manager** (Maccy, Paste, Raycast clipboard, Alfred clipboard history) and retry. If that fixes it, whitelist `tdmstudio.proquest.com` in the manager's settings.

**4. Use the Jupyter Edit-menu Paste instead of Cmd+V.**
In the JupyterLab toolbar: **Edit → Paste** (or right-click in the cell → **Paste**). This goes through a different code path than the Cmd+V keyboard shortcut and often works when the shortcut doesn't.

**5. Bypass paste entirely — upload the file.**
This is the cleanest workaround and what I'd recommend long-term:
- Save your code to a `.py` or `.ipynb` file locally.
- In TDM Studio's JupyterLab file browser, click the **Upload** arrow icon → pick the file.
- Then either `%load yourfile.py` in a cell, or just open the `.ipynb` directly.
This is also ProQuest's officially recommended workflow precisely because pasting into the browser editor is flaky. ([Using the Jupyter Notebook](https://proquest.libguides.com/tdmstudio/jupyternotebook))

**6. Use `%load` from a URL.**
Push a snippet to a GitHub gist, then in a TDM cell: `%load https://gist.githubusercontent.com/.../raw/file.py`. No clipboard needed.

**7. Last resort: paste into a terminal first.**
In TDM JupyterLab, open **File → New → Terminal** and `cat > snippet.py` then Cmd+V (terminals use a different paste handler) → Ctrl+D → then `%load snippet.py` in your notebook.

## What to check right now to confirm the cause

In TDM Studio, open your browser's DevTools console (Cmd+Opt+I in Chrome, Cmd+Opt+C in Safari after enabling the Develop menu) and try Cmd+V. If you see a red error like `NotAllowedError: Read permission denied` or `Document is not focused`, it's #1/#2. If nothing appears, it's #3, #4, or #5.

Given you're already editing notebooks here in VS Code, **#5 (upload the .ipynb)** is the workaround that actually scales — you skip the paste problem entirely and stay in the upload-and-run flow we set up last turn.

Cold Turkey blocking "Amazon" matches those — that's why your peers can paste (no Cold Turkey block) and you can't.

**2. Under "Exceptions" (or "Whitelist") add these domains:**

```
tdmstudio.proquest.com
*.proquest.com
*.amazonaws.com
*.awsapps.com
*.cloudfront.net
```

If your block is in **Locked** mode and won't let you edit:

- **Option A — Wait it out.** A locked block can't be edited until the timer expires. Check the lock countdown.

## TL;DR — copying out of TDM Studio is the same Clipboard-API problem in reverse, with extra Jupyter quirks layered on

The "paste **into** TDM" issue was browser permission to **read** your local clipboard. Copying **out** of TDM is the browser's permission to **write** to your clipboard — same API, but JupyterLab also has long-standing bugs that swallow selections inside cells. Atlas already solved the read side; the write side mostly just works in Atlas too, but there are three known traps that cost time. Here's the actual playbook.

## Five reliable ways to copy out, ranked

### 1. Code cell → just select with mouse + Cmd+C
- Click into the cell first (cursor visible).
- Click-drag to select the lines you want.
- **Cmd+C** → switch back here → Cmd+V.
- This works in Atlas. If it ever doesn't, fall back to **Edit menu → Copy** in JupyterLab's top bar instead of the keyboard shortcut. ([JupyterLab #12315](https://github.com/jupyterlab/jupyterlab/issues/12315))

### 2. Cell **output** (printed text, dataframes) → right-click → "Copy Output to Clipboard"
- Right-click on the output area below a cell → **Copy Output to Clipboard**.
- This grabs the entire output as plain text. Works for `print()`, `df.head()`, anything textual.
- Caveat: it's the *whole* output, not a selection. If you need a piece, use method 1 or 3.

### 3. The bulletproof method — write to a file, then open the file
For anything longer than a screenful, or anything you'd otherwise lose to selection bugs:

```python
text = "...whatever you want to copy..."
with open("clip.txt", "w") as f:
    f.write(text)
```

Then in the JupyterLab file browser (left sidebar) **double-click `clip.txt`** to open it in a tab → Cmd+A → Cmd+C. The text editor view has zero selection bugs. **This is what I'd use for anything important** — it never fails.

For dataframes:
```python
df.to_csv("clip.csv", index=False)
```
Open the CSV → select all → copy.

### 4. Whole notebook or whole file → use Download
- Right-click any file in the JupyterLab file browser → **Download**.
- The `.ipynb` lands in your Mac's Downloads folder. Open it in VS Code here. Full content, no clipboard needed.
- **This is the workflow I'd use for editing notebooks** — download → edit in VS Code → upload back. You already have `package_nigeria_outputs.ipynb` doing the bulk version of this.

### 5. The `%%javascript` clipboard trick (last resort)
If the cell's output is awkward to select:
```python
text = "your text here"
import IPython, json
IPython.display.display(IPython.display.Javascript(
    f'navigator.clipboard.writeText({json.dumps(text)})'
))
```
Run that cell. Atlas will (usually silently) copy it to your Mac clipboard. If it prompts for permission, click Allow. Works in Atlas; fails in some Chrome configs.

## Three traps that waste time

1. **Selecting across multiple cells doesn't work** — Jupyter only lets you copy from one cell at a time via mouse selection. Use method 3 (write to file) for multi-cell grabs. ([JupyterLab #2155](https://github.com/jupyterlab/jupyterlab/issues/2155))

2. **The "copy" button on cell outputs sometimes copies nothing** — silent failure, no error. If Cmd+V here gives you stale clipboard contents, it didn't actually copy. Verify by checking what's on your clipboard before pasting. Fall back to method 3. ([JupyterLab #17411](https://github.com/jupyterlab/jupyterlab/issues/17411))

3. **Plots / images don't copy as images via right-click** in any browser reliably — right-click → **Save image as** → drag the saved PNG into VS Code or wherever you need it. Or use:
   ```python
   plt.savefig("plot.png")
   ```
   then download the file.

## What I'd set up right now

Add this helper to the top of your TDM notebooks so anytime you want to copy something out, it's two lines:

```python
def clip(x):
    """Write anything to clip.txt in the current dir, then open clip.txt in JupyterLab to copy."""
    from pathlib import Path
    Path("clip.txt").write_text(str(x))
    print("→ open clip.txt in the file browser, Cmd+A, Cmd+C")
```

Then `clip(df.to_string())` or `clip(my_long_string)` whenever you need to get something out. Beats fighting the selection bug every time.

## A — Topic Modeling

**The intuition:** Right now we *told* the LLM what 8 risk factors to look for (Government Stability, Inflation, etc.). That's like walking into a library with a checklist and only counting books that match. Topic modeling is the opposite — it walks into the library, reads everything, and tells you *back* what the books are about.

**How it works (high level):**
- Every article is treated as a "bag of words" (or a sentence-embedding vector, depending on the technique)
- The algorithm finds clusters of words/articles that hang together — "this group of articles all talk about *fuel subsidies, naira, inflation, IMF*; this other group talks about *Boko Haram, kidnap, military, Borno*."
- Each cluster is a **topic**. Each topic gets ranked keywords (so you can name it: "FX & subsidy crisis", "Northeast insurgency", etc.)
- Each article gets a topic distribution ("70% topic 3, 30% topic 7").

**Two flavors:**
- **LDA** (Latent Dirichlet Allocation) — classic, older, slower, less coherent topics. Course-canonical.
- **BERTopic** — uses modern sentence embeddings (BERT), gives much cleaner topics. Faster, prettier.

We'd use BERTopic. ~10 min runtime on 391 articles.

**What this proves:**
- *Do our pre-specified ICRG factors actually match what Nigerian news talks about?* (Maybe topic modeling surfaces something like "Diaspora remittances" that we never coded for.)
- *Which topics dominate which quarters?* — we get a chart of topic share over time. Beautiful narrative companion to the risk index.

**The output:** one topic-over-time stacked area chart + a CSV with topic labels + top words.

**The intuition:** We've shown the Risk Index *correlates* with FDI (slide 11). But correlation says "when one moves, the other moves." It doesn't say "knowing the Risk Index helps you forecast FDI." Those are different. The final test is: **does our news-derived number contain real information about future FDI flows that wasn't already in vanilla macro data?**

1. **Baseline model:** Predict Nigeria's FDI from lagged GDP growth + lagged FDI itself. This is what an economist would do *without* news data. Get an R² (a "how much variance did we explain" score, 0 to 1, higher is better).
