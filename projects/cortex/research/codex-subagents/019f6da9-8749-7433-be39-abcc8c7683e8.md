# Codex subagent report: Hilbert

Merge-blocker: **YES**. No P0s; five concrete P1s.

## Findings

1. **[P1] An expired subscribe lease permits a later DELETE while the original POST may still complete.**
   Expired subscribe operations are treated as safely retryable and the global fence is cleared ([023_whatsapp_phone_registration.sql:761](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:761)). A late completion whose old job is no longer `processing` simply returns `stale` without forcing reconciliation ([023_whatsapp_phone_registration.sql:925](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:925)).

   **Scenario:** A subscribe POST remains provider-in-flight past two minutes. All owners disconnect, the expired lease is cleared, and a new DELETE completes. The delayed POST then completes last, leaving Meta subscribed while Cortex records `unsubscribed`.

   The inverse stale-DELETE path can also become unrecoverable: it marks the old-generation job as reconciliation-required ([023_whatsapp_phone_registration.sql:741](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:741)), but recovery only accepts a job matching the current desired generation ([023_whatsapp_phone_registration.sql:1138](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:1138)).

   **Minimal fix:** Treat every expired provider-call lease as ambiguous when the desired operation changed. Probe/reconcile actual provider state before allowing the opposite operation, and let recovery resolve the stale job by immutable job ID while queuing the current generation.

2. **[P1] WABA desired state is not maintained for every account mutation or deletion.**
   Connect directly upserts `waba_id` and `lifecycle_active=true`, then separately invokes lifecycle activation/refresh ([whatsapp-account.ts:212](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-account.ts:212), [whatsapp-account.ts:245](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-account.ts:245)). No account trigger maintains the WABA ledger. GDPR deletion removes integrations ([020_relationship_manager.sql:1065](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/020_relationship_manager.sql:1065)), cascading account deletion through [014_whatsapp_core.sql:363](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/014_whatsapp_core.sql:363), without refreshing WABA state.

   **Scenario:** A process crashes after making an account lifecycle-active but before refresh, leaving desired state falsely unsubscribed. More critically, deleting a user removes the account and encrypted token while the WABA ledger can remain subscribed; Meta continues delivering data with no credential left for cleanup.

   **Minimal fix:** Make account creation, WABA changes, activation, and deletion atomically refresh both old and new WABA rows through database triggers/RPCs. User deletion must retain a service-owned cleanup tombstone and encrypted cleanup credential until remote unsubscribe is confirmed.

3. **[P1] Durable WABA retry jobs have no consumer.**
   Migration 023 creates and backfills ready jobs ([023_whatsapp_phone_registration.sql:242](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:242), [023_whatsapp_phone_registration.sql:345](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:345)), but the only non-test claim path is the request-synchronous helper ([whatsapp-subscription.ts:33](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-subscription.ts:33)). No worker or cron consumes due jobs or invokes WABA recovery.

   **Scenario:** A transient disconnect DELETE failure returns 503 and stores `retryable`; if the user does not repeat the POST, it remains forever. Backfilled cleanup jobs for old disconnected rows are never attempted at all.

   **Minimal fix:** Add an authenticated scheduled worker that leases due jobs, obtains an explicitly authorized WABA credential, probes/reconciles provider state, and applies bounded retry/backoff. Add audited operator handling for reconciliation-required jobs.

4. **[P1] A confirmed WhatsApp send followed by execution-settlement failure is recorded as terminal failure.**
   After Meta returns a message ID, the adapter settles the account execution lease before returning the receipt ([whatsapp-action-adapter.ts:167](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-action-adapter.ts:167)). Settlement failure throws `ACTION_PROVIDER_AMBIGUOUS` ([whatsapp-action-adapter.ts:401](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-action-adapter.ts:401)), but the shared engine recognizes only timeout and missing-receipt codes as ambiguous and otherwise stores a terminal failure ([engine.ts:267](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/actions/engine.ts:267)).

   **Scenario:** Meta accepts the message, then the lease-finalization RPC experiences a database failure. Action history says terminally failed instead of reconciliation-required, creating a false outcome and duplicate-send risk during manual recovery.

   **Minimal fix:** Classify `ACTION_PROVIDER_AMBIGUOUS` through `persistAmbiguousOutcome`. Persist the returned provider message ID before—or atomically with—settling the execution lease.

5. **[P1] A crashed send can permanently prevent user disconnect.**
   An expired execution lease is changed to `reconciliation_required`, and disconnect returns without fencing ([023_whatsapp_phone_registration.sql:623](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:623)); the route returns 409 for every such attempt ([disconnect/route.ts:52](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/app/api/integrations/whatsapp/disconnect/route.ts:52)). Recovery exists only as a service-role RPC ([023_whatsapp_phone_registration.sql:1312](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/supabase/migrations/023_whatsapp_phone_registration.sql:1312)) and has no application/operator caller. Reconnect also rejects non-idle execution state ([whatsapp-account.ts:119](/Users/naomiivie/cortex/.worktrees/cortex-meta-imessage-redo/lib/integrations/whatsapp-account.ts:119)).

   **Scenario:** The process dies after the provider call but before settlement. After lease expiry, the user can neither disconnect nor reconnect; the integration remains active and webhook subscription remains desired indefinitely without direct database intervention.

   **Minimal fix:** Provide an audited authorized recovery path. Local lifecycle fencing and remote-cleanup queuing must remain available even while the individual action outcome stays quarantined for reconciliation.
