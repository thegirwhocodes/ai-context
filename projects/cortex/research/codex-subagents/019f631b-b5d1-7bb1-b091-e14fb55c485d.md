## Proven P0 findings

### P0 — Remaining tenant-bare FKs

Migration 020 at `55fe49b` correctly repairs person references using:

```sql
ADD CONSTRAINT ... FOREIGN KEY (...) ... NOT VALID;
-- quarantine and repair invalid references
VALIDATE CONSTRAINT ...;
```

It does not repair these legacy single-column FKs:

```sql
cortex_events.source_account_id
  REFERENCES cortex_integrations(id)

cortex_events.source_document_id
  REFERENCES cortex_documents(id)

cortex_commitments.source_event_id
  REFERENCES cortex_events(id)

cortex_commitments.source_document_id
  REFERENCES cortex_documents(id)
```

These permit a tenant-A row to reference a tenant-B object UUID. RLS on the child row does not enforce ownership of the referenced row.

Required replacements:

```sql
FOREIGN KEY (source_account_id, user_id)
  REFERENCES cortex_integrations(id, user_id)
  ON DELETE SET NULL (source_account_id) NOT VALID;

FOREIGN KEY (source_document_id, user_id)
  REFERENCES cortex_documents(id, user_id)
  ON DELETE CASCADE NOT VALID;

FOREIGN KEY (source_event_id, user_id)
  REFERENCES cortex_events(id, user_id)
  ON DELETE SET NULL (source_event_id) NOT VALID;

FOREIGN KEY (source_document_id, user_id)
  REFERENCES cortex_documents(id, user_id)
  ON DELETE SET NULL (source_document_id) NOT VALID;
```

Before validation: quarantine each mismatch, null or delete according to the intended ownership semantics, then validate. The old single-column constraints must be removed.

Baseline `cortex_messages.conversation_id` is also tenant-bare despite 014 creating `(id,user_id)` uniqueness for conversations.
