# Codex subagent report: /root/parallel_stt_research

## Research conclusion

The smoothest safe implementation is:

1. Keep Gemini Live responsible for the continuous conversation, VAD, barge-in, and turn boundaries.
2. On numeric-answer turns only, send the exact same learner-audio segment concurrently to:
   - Groq `whisper-large-v3`
   - a preloaded local `faster-whisper` model
3. Grade automatically only when the two engines extract the same unambiguous numeric value.
4. If they disagree, time out, or detect multiple values, ask the learner to repeat just the number. Do not allow one engine to overrule the other during the first rollout.
5. Run this in shadow mode first on Naomi’s number, then enable it for grading after measuring real Nigerian PSTN audio.

The repository already contains most of this consensus engine in [stt.py](/Users/naomiivie/Education%20for%20Equality/sabi-server/stt.py). Its regression passes, including concurrent start, numeric-value agreement, timeout handling, audit data, Gemini tie-break, and fail-closed behavior:

```text
PASS Groq and local Whisper start together
PASS consensus returns without waiting for Gemini
PASS same number overrides different object nouns
PASS consensus is authoritative
PASS both transcripts remain auditable
PASS Gemini resolves disagreement
PASS slow local vote is time-bounded
PASS unresolved disagreement fails closed
PASS parallel STT consensus regression
```

However, the new Gemini Live route does not use this engine. [gemini_live.py](/Users/naomiivie/Education%20for%20Equality/sabi-server/gemini_live.py) sends 8 kHz audio directly to Gemini and never imports or calls `SpeechToText`. Therefore the current good-sounding Twilio/Gemini Live call is not running Groq and local Whisper side by side.

## What should change in the existing implementation

The existing consensus code is a strong scaffold, but five details need correction before connecting it to live grading.

### 1. Attach it to Gemini Live without replacing Gemini’s VAD

Gemini currently receives caller audio continuously and uses:

- low start-of-speech sensitivity;
- low end-of-speech sensitivity;
- 160 ms prefix padding;
- 650 ms silence;
- `START_OF_ACTIVITY_INTERRUPTS`;
- `TURN_INCLUDES_ONLY_ACTIVITY`.

That behavior is why random sounds no longer cause interruptions. The new STT sidecar must not control barge-in or conversation turns.

For shadow evaluation, copy the learner PCM at `_finalize_turn()` and transcribe it asynchronously.

For live numeric grading, intercept `grade_numeric_answer` in `_handle_tool_call()`:

1. Lock and snapshot the current `input_pcm`.
2. Run a local VAD over the snapshot and select the most recent complete speech segment.
3. Add approximately 160–200 ms of padding at each edge.
4. Resample once from 8 kHz to 16 kHz mono.
5. Give the exact same resulting bytes to Groq and local Whisper.
6. Return the numeric consensus to the deterministic grader.

Asterisk’s `AudioSocket()` application normally supplies signed-linear 16-bit, 8 kHz mono PCM. Upsampling to 16 kHz satisfies Whisper but cannot recreate frequencies already lost on the telephone path. [Asterisk AudioSocket application](https://docs.asterisk.org/Latest_API/API_Documentation/Dialplan_Applications/AudioSocket/), [protocol definition](https://docs.asterisk.org/Configuration/Channel-Drivers/AudioSocket/).

### 2. Remove question text from numeric STT prompts

The current Groq request passes the recent tutor question into Whisper’s prompt. That can bias the transcription toward operands already present in the question. For example, “Three books have four pages each” injects “three” and “four” into the recognizer immediately before the child says the answer.

For graded numeric turns:

- Do not provide the expected answer.
- Do not provide the full problem or its operands.
- Prefer no prompt, or a fixed generic prompt such as “A Nigerian learner is saying a short answer. Transcribe literally.”
- Do not list every number in the prompt unless tests prove it improves precision without hallucinating numbers from noise.

The local implementation already suppresses its full prompt on numeric turns, but the Groq implementation does not.

### 3. Replace fabricated confidence scores

Current code assigns:

- Groq nonempty transcript: `0.82`
- Groq/local agreement: at least `0.95`

Those are labels, not measured probabilities.

Groq’s current `verbose_json` response does provide segment-level `avg_logprob`, `no_speech_prob`, and `compression_ratio`; the code comment saying it does not is outdated. Groq also supports word and segment timestamps. [Groq Speech-to-Text documentation](https://console.groq.com/docs/speech-to-text).

Local faster-whisper exposes:

- segment `avg_logprob`;
- `no_speech_prob`;
- compression ratio;
- word probabilities when word timestamps are enabled;
- Silero VAD information.

Confidence should be calibrated on labeled Sabi calls using a logistic or isotonic model. Inputs can include:

- both extracted numbers;
- engine agreement;
- minimum/mean log probability;
- maximum no-speech probability;
- word probability for the number token;
- VAD speech duration;
- clipping and approximate SNR;
- transcript length;
- presence of multiple distinct numbers;
- model latency or timeout;
- carrier/codec if available.

Calibration must use held-out speakers and phones. Measure probability that the extracted numeric value is correct, not generic WER. Initially target accepted-answer precision of at least 98%, letting the system abstain and ask for repetition when uncertain.

### 4. Shorten the deadline

The current consensus deadline is five seconds. That is far too long for a natural tutoring response.

Recommended starting limits:

- soft target: 800 ms after speech endpoint;
- hard consensus deadline: 1.2–1.5 seconds;
- late results may be logged but must never be applied to the next turn;
- a 429 or provider failure should fall back immediately, not sleep and retry while the child waits.

Each request must carry `call_uuid`, `turn_id`, and an audio hash. Discard any response whose turn is no longer current.

### 5. Do not let Gemini choose unilaterally after Whisper disagreement

The current code starts a separate Gemini transcription and lets it decide when Groq and local Whisper disagree. For the strict behavior Naomi requested—“if they both say the same thing, the agent defers to that”—the first production rule should be:

- Groq numeric value = local numeric value → eligible to grade.
- Anything else → repeat prompt.

A later calibrated policy could accept two-of-three agreement between Groq, local STT, and the already-running Gemini Live transcript. A separate Gemini transcription API call is unnecessary because Gemini Live already heard the audio.

Also, cancelling a running Python future does not normally stop its in-flight HTTP request. The current eager third request can still consume quota after Groq/local agree.

## Concurrency and audio architecture

Use one canonical per-turn audio object:

```text
Asterisk AudioSocket 8 kHz PCM
            │
            ├── Gemini Live continuous stream
            │     owns VAD, conversation and barge-in
            │
            └── ring buffer tagged by call + turn
                       │
                numeric tool call
                       │
            latest VAD speech segment
                       │
               resample once to 16 kHz
                ┌──────┴────────┐
                │               │
          Groq Whisper     local recognizer
                │               │
                └──── candidate normalizer
                          │
                 exact numeric agreement
                          │
             deterministic answer grader
```

Use a persistent `httpx.AsyncClient` or Groq SDK client so TLS connections are reused. The current `httpx.post()` creates avoidable connection overhead.

The local model must be loaded and warmed once at service startup. Do not instantiate it per turn. The current `_local_inference_lock` prevents unsafe simultaneous access but serializes every call across all learners. A production setup should use:

- a dedicated local-STT worker or service;
- bounded queue and semaphore;
- one controlled GPU worker initially;
- optional 20–50 ms microbatching if concurrency grows;
- explicit queue timeout;
- GPU memory and latency metrics.

The current three-thread global executor can become congested because local inference is serialized behind its lock while Groq/Gemini requests occupy the remaining workers.

## Numeric agreement rules

The current design correctly treats “two apples” and “two fries” as the same numeric answer. It should be tightened as follows:

1. Apply numeric extraction only when the curriculum item explicitly expects a number.
2. Parse complete compound values such as “twenty four” and “one hundred and two.”
3. Return a candidate only if the utterance contains one distinct numeric value.
4. If the child says “I thought three, but it is two,” do not select the first number; mark it ambiguous or select the final answer only after that rule has been validated.
5. Treat teen/tens conflicts—13/30, 14/40, 15/50—as high-risk disagreements requiring repetition.
6. Restrict Nigerian and telephone homophone mappings to short numeric-answer turns.
7. Never infer correctness from object nouns. If the answer is “two,” “two mangoes,” “two fries,” and “two apples” are all semantically equivalent unless the lesson is specifically testing units.
8. If no engine finds a number, do not convert ordinary sounds into a number.
9. Keep the deterministic correct answer outside both ASR prompts.

For nonnumeric conversation, exact transcript agreement is too strict and semantic similarity is unsafe for grading. Parallel STT should initially govern numeracy only. Literacy phonemes and isolated letter sounds require a separate evaluation protocol.

## Groq: current limits, costs, and suitability

Groq documents file/URL transcription and translation endpoints, not a supported streaming STT WebSocket. Therefore the smooth approach is per-turn batch transcription after Gemini identifies a learner utterance, not overlapping rolling windows. [Groq Speech-to-Text](https://console.groq.com/docs/speech-to-text).

Current models:

| Model | Current price | Vendor speed factor | Vendor WER | Recommendation |
|---|---:|---:|---:|---|
| `whisper-large-v3` | $0.111/audio hour | 189x in STT docs | 10.3% | Use first for grading accuracy |
| `whisper-large-v3-turbo` | $0.04/audio hour | 216x | 12% | Test later if numeric accuracy is equivalent |

Groq explicitly recommends large-v3 for error-sensitive multilingual use. These WER figures are general vendor figures, not Nigerian children over PSTN.

Other current details:

- Minimum accepted clip: 0.01 seconds.
- Minimum billed clip: 10 seconds.
- Free-tier upload: up to 25 MB.
- Developer tier: up to 100 MB.
- Groq internally down-samples to 16 kHz mono.
- WAV is recommended for lower latency; FLAC for smaller lossless uploads.
- Prompt limit: 224 tokens.
- Temperature defaults to zero.
- Word and segment timestamps are supported.
- It is a file request, so finalization of the learner turn must happen before sending.

At the 10-second minimum:

- large-v3 costs about $0.000308 per learner turn;
- turbo costs about $0.000111 per learner turn;
- 20-question lesson: approximately $0.00617 large-v3 or $0.00222 turbo;
- 30-question lesson: approximately $0.00925 large-v3 or $0.00333 turbo.

The current free plan limits are organization-wide:

- 20 requests/minute;
- 2,000 requests/day;
- 7,200 audio seconds/hour;
- 28,800 audio seconds/day.

At 20 numeric turns per lesson, request count alone permits roughly 100 such lessons/day on the base free plan. Multiple simultaneous learners can also hit the 20 RPM limit. Exact account limits should be read from the Groq console and response headers. [Groq rate limits](https://console.groq.com/docs/rate-limits), [Groq pricing](https://groq.com/pricing).

Groq says inference inputs/outputs are not retained by default, although it may temporarily log them for reliability or abuse investigation for up to 30 days. All customers can enable Zero Data Retention; retained customer data is stored in US GCP buckets. Usage metadata is always retained but excludes input/output content. Groq says it does not train on inputs or outputs without explicit permission. [Groq data controls](https://console.groq.com/docs/your-data), [services agreement](https://console.groq.com/docs/legal/services-agreement).

Because the learners are children, enable ZDR, minimize raw audio retention, use pseudonymous IDs, document consent, encrypt stored clips, and set a deletion period.

## Local faster-whisper and hardware

`faster-whisper` is the easiest local companion because it is already implemented. It uses CTranslate2, supports FP16 and INT8, word timestamps, and Silero VAD. Its maintainers report up to four times the speed of OpenAI Whisper at the same accuracy, with lower memory, but those are reference benchmarks rather than Sabi phone benchmarks. [faster-whisper repository](https://github.com/SYSTRAN/faster-whisper).

Published reference benchmarks for 13 minutes of audio:

- RTX 3070 Ti, large-v2 FP16: 63 seconds, 4,525 MB VRAM.
- Same model batch size 8: 17 seconds, 6,090 MB.
- INT8 GPU: 59 seconds, 2,926 MB.
- Intel i7-12700K, small FP32: 157 seconds, 2,257 MB RAM.
- CPU small INT8: 102 seconds, 1,477 MB.
- CPU batched INT8: 51 seconds, 3,608 MB.

These measure long-audio throughput, not cold or p95 latency for two-second learner answers.

The planned Hetzner GEX44 has:

- RTX 4000 SFF Ada, 20 GB GDDR6 ECC;
- Intel i5-13500;
- 64 GB RAM;
- two 1.92 TB NVMe drives.

That is sufficient for a warmed local Whisper-class recognizer, subject to actual Ollama/GPU sharing. [Hetzner GEX44 specifications](https://www.hetzner.com/dedicated-rootserver/gex44/).

The current Docker configuration explicitly forces local Whisper to CPU because the Sabi container has no usable CUDA device. That is the largest infrastructure problem. Expose the GPU to either the Sabi container or, preferably, a dedicated local-STT container. Since Gemini Live now handles the LLM in the cloud, the local route may not need Ollama occupying the GPU during these calls.

Use local `large-v3` FP16 initially for quality. Benchmark `turbo`, medium, and INT8 against the Sabi gold clips before changing. CPU large-v3 may work for short clips, but it should not be placed synchronously behind a 1.5-second deadline without measured p95 results.

Groq large-v3 and local large-v3 are not truly independent votes: they share architecture and weights and therefore can make correlated errors. They differ in runtime, quantization, decoding, and audio preprocessing, which provides some diversity, but agreement is evidence—not certainty.

## Other free/self-hosted STT candidates

### Highest-priority benchmark candidates

**Azure Speech `en-NG`**

Azure explicitly supports Nigerian English and offers real-time and fast transcription. `en-NG` also supports Custom Speech data including human-labeled audio, audio-only adaptation, text, structured text, output formatting, and pronunciation data. Its F0 tier provides five audio hours/month shared between standard and custom real-time transcription, plus one hosted custom model; batch is not included. [Azure language support](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/language-support), [Azure Speech pricing](https://azure.microsoft.com/en-us/pricing/details/speech/).

This is the strongest independent cloud comparator because it has a Nigerian English locale. Run it in the offline bake-off before adding another generic English recognizer. Five hours/month equals only about 43 complete seven-minute calls, but far more if only short learner turns are submitted.

**SBPN Base/Large**

“Sometin Beta Pass Notin,” released in May 2026, covers Yoruba, Hausa, Igbo, Nigerian Pidgin, and Nigerian English. It comes in 120M and 600M variants and is based on a Parakeet/NeMo family rather than Whisper, providing real model-family diversity. The authors report an average 29% relative WER reduction over monolingual baselines, although the public model card does not provide enough per-domain telephone detail to trust it without testing. It accepts 16 kHz mono WAV. The public weights are CC BY-NC-SA 4.0 and described as research/noncommercial only, so deployment licensing must be cleared. [SBPN model](https://huggingface.co/ogunlao/SBPN_multilingual_base), [paper](https://arxiv.org/abs/2605.17710).

**NaijaVox 2.0**

A 2026 Whisper-large-v3 LoRA model for Nigerian English, Pidgin, Yoruba, Hausa, and Igbo. The model card reports:

- Pidgin: 14.7% WER;
- Nigerian English: 19.6%;
- Yoruba: 22.3%;
- Hausa: 25.8%;
- Igbo: 30.5%.

But those figures use only 50 samples per language and not Nigerian PSTN child audio. It remains Whisper-family, so it is a quality-oriented local replacement to test, not a genuinely independent second vote. The card labels it Apache 2.0 but adds binding behavioral restrictions, so treat it as a custom license requiring review. [NaijaVox 2.0 model card](https://huggingface.co/Axiveri/NaijaVox-2.0).

### General self-hosted choices

**NVIDIA Parakeet / Nemotron**

`parakeet-unified-en-0.6b` is a 600M FastConformer RNN-T supporting offline and streaming operation with configurable 160–2,080 ms latency. It was trained mostly on approximately 250,000 hours of US English, not Nigerian English. It is a valuable third model because its errors should be less correlated with Whisper. [Parakeet Unified](https://huggingface.co/nvidia/parakeet-unified-en-0.6b).

The 2026 Nemotron 3.5 streaming model is also a 600M cache-aware FastConformer RNN-T with 80–1,120 ms chunks and commercial-use terms. Its 40 locales do not include Nigerian English, Hausa, Igbo, Yoruba, or Pidgin, so it is an architecture-diversity experiment, not the best accent match. [Nemotron 3.5 ASR](https://huggingface.co/nvidia/nemotron-3.5-asr-streaming-0.6b).

NeMo’s cache-aware models reuse prior encoder activations instead of repeatedly processing overlapping windows; this is better true streaming architecture than making Whisper repeatedly re-transcribe a rolling buffer. [NeMo cache-aware streaming](https://docs.nvidia.com/nemo-framework/user-guide/latest/nemotoolkit/asr/models.html).

**Meta Omnilingual ASR**

Released under Apache 2.0, with CTC and LLM-style models from 300M to 7B supporting more than 1,600 languages. The 300M CTC model is approximately 1.3 GiB download/~2 GiB inference VRAM; 1B CTC approximately 3.7 GiB/~3 GiB VRAM. It is attractive for future Nigerian-language lessons, but has no demonstrated Nigerian narrowband-numeracy result. [Omnilingual ASR](https://github.com/facebookresearch/omnilingual-asr), [model specifications](https://huggingface.co/facebook/omniASR-LLM-7B).

**Meta MMS**

`mms-1b-all` supports more than 1,100 languages at 16 kHz via per-language adapters. It is a 1B wav2vec2/CTC model, but the weights use CC BY-NC 4.0. It is more relevant to future Hausa/Igbo/Yoruba transcription than to Nigerian-accented English numeracy. [MMS model card](https://huggingface.co/facebook/mms-1b-all).

**Moonshine v2**

A genuinely streaming ONNX system trained from scratch, not Whisper. English models range from 34M to 245M parameters, with vendor-reported WERs of 12.0%, 7.84%, and 6.65%. It caches streaming state and runs locally across Linux, mobile, and Raspberry Pi. English code/models are MIT; non-English models use a noncommercial community license. It has no Nigerian or PSTN benchmark. It is a good low-latency endpoint/transcription experiment, not an immediate grading authority. [Moonshine](https://github.com/moonshine-ai/moonshine).

**Vosk**

Apache 2.0, offline streaming, compact models around 50 MB, dynamic vocabulary, and an Asterisk-compatible WebSocket/gRPC server. The official English models show a sharp domain problem: one model reports 5.69% WER on clean LibriSpeech but 29.78% on call-center audio. There is no official Nigerian English/Pidgin model. A constrained number grammar could make it a fast tertiary signal, but it should not be trusted without Sabi-specific testing. [Vosk API](https://github.com/alphacep/vosk-api), [models](https://alphacephei.com/vosk/models), [Vosk server](https://github.com/alphacep/vosk-server).

**whisper.cpp**

Compact C/C++ deployment with integer quantization, CPU/GPU support, Silero VAD, and configurable speech/silence thresholds and padding. Its sample streaming implementation repeatedly processes a five-second window every 500 ms and is explicitly described as naïve. It is a deployment alternative to faster-whisper, not independent recognition. [whisper.cpp](https://github.com/ggml-org/whisper.cpp).

**sherpa-onnx**

Apache 2.0 runtime supporting offline/streaming ASR, Silero VAD, enhancement, WebSockets, and models including Whisper, Moonshine, Parakeet, and Zipformer across server/mobile/embedded systems. It is a useful service boundary but not itself a Nigerian-trained recognizer. [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx).

**wav2vec2/XLS-R and SpeechBrain**

These are mainly training and deployment building blocks. Meta’s XLSR-53 public checkpoint is pretraining-only and must be fine-tuned for ASR. Existing project research records Nigerian Pidgin experiments around 30% WER, which is not strong enough for unverified grading. They become useful if Sabi collects a consented, telephone-domain Nigerian child dataset for fine-tuning. [XLSR-53](https://huggingface.co/facebook/wav2vec2-large-xlsr-53).

## Evaluation and rollout

### Phase 1: shadow mode

Limit to Naomi’s number.

For every numeric answer, store:

- call UUID and monotonically increasing turn ID;
- audio hash and speech timestamps;
- Gemini Live transcript;
- Groq raw transcript and metadata;
- local raw transcript and metadata;
- extracted numeric candidates;
- agreement outcome;
- per-engine and total latency;
- model/config/prompt versions;
- whether the grader would accept, reject, or abstain.

Do not let the sidecar alter Gemini’s behavior yet.

### Phase 2: labeled PSTN bake-off

Build a gold set using audio after it has passed through Twilio/Asterisk, not clean recordings. Include:

- numbers 0–100;
- teen/tens pairs: 13/30, 14/40, 15/50, 16/60;
- one/two/three and common Nigerian/telephone homophones;
- number plus arbitrary objects;
- Pidgin and code-switching;
- soft children’s voices;
- inexpensive handsets;
- background adults, fans, market noise, television;
- breaths, coughs, clicks, laughter and silence;
- clipped first phonemes;
- barge-in and echo;
- “I thought X, but the answer is Y.”

Human-label twice where possible.

Measure:

- numeric-value accuracy;
- agreement coverage;
- precision among accepted answers;
- wrong-agreement rate;
- abstention/repeat rate;
- false acceptance from non-speech;
- p50/p95/p99 endpoint-to-consensus latency;
- provider failures and Groq 429s;
- results by age, accent, phone, noise and carrier.

Generic WER is secondary. A transcript may have poor WER but still recover the correct number, or excellent WER while confusing 15 and 50.

### Phase 3: gated grading

Enable:

```text
exact external numeric agreement
AND one distinct value
AND calibrated probability above threshold
AND current turn id still valid
→ grade

otherwise
→ “I didn’t catch the number clearly. Say just the number again.”
```

Do not say the child was wrong after an ASR disagreement.

### Phase 4: model diversity

Benchmark Azure `en-NG`, SBPN, NaijaVox 2.0, and Parakeet against the same clips. If one beats generic local Whisper on numeric-value accuracy and licensing is acceptable, replace the local large-v3 vote with that model. A Parakeet/SBPN-family vote plus Groq Whisper is more meaningful than two copies of large-v3.

No code or deployment changes were made during this research.
