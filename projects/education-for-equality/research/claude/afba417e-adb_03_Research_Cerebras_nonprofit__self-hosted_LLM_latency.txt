- RAM: 64 GB

**Key constraint:** 280 GB/s memory bandwidth. Compare to:
- RTX 3090: 936 GB/s
- RTX 4090: 1,008 GB/s
- H100 SXM5: 3,350 GB/s
- H200: 4,800 GB/s

The RTX 4000 Ada SFF has **significantly less memory bandwidth than consumer gaming GPUs** despite having 20 GB VRAM. This is the primary bottleneck for LLM token generation speed.

**Important note on prompt processing vs generation:**

## Benchmark by Inference Engine on This GPU

No ExLlamaV2-specific benchmarks for RTX 4000 Ada SFF were found in any source. Here's what is known from across GPU types:

**Ollama (llama.cpp backend):**
- RTX 4000 Ada SFF: ~44 tok/s (this IS the localscore benchmark — localscore uses llama.cpp)
- Ollama adds 3–10% overhead vs raw llama.cpp due to Go server layer
- Effective with Ollama: ~40–43 tok/s

**llama.cpp (raw):**
- RTX 4000 Ada SFF: ~44–54 tok/s
- RTX 4090: ~150 tok/s (for reference: 4090 has 3.6x the memory bandwidth)
- RTX 3090: similar to 4090 in practice (~936 GB/s bandwidth, so ~100–150 tok/s range)

**vLLM:**
- vLLM is designed for **high-throughput multi-request serving**, NOT single-request latency
- For single concurrent request: vLLM has overhead from PagedAttention + CUDA graph warmup; may actually be slower than llama.cpp for single-stream
- For concurrent users (e.g., 16+ simultaneous): vLLM wins significantly
- On H100 with vLLM: 2,300–2,500 tok/s for Llama 8B (this is aggregate throughput across many concurrent requests, not per-request generation speed)
- vLLM does NOT help single-request latency for token generation on a consumer/prosumer GPU — it may slightly hurt it

**ExLlamaV2:**
- No RTX 4000 Ada SFF specific data found
- On RTX 3090 (936 GB/s bandwidth): ExLlamaV2 with EXL2 4-bit quant typically achieves 130–160 tok/s
- The bandwidth ratio suggests RTX 4000 Ada SFF with ExLlamaV2 EXL2 4-bit would get ~40–55 tok/s (proportional to 280/936 bandwidth ratio × 3090 speed)
- ExLlamaV2 is generally the fastest for generation on NVIDIA for single-user scenarios, but not dramatically faster than llama.cpp with good quants on this GPU

**TensorRT-LLM:**
- TensorRT-LLM outperforms llama.cpp by ~62.57% in benchmarks (from jan.ai testing)
- If llama.cpp gives 44 tok/s on this GPU, TensorRT-LLM might give ~70–72 tok/s
- Setup complexity is very high; requires building NVIDIA-specific engine files
- Best for production where you won't change models often

## Does vLLM Help Single-Request Latency?

**No, not for generation speed on a single request.**

vLLM's advantages:
- PagedAttention: eliminates KV cache memory fragmentation → allows larger batch sizes and longer contexts
- Continuous batching: serves many concurrent users efficiently
- At 16+ concurrent requests: vLLM wins vs llama.cpp significantly

vLLM's disadvantages for single-request:
- Overhead from CUDA graph capture on startup (30–60 second warm-up)
- PagedAttention has per-token overhead vs contiguous KV cache
- Single-request throughput is comparable to or slightly below llama.cpp

**For Sabi** (one voice call at a time, sequential 200-token outputs): **vLLM is not the right choice**. Stick with llama.cpp/Ollama or ExLlamaV2 for single-stream low-latency scenarios.

## Is Speculative Decoding Useful for 200-Token Outputs?

**For n-gram speculative decoding (no extra model required):**

Results are **mixed and context-dependent**:

- Reported speedup with 60% acceptance rate: ~2x (from 90–100 tok/s baseline to 182 tok/s baseline in one test — note this was on different hardware, not RTX 4000 Ada)
- N-gram decoding works by scanning the recent context for repeated patterns; for short outputs (200 tokens) with diverse content, the pattern cache has limited history to draw from — acceptance rates will be lower
- For scripted/repetitive content (like a fixed curriculum script), n-gram acceptance rates could be higher

**For EAGLE-3 / Medusa draft-model speculative decoding:**
- Requires loading a small draft model alongside the main model
- On a 20 GB VRAM GPU running 8B (which uses ~4–5 GB at Q4), there is headroom for a small 1B draft model
- EAGLE-3 in vLLM achieves **1.8x latency reduction** on Llama 3.1 8B on A100 (reported by Red Hat/vLLM blog)
- This would push ~44 tok/s to potentially ~79 tok/s on the GEX44 — not verified for this specific GPU
- Setup complexity is high

**Verdict for 200-token voice outputs:**
- N-gram speculative decoding: try it, costs nothing, llama.cpp `--spec-type ngram-simple` flag — may give 10–50% speedup on repetitive content, minimal benefit on diverse content
- EAGLE draft model: possibly worth exploring, but setup is complex and vRAM overhead is a concern
- **Neither gets you to 2,100 tok/s**

## What Hardware Would Actually Hit 2,000 tok/s Self-Hosted?

**Understanding the math:** 2,000 tok/s for Llama 8B generation requires approximately:

The model weights at Q4 are ~4.5 GB, but each token generation must load all those weights from VRAM through the compute units. At Q4_K_M, generation speed scales roughly linearly with memory bandwidth.

- RTX 4000 Ada SFF: 280 GB/s → ~44 tok/s
- To get 2,000 tok/s: need ~16x more bandwidth → **~4,480 GB/s**

That's above even the H100 SXM5 (3,350 GB/s). You'd need multiple H100s in tensor-parallel mode, OR the Cerebras Wafer Scale Engine (which is what Cerebras uses — WSE-3 has 21 PB/s internal bandwidth, an entirely different architecture class).
