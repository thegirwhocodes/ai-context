1. **Critical — a concurrent OAuth callback can reactivate an integration during disconnect.**
   Files: [Gmail callback:82](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/app/api/integrations/gmail/callback/route.ts:82), [upsert-integration.ts:71](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/lib/integrations/upsert-integration.ts:71), [migration 024:520](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security_and_disconnect.sql:520)

   Failure scenario: the callback’s tombstone check succeeds; disconnect then locks the row, creates a tombstone, and sets it to `revoked`; afterward the callback’s unconditional ID-based update writes fresh tokens and restores `active`. Disconnect revokes only the old captured token, while finalization fails because it requires the row still be `revoked`. The API can report local deactivation even though fresh credentials remain active.

   Minimal fix: move reconnect authorization and credential persistence into a database transaction/RPC using the same row or advisory lock as disconnect. Reject activation whenever an incomplete tombstone exists, and revoke the newly exchanged token when that atomic operation loses the race.
