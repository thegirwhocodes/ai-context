# Codex subagent report: /root/route_test_review

Below is the protocol I would hand to the test team. The most important improvement over the original outline is separating a true channel-quality test from a live-speaker test: the same person saying the same phrase three times does not produce identical input, so route effects can otherwise be confused with natural speaking variation.

# Sabi Telephony Route A/B/C Test Protocol

## 1. Objective

Determine whether recognition failures are primarily caused by:

- Africa’s Talking’s Nigerian carrier/SIP route
- The international Nigeria-to-US Twilio route
- Narrowband 8 kHz telephone audio generally
- The STT model, endpointing, or characteristics of the speaker’s voice

Routes:

- **A:** Nigerian caller → Africa’s Talking Nigeria → Asterisk
- **B:** Same Nigerian caller → US Twilio → test capture endpoint
- **C:** Same phone → browser/WebRTC over mobile data, used as a higher-bandwidth reference

This is a within-speaker crossover test. Every included speaker must test every route.

## 2. Primary test question

Using an identical STT model, model version, configuration, prompt and segmentation method, does Route B produce more correct transcripts than Route A?

Secondary questions:

- How much does native WebRTC audio improve recognition?
- Are word beginnings or endings being truncated?
- Do results differ for children, Nigerian names, numbers, short answers, mobile networks or device types?
- What is each route’s connection reliability, latency and cost per successfully understood turn?

## 3. Two complementary test layers

### Layer 1: Technical replay test

Use a set of high-quality, consented Nigerian speech recordings captured at 48 kHz. Play the exact same recordings through a fixed loudspeaker into the same phone, at a marked distance and fixed volume, while connected over A, B and C.

This is the cleanest test of the routes because every route receives the same acoustic input. Do not use an already degraded 8 kHz phone recording as the replay source; that would apply telephone degradation twice.

Recommended setup:

- One phone, fixed on a stand
- Speaker fixed approximately 20–30 cm from the phone microphone
- Marked speaker and phone positions
- Fixed playback volume, documented once
- Quiet room
- Same SIM and mobile network
- Wi-Fi, Bluetooth and Wi-Fi Calling disabled
- Mobile data from that SIM used for WebRTC
- At least three separately established calls per route, not three repetitions inside one call only

### Layer 2: Live-speaker crossover test

Test real participants using the same phone, SIM, room and normal handset position for all three routes. This captures natural speech, human behavior, carrier variability and real-world usability.

The replay test answers, “Which channel preserves identical input better?” The live test answers, “Which route works better for Sabi’s actual callers?”

## 4. Participants and workload

Run the study in stages.

### Stage 0: Infrastructure dry run

- 2–3 adult staff
- No children
- Confirm recording, timestamps, file mapping, randomization, STT reproducibility and cost logging
- Do not include these results in the final analysis

### Stage 1: Adult pilot

- 12 adults
- Aim for representation across the principal intended mobile networks
- At least four testers per network where feasible
- Use this pilot to estimate variability and refine the final sample size

This can identify a very large route failure but should not be treated as definitive proof of small differences.

### Stage 2: Confirmatory field test

- Preferably 24–36 participants
- At least 8 participants on each major network being compared
- Include at least 12 children if children are the target population
- Analyze adults and children separately as well as together

Utterances are clustered by speaker and phrase. Thousands of utterances must not be represented as thousands of independent participants.

### Phrase workload

Use a 36-phrase master pool. Assign 12–18 phrases to each participant using a balanced-incomplete-block schedule so every phrase is tested by approximately the same number of speakers.

Each assigned phrase is said:

- Once in each of three separately randomized rounds
- On each of the three routes
- Three times per route in total

For 12 assigned phrases, that is 108 utterances per participant. Allow approximately 20–30 minutes including connections and breaks. For children, keep sessions shorter or split them into two sessions.

## 5. Phrase-set design

The 36-phrase pool should contain predetermined strata:

- 8 Nigerian names, including names known to challenge general STT
- 8 numbers and number contrasts
- 6 very short answers
- 6 ordinary Nigerian English sentences
- 4 curriculum/lesson responses
- 4 Nigerian English or Pidgin phrases, if these are in product scope

Include number contrasts such as:

- thirteen / thirty
- fourteen / forty
- fifteen / fifty
- sixteen / sixty
- eighteen / eighty
- nineteen / ninety

Include one-word answers, multiword names, sentences of approximately 5–12 words and responses resembling actual Sabi lessons.

“Child speech” is a speaker population, not merely a phrase category. Adults imitating children cannot substitute for consented child participants.

Use two task types:

1. **Repeat-known-text task:** participant reads or repeats an exact phrase, providing indisputable ground truth.
2. **Sabi-like response task:** participant answers an actual lesson question. These should be manually annotated separately because natural answers may be valid without exactly matching one reference string.

## 6. Randomization and counterbalancing

Assign participants evenly across the six possible initial route orders:

- ABC
- ACB
- BAC
- BCA
- CAB
- CBA

Use three rounds. Change the route order between rounds so a route is not always affected by freshness, fatigue or network conditions at the same point.

Within every route and round:

- Randomize phrase order independently
- Do not repeat the same phrase back-to-back
- Keep all routes close together in time
- Use identical prerecorded instructions and prompts
- Do not tell the participant to enunciate more clearly on one route

Route order, phrase order and phrase assignment should be generated before testing, not selected by the operator.

## 7. Standard tester procedure

Before testing:

- Obtain consent; for children obtain guardian consent and child assent
- Charge the phone sufficiently
- Record phone make/model, OS, SIM network, location and approximate signal state
- Disable Wi-Fi, Bluetooth and Wi-Fi Calling
- Confirm the same SIM supplies voice and mobile data
- Use no headset or speakerphone
- Hold or mount the handset consistently
- Confirm the participant has not been billed unexpectedly for the US call

For each route:

1. Operator opens or dials the assigned test route.
2. Record call-setup success and connection time.
3. Play the same instructions.
4. Present phrases in the preassigned order.
5. Participant speaks normally and only repeats when instructed.
6. Do not silently discard mistakes, failed calls or disconnections.
7. If a call disconnects, allow one retry and flag both events.
8. After completion, record unusual noise, interruption or device behavior.
9. Give breaks between rounds, especially for children.

The test coordinator can label routes “Test 1,” “Test 2,” and “Test 3.” Participants may still infer the international route, so the essential blinding is analyst and scorer blinding.

## 8. Audio capture requirements

Preserve the first audio representation available from each provider before:

- Denoising
- Equalization
- Gain normalization
- Resampling
- Voice-activity detection
- Utterance segmentation

For every route save:

- Complete raw inbound caller-only call
- Original encoded media where available: PCMA, μ-law or Opus/media chunks
- Losslessly decoded PCM copy
- Separate outbound prompt channel
- Provider and transport metadata
- Immutable SHA-256 manifest

Do not use real-time VAD segments as the sole analysis audio. Preserve the continuous call and segment it offline using the same procedure for all routes. Otherwise a Route A/B comparison could accidentally become a comparison of two endpointing systems.

For WebRTC, save:

1. Native WebRTC/PCM audio at its actual rate
2. A deliberately downsampled and G.711-simulated 8 kHz version

This creates three useful contrasts:

- **A versus B:** local Nigerian route versus international Twilio route
- **WebRTC native versus WebRTC-G.711:** bandwidth/codec effect
- **WebRTC-G.711 versus A/B:** additional handset, carrier and telephony-path degradation

Record browser audio constraints and actual settings. Browser echo cancellation, noise suppression and automatic gain control should be disabled where supported, with the returned `getSettings()` values saved. Otherwise Route C may be measuring browser enhancement as well as bandwidth.

## 9. STT test controls

For the primary comparison:

- Use the same STT provider and exact model version
- Pin all decoding settings
- Use deterministic decoding where supported
- Use the same language code
- Use the same phrase hints or no phrase hints
- Use the same endpointing and utterance boundaries
- Run all audio in one randomized batch
- Store a configuration hash with every transcript

Do not compare AT+Google with Twilio+ElevenLabs and call that a route test.

Run two STT conditions if resources permit:

- **Unconstrained:** no knowledge of expected phrases
- **Production-like:** identical Sabi lesson context, vocabulary bias or answer constraints applied to every route

## 10. Blinding

Audio presented to STT and human scorers should use opaque identifiers such as:

`clip_000001.wav`

Do not include route, codec, provider, network or participant information in:

- Filename
- Directory path available to scorers
- WAV metadata
- Batch order

Keep the mapping in a separate restricted file controlled by one coordinator. Freeze the metric definitions and decision rules before revealing route identities.

A listener may guess that WebRTC sounds clearer; this cannot be fully prevented. They should still never see the actual labels.

Suggested storage structure:

```text
protocol-v1/
  restricted/
    participant-identity-map.enc
    route-blinding-key.enc
  raw-calls/
    call_<opaque-id>.<original-format>
  decoded-calls/
    call_<opaque-id>.wav
  blinded-segments/
    clip_<opaque-id>.wav
  manifests/
    checksums.sha256
    capture-metadata.csv
  results/
    stt-output.csv
    human-audit.csv
    analysis.csv
```

## 11. Minimum data schema

Each utterance record should contain:

- Protocol and capture-software version
- Pseudonymous participant ID
- Age band, not unnecessary birthdate
- Adult/child indicator
- Self-described language/accent information where consented
- Mobile network
- Phone model, OS and relevant audio settings
- Route, concealed until unblinding
- Route order, round and call ID
- Phrase ID, category and canonical text
- Take number and randomized position
- Opaque raw-call and segment file IDs
- Original codec, sample rate, channel count and duration
- Prompt-end, speech-start and speech-end timestamps
- Last-audio-received and final-transcript timestamps
- STT model/version/configuration hash
- Raw and normalized transcript
- Confidence and alternatives where available
- Exact-match, WER/CER and critical-slot result
- Beginning/end truncation flags
- Packet-loss, jitter and RTP gap data where available
- Connection success, disconnect and retry flags
- Call duration
- Project-side cost and caller-side cost
- Operator notes and consent version

Unavailable network telemetry must be stored as unavailable, not as zero.

## 12. Metrics

### Primary metric

**Normalized exact-match accuracy**, paired within participant and phrase, for Routes A and B.

Normalization rules must be frozen in advance, for example:

- Lowercase
- Standardize punctuation and whitespace
- Convert number words/digits to one canonical representation
- Do not silently correct names or replace incorrect words

### Critical secondary metrics

- Exact match for names
- Exact match for numbers
- Critical-answer or slot accuracy
- Word error rate for sentences
- Character error rate for names
- Beginning truncation
- Ending truncation
- Call setup/completion rate
- Speech-end-to-final-transcript latency
- Median and p95 latency
- Packet loss, jitter and RTP sequence gaps where available
- Provider cost per minute
- Caller cost
- Cost per correctly understood turn

Latency timestamps should be taken on the capture/STT servers using monotonic clocks where possible. Do not claim true microphone-to-server one-way latency unless the system contains a defensible synchronization method.

Have two blinded human listeners independently audit all errors or a preregistered sample. Adjudicate disagreements. They should judge what is actually audible, not what the script says it should be.

## 13. Statistical analysis

The unit of inference is not the individual audio file alone. Use either:

- Mixed-effects logistic regression with route as a fixed effect and participant and phrase as random effects, or
- A two-way cluster bootstrap over participants and phrases

Report:

- Paired percentage-point difference
- 95% confidence interval
- Results by phrase category
- Adults and children separately
- Network-specific results, clearly labeled exploratory unless sufficiently powered
- Connected-call speech accuracy
- An intention-to-test result that treats connection failure as an operational failure

Do not remove route-related failed calls from the only reported result.

Use Stage 1 variance and clustering estimates to calculate the final confirmatory sample. A 12-person pilot can expose large defects but is not adequate evidence that two routes are equivalent.

## 14. Predefined decision rules

Recommended rules:

### Switch or seriously pursue Twilio only if all are true

- Route B improves overall exact match over A by at least 10 percentage points
- Lower bound of the 95% confidence interval is at least +5 points
- It does not reduce child, number or name accuracy by more than 5 points
- It does not create a material call-connection barrier
- p95 transcript latency is no more than 300 ms worse than A
- Caller-side international cost and access are acceptable
- Improvement remains when analyzed across multiple mobile networks

### Treat routes as practically equivalent only if

The entire 95% confidence interval for A–B exact-match difference lies within ±5 percentage points.

If the interval crosses both meaningful benefit and meaningful harm, the result is inconclusive—not evidence of equivalence.

### Retain Africa’s Talking if

- Twilio improves accuracy by less than 5 points
- The result is inconclusive and Twilio is less accessible or more costly
- Twilio’s apparent benefit occurs on only one device/network or disappears in the controlled replay test

### Offer WebRTC as a higher-quality route if

- Native WebRTC improves exact/critical-answer accuracy by at least 10 points
- Completion, data use and user flow are acceptable
- The benefit survives the child and low-end-device analysis

Also compare cost per correctly understood turn, not merely price per minute.

## 15. Major confounds the team must guard against

- Natural variation between repeated human utterances
- Different call times or network congestion
- Different prompt audio or agent behavior
- Different VAD and segmentation
- STT model/version drift during the experiment
- Route-specific gain normalization or denoising
- Browser noise suppression/AGC
- Speakerphone, Bluetooth or Wi-Fi Calling
- Prompt leakage or echo into the caller channel
- Fatigue, memorization and order effects
- Dropping failed calls only from the worse route
- Treating repeated utterances as independent samples
- Confusing a higher-bandwidth WebRTC reference with a pure carrier comparison
- Comparing network telemetry that is measured differently by each platform
- Scorers learning the route from filenames or metadata

## 16. Privacy and child-safety requirements

Voice recordings are sensitive and potentially identifying.

- Adult dry run must succeed before recording children
- Obtain guardian consent and age-appropriate child assent
- Clearly disclose call recording and external STT processing
- Do not ask participants to say their real full names, phone numbers, addresses, school or other personal details
- Use invented names and fixed test content
- Keep identity/contact details separate from audio IDs
- Restrict the unblinding key
- Encrypt stored audio and transfers
- Establish retention and deletion dates before collection
- Confirm every external STT service is approved for these recordings
- Record withdrawals and delete the corresponding audio through the identity map
- Reimburse any test-related airtime or international charges

## 17. Required handoff package

The implementation team should receive:

- Frozen protocol and decision thresholds
- Phrase master list and category labels
- Balanced participant-to-phrase assignments
- Latin-square route-order assignments
- Operator checklist and participant instructions
- Adult consent, guardian consent and child assent forms
- Capture configuration and version manifest
- File/metadata schema
- Blinding key procedure
- Raw-capture validation checklist
- Locked STT configuration
- Scoring normalization rules
- Statistical analysis template
- Cost log
- Incident/deviation log
- Final decision-memo template

This design makes a defensible distinction between a carrier-route problem, an 8 kHz telephony problem, a WebRTC bandwidth benefit, an endpointing problem and an STT model mismatch.
