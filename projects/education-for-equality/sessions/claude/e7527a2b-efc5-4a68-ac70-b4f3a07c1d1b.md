## 1. Replace DTW with a Pretrained Neural Model (Highest Impact)

**Current:** Angle-based DTW matching against manually recorded references. Requires running `reference_recorder.py` (which was never completed). Vocab limited to however many signs you manually record. Signer-dependent.

**Research says:** Multiple pretrained models exist that work immediately:
- **CorrNet+** — open source, handles continuous SLR AND translation from RGB video, SOTA on PHOENIX-2014T
- **SignVLM** — CLIP-based, zero-shot capable, works across multiple sign languages
- **Google SignGemma** — on-device, <200ms, trained on 10,000+ hours (developer preview)

**The optimization:** Integrate CorrNet+ or SignVLM as the primary recognition engine. The DTW matcher ([sign_matcher.py](app/sign_matcher.py)) would become a fallback for custom signs, not the primary engine. This eliminates the reference recording bottleneck entirely — you go from 0 vocab to 100-2,000 signs instantly.

**Why this matters:** Right now the system literally cannot recognize anything because no references were ever recorded. A pretrained model makes the system functional out of the box.

---

## 2. Add Temporal Sequence Processing to the Detection Loop

**Current:** [sign_buffer.py](app/sign_buffer.py) buffers frames correctly but the entire pipeline depends on the DTW matcher having references. The detection loop in [app.py:86-186](app/app.py#L86-L186) processes one sign at a time in isolation.

**Research says:** Continuous SLR (recognizing connected, fluid signing) requires CTC-based seq2seq models that handle coarticulation — signs blending into each other. Best approach is CTC + Transformer encoder.

**The optimization:** Instead of waiting for signing to "stop" (the pause threshold in [sign_buffer.py:45](app/sign_buffer.py#L45)), implement a sliding window approach. Feed overlapping 2-second windows to the model continuously. This enables recognizing signs mid-stream without waiting for the signer to pause.

---

## 3. Actually Use the Face Features for NMM Detection

**Current:** [keypoint_extractor.py:99-164](app/keypoint_extractor.py#L99-L164) extracts 6 face features (eyebrow height, mouth openness, head tilt, etc.) — but they're just concatenated into the feature vector for DTW matching. No actual grammatical interpretation happens.

**Research says:** Non-manual markers carry grammatical meaning:
- Raised eyebrows = yes/no question
- Furrowed brows = wh-question
- Head shake = negation
- Mouth morphemes ("cha", "mm", "th") = adverbial modifiers

Apple's CHI 2025 system achieved 98% precision on yes/no question detection, 93% on wh-questions.

**The optimization:** Add a simple NMM classifier that reads the face features and emits grammatical markers alongside the sign recognition:

```python
# After extracting face_feat in the detection loop:
if face_feat[0] > threshold and face_feat[1] > threshold:  # both brows raised
    nmm = "QUESTION_YN"
elif face_feat[0] < threshold and face_feat[1] < threshold:  # both brows furrowed
    nmm = "QUESTION_WH"
```

Then pass these to [language.py](app/language.py)'s `assemble_sentence()` so Claude knows "WATER WANT" + QUESTION_YN = "Do you want water?" vs just "I want water."

**Current:** [speech.py:76-84](app/speech.py#L76-L84) uses `speech_recognition` library with Google STT. It blocks, times out after 3 seconds, and requires internet.

**Research says:** Whisper runs locally, handles noise better, supports continuous streaming, and is more accurate. The product plan listed this as a Phase 1 upgrade.

**The optimization:** Replace `recognize_google()` with `faster-whisper` (a CTranslate2-optimized Whisper). Runs on CPU, ~5x realtime on the small model. No internet needed. Continuous listening without timeouts.

## 5. Fix the TTS Blocking/Latency Issue

**Current:** [speech.py:38-54](app/speech.py#L38-L54) — Edge TTS saves to `/tmp/dactyl_tts.mp3` then plays with `os.system("afplay ...")`. This blocks the audio thread until playback finishes.

**The optimization:**
- Queue TTS outputs so concurrent signs don't overwrite the temp file
- Use `subprocess.Popen` instead of `os.system` for non-blocking playback
- Pre-generate common phrases ("hello", "thank you", "help") as cached audio files for zero-latency playback on frequent signs

## 6. Richer Feature Representation in Keypoint Extractor

**Current:** 54 features per frame (20 hand angles per hand + 6 face + 8 pose).

**Research says:** The 2026 paper on geometry-aware metric learning showed that adding **inter-hand features** (distance between hands, relative hand position, whether hands are touching) gave significant accuracy boosts. SignGlass also uses hand-to-face relative position for signs like MOTHER/FATHER (same handshape, different location).

**The optimization:** Add to [keypoint_extractor.py](app/keypoint_extractor.py):
- Distance between left and right hand (normalized by shoulder width)
- Each hand's position relative to face center (for signs at forehead, chin, chest)
- Hand velocity (delta between current and previous frame's position)
- These would add ~8-10 more features per frame, targeting the exact features that distinguish similar signs.

## 7. Improve the Fingerspelling Classifier

**Current:** [fingerspell.py](app/fingerspell.py) is entirely rule-based with hardcoded thresholds. Covers ~18 letters. Missing G, H, J, M, N, P, Q, T, Z. Confidence values are hardcoded.

**Research says:** Rule-based on MediaPipe + Random Forest achieves 98.83% on static ASL letters. A small trained classifier on the angle features would massively outperform the rules.

**The optimization:**
- Train a lightweight classifier (Random Forest or small MLP) on the 20 hand angle features from `_hand_angles()` using ASL alphabet image datasets (available on Kaggle/HuggingFace)
- This would cover all 26 letters + numbers with real confidence scores
- Falls back to the rule-based system if the classifier isn't loaded

**Current:** The hackathon plan called for TGCN as a secondary engine. It was never integrated.

**Research correction from the session:** Real TGCN benchmarks show ~55% on WLASL100 (not the claimed >85%). But even at 55%, it adds value as an ensemble member. When DTW and TGCN agree, confidence is very high. When they disagree, flag as ambiguous.

**The optimization:** Add a `tgcn_model.py` wrapper. Run both DTW and TGCN on each sequence. If both agree → high confidence (green). If one matches → medium (yellow). Neither → unknown (gray). The combined accuracy of the ensemble exceeds either alone.

**Current code (freezes):**
- Backend: `_make_snapshot()` — returns a **single JPEG** per request. One frame, done.
- Frontend: `pollCamera()` with `setInterval` — polls every 80-120ms by creating a new `Image()` object each time. The snapshot polling approach is inherently fragile — it depends on every single HTTP request completing fast. One slow response and the `loading = true` guard locks it up.

The fix is to go back to MJPEG streaming for the feeds. The streaming generators never freeze because the browser holds a single persistent connection and the server pushes frames as they're available.

Great question. **It CAN be the same speed as localhost** — with WebRTC. Here's why:

**Tunnels will always be slower than localhost** because every video frame travels: your machine → tunnel server → viewer's browser. That's a detour through a third-party server.

**WebRTC eliminates the middleman.** Video goes directly from your machine to the viewer's browser — peer-to-peer. The tunnel only handles the initial handshake (a few KB), then it's out of the picture. Latency drops to 50-150ms regardless of what tunnel you use.

**Your idea about "opening localhost on the person's computer"** — that's basically what WebRTC does. The viewer's browser connects directly to your machine and receives the video stream as if it were local. Plus it uses H.264 compression (10-50x smaller than MJPEG), so it's actually faster than our current localhost MJPEG approach.

**Quick comparison:**

| Approach | Video path | Latency | Bandwidth |
|---|---|---|---|
| Localhost (current) | Camera → Flask → your browser | ~0ms | 3-6 MB/s (MJPEG, uncompressed) |
| Cloudflare tunnel | Camera → Flask → Cloudflare → viewer | 50-260ms | 3-6 MB/s through tunnel (slow) |
| **WebRTC** | Camera → **directly to viewer's browser** | 50-150ms | 0.1-0.3 MB/s (H.264 compressed) |

There's a Python library called `aiortc` that does WebRTC with Flask + OpenCV. It would replace our MJPEG `<img src>` tags with a WebRTC video element. The tunnel (Cloudflare, ngrok, whatever) only carries the tiny signaling messages.

# Every Way to Share Dactyl Without Touching Code

## The Situation

Dactyl runs on localhost:5001. It uses WebRTC for video (peer-to-peer) and SocketIO for signaling/events. The camera runs on YOUR machine. You need other people to see it — across the room or across the internet.

Because WebRTC sends video directly browser-to-browser, **the tunnel only carries tiny signaling messages** (~KB/s). Video quality and speed are the same regardless of which tunnel you pick.

---

## 1. Tunneling Services (Ranked)

### ngrok — Best Overall

One command: `ngrok http 5001`

Gives you something like `https://abc123.ngrok-free.app`. HTTPS built-in. WebSocket and SocketIO work out of the box — ngrok correctly passes the WebSocket upgrade headers. WebRTC signaling flows through fine, then video goes P2P and bypasses ngrok entirely.

**Free tier:** 1 static domain (you pick the name, like `dactyl-demo.ngrok-free.app` — it's yours permanently), 20 connections/minute, 1 online agent. The catch: free tier shows an interstitial "Visit Site" warning page on first visit. Viewers click through it once and they're in.

**Paid ($8/mo Personal):** Removes the interstitial, 3 static domains, IP restrictions, more connections. $20/mo Pro gets 5 domains and OAuth protection.

**Latency:** 30-80ms added for signaling. Doesn't matter for video since WebRTC is P2P.

**macOS:** `brew install ngrok`. No kernel extensions, no system network interception, no blocking your browser. Clean install, clean uninstall.

**Setup time:** 30 seconds.

---

### Cloudflare Quick Tunnel — Best Free, No Account

One command: `cloudflared tunnel --url http://localhost:5001`

Gives you something like `https://random-words-here.trycloudflare.com`. No sign-up, no account, no interstitial warning. HTTPS automatic. Cloudflare's global edge network means very low latency (often under 30ms to nearest PoP).

**Free:** Unlimited bandwidth, no rate limits documented, no account needed. URL is random and changes every restart.

**Named tunnel (free with account):** If you create a free Cloudflare account and add a domain ($10/year for a .com), you get a permanent URL like `demo.dactyl.dev`. Completely free after the domain purchase.

**WebSocket/SocketIO:** Full native support. Cloudflare explicitly supports WebSocket proxying.

**macOS:** `brew install cloudflared`. No system extensions, no network interception. Safe.

**Gotcha:** Quick tunnel URLs are ugly long random strings. And if your network blocks QUIC protocol (common on university WiFi), add `--protocol http2` to the command.

**Setup time:** 30 seconds for quick tunnel. 5 minutes for named tunnel with account.

---

### Pinggy — Zero Install, SSH-Based

One command: `ssh -p 443 -R0:localhost:5001 a.pinggy.io`

Nothing to install. Works from any terminal that has SSH (which macOS does by default). Gives you an HTTPS URL immediately.

**Free:** 60-minute sessions, then the URL expires and you get a new one. 1 Mbps bandwidth limit on free. Random subdomain.

**Paid ($2.50/mo):** Persistent URLs, higher bandwidth, custom domains.

**WebSocket:** Full support.

**macOS:** Works anywhere SSH works — nothing to install, nothing to configure, nothing that could block your browser.

**Best for:** Quick demos when you can't or don't want to install anything. The 60-minute limit is tight but covers most demo scenarios.

**Setup time:** 10 seconds.

---

### Serveo — Also Zero Install

One command: `ssh -R 80:localhost:5001 serveo.net`

Same idea as Pinggy — SSH-based, nothing to install. Gives you `https://something.serveo.net`.

**Free:** Completely free, no account.

**Reliability warning:** Serveo has had extended outages — it was down for months in 2020-2021. Currently operational but no SLA. Don't rely on it for anything important.

**WebSocket:** Supported.

**Setup time:** 10 seconds.

---

### localhost.run — Another SSH Option

One command: `ssh -R 80:localhost:5001 localhost.run`

Same pattern. Free, HTTPS, WebSocket supported. URLs rotate, rate limited.

**Setup time:** 10 seconds.

---

### bore — Rust-Based, Self-Hostable

Command: `bore local 5001 --to bore.pub`

Free, open source, very fast (thin TCP proxy, <5% overhead). If you self-host bore on a VPS, you control everything.

**Critical problem:** No HTTPS built-in. The public `bore.pub` relay gives you `bore.pub:RANDOM_PORT` over plain TCP. Modern browsers **require HTTPS** for WebRTC's `getUserMedia()` camera access. So if the viewer needs camera access, bore won't work. If they're just viewing your stream, it might work but the browser may still complain.

**Verdict:** Not suitable for WebRTC apps unless you add your own TLS termination.

---

### Tailscale Funnel — Avoid

Permanent URL (`https://your-machine.tail-net.ts.net`), free, decent speed. But on macOS it installs a system network extension that **intercepts all your network traffic**, can block your browser and other apps (you experienced this), and requires the Tailscale daemon to be running at all times. Port restrictions (443/8443/10000 only). Over-engineered for a demo.

**Verdict:** Don't use for Dactyl. The macOS network interception issues are a dealbreaker.

---

### localtunnel (npm) — Unreliable

`npx localtunnel --port 5001`. Free, gives `*.loca.lt` URL. But the public server frequently goes down, connections drop randomly, and SocketIO can be flaky with its long-polling fallback.

**Verdict:** Fine for a 5-minute test. Don't trust it for a demo.
