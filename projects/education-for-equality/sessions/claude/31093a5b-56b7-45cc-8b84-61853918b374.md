## What I found (the mechanics)

**The mic is a hard singleton.** Local VoiceMode's `converse` always records from the *system default* microphone ([converse.py:798](/Users/naomiivie/.claude/plugins/marketplaces/voicemode/voice_mode/tools/converse.py#L798) — `sd.default.device[0]`). There is **no env var to assign different mics to different sessions**. Every local session shares one mic + one speaker.

**The "conch" is the traffic cop.** VoiceMode coordinates sessions with a flock-based lock file at `~/.voicemode/conch` ([conch.py](/Users/naomiivie/.claude/plugins/marketplaces/voicemode/voice_mode/conch.py)). Only one `converse` can hold the mic at a time. The critical knob is the per-call **`wait_for_conch`**, which **defaults to `false`** — meaning *"if another agent is speaking, bail immediately."* That's exactly the "fighting" you'd feel. Set it to `true` and a busy session **queues politely** (waits up to `CONCH_TIMEOUT`=60s) instead of colliding. Stale locks from a crashed session auto-clear after `CONCH_LOCK_EXPIRY`=300s.

**Per-session identity comes from per-project config.** Config precedence is: env → **`.voicemode.env` in the project's working dir** → `~/.voicemode/voicemode.env` → defaults. So each project folder can get its **own distinct voice** (af_sky / af_bella / af_nova…) so you can tell sessions apart by ear.

**True parallel = different audio endpoints.** Two real options exist, both with caveats:
- **LiveKit rooms** — marked *"coming soon"* in this build (8.6.1). Not usable yet.
- **VoiceMode Connect** (voicemode.dev cloud) — the genuine multi-device path: each session routes to a separate client (your **phone app** or a **browser tab**). But it needs *your* OAuth login + internet + higher latency, and its own skill admits multi-agent routing is still under-specified ("How do multiple agents on the same account interact?").

## The honest bottom line

One person physically has one mouth and one pair of ears — you can't *usefully* hold two live voice chats at the same instant.
