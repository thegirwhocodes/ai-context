1. **P1 — Consent-version changes do not prohibit replay.**
   [Migration 024](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:2564) leaves `consent_withdrawn_at` unset when consent remains granted but its version changes. [Reconciliation](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/lib/lora/training-reconciliation.ts:37) suppresses PUT replay only for withdrawal/disconnect.
   **Scenario:** an ambiguous attempt was leased under version 4; the user reaffirms consent or reconnects, creating version 5; dispatcher lookup returns 404, so Cortex resubmits the version-4 payload. Activation also invalidates only `prepared` leases at [line 1994](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:1994).
   **Minimal fix:** mark every post-claim consent-version change as replay-forbidden, including activation; immediately before every dispatcher PUT, lock sources and revalidate the exact persisted consent versions or require a new lease.

2. **P1 — A completed/cancelled followup can be inserted after disconnect proof.**
   [The writer trigger](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:4024) bypasses the writable/tombstone assertion whenever the new followup status is `completed` or `cancelled`.
   **Scenario:** finalization obtains the integration lock, deletes and proves zero followups, then commits. A concurrent completed-followup insert waiting behind that lock resumes, takes the status exception, and survives after deletion.
   **Minimal fix:** remove the status exception. Only the transaction-local disconnect-cleanup marker should authorize cleanup writes.

3. **P1 — Per-field provenance can still be fabricated across accounts.**
   [The capture trigger](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:4307) records every unchanged field whenever only the person’s source pointer changes. The historical [backfill](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:1104) also derives every linked person’s name from the message `from` field regardless of `relationship_role`.
   **Scenario:** account A supplies sensitive notes; a generic account-B message merely updates `last_contacted_at`, causing A’s notes/metadata to be copied as B provenance. Disconnecting A therefore retains A-only facts. For outbound mail, recipient Alice can be backfilled with the user’s sender name.
   **Minimal fix:** capture only actually changed fields; rely on explicit observation writers for equal values. Backfill names from the role-specific matched candidate (`from`, `to`, attendee), and do not fabricate unsupported field observations.

4. **P1 — Machine extraction overwrites user-confirmed people.**
   [Assistant-loop update](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/lib/ai/assistant-loop.ts:388) applies the full machine-derived row to an existing person while preserving `user_confirmed: true`.
   **Scenario:** a user corrects Alice’s name, relationship, priority, or notes; a later model extraction matching Alice’s email silently replaces those values while the row still claims to be user-confirmed.
   **Minimal fix:** never update user-controlled fields or source pointers when `existing.user_confirmed` is true. Store machine observations separately and make per-field user provenance win at write time.

5. **P1 — Access-token ciphertext is queued into an outbox that can never process it.**
   Several race/disconnect branches enqueue `credential_kind='access_token'`, including [activation race loss](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:1830) and [disconnect](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:4562). But [the worker](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:2401) categorically claims only refresh tokens.
   **Scenario:** Google omits a refresh token and activation loses a disconnect race. The access credential remains encrypted in a permanently queued row; “remote revocation queued” is misleading, and exact retention is violated.
   **Minimal fix:** send all access-only paths to the digest-only retirement ledger, adding required retirement reasons. Never store access-token ciphertext in the remote-revocation outbox.

6. **P1 — The autonomous retry schedule defeats the six-attempt contract.**
   Reconciliation runs only once daily in [vercel.json](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/vercel.json:4), while attempts expire after 24 hours and unknown outcomes schedule a 15-minute retry.
   **Scenario:** a pre-dispatch crash just after the daily run waits almost 24 hours for its first replay. One transient dispatcher outage then pushes the next run beyond the age cap, dead-lettering after zero or one effective recovery attempts—not six.
   **Minimal fix:** run a dedicated reconciler every 5–10 minutes, or otherwise align the deadline and attempt cap with the actual scheduler cadence.

7. **P1 — Late webhooks can replace the stable provider-job mapping.**
   [Webhook reconciliation](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/supabase/migrations/024_google_oauth_security.sql:3552) overwrites `provider_job_id` with any nonempty incoming ID, while [the route](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/app/api/lora/webhook/route.ts:42) permits a missing ID.
   **Scenario:** a faulty dispatcher launches jobs A and B. Cortex records A, but B’s later signed webhook rebinds the attempt and can fail or deploy the wrong result. A terminal webhook without an ID can also reconcile an unknown attempt without a durable provider mapping.
   **Minimal fix:** require a nonempty job ID and atomically bind it only when the stored ID is null or equal; reject mismatches. Bind the webhook to the stable submission/tenant identity.

8. **P1 — Dispatcher transport is not fail-closed.**
   [Configuration validation](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/lib/lora/training-client.ts:294) accepts any absolute URL, and [dispatch](/Users/naomiivie/cortex/.worktrees/google-oauth-redo/lib/lora/training-dispatcher.ts:55) sends the bearer token, complete base64 training corpus, and secret-bearing webhook over it.
   **Scenario:** an `http://` dispatcher configuration exposes private Gmail training data and credentials to interception and permits spoofed job mappings.
   **Minimal fix:** require HTTPS in production, allowing HTTP only for explicit localhost development; reject URL credentials, query, and fragment components.
