I've now read the actual production code end-to-end. Here's the full picture of Sabi's codebase.

## Two codebases, one product

**`sabi-server/`** (Python/FastAPI) is the real production voice engine — a private, self-hosted server running on a Hetzner GPU box (136.243.8.51). **`curriculum-app/`** (Next.js) is the public web platform (marketing, pricing, demo, admin/advisor pages) plus a *secondary*, numeracy-only Africa's Talking webhook path in `lib/voice/` that mirrors the Python logic in TypeScript. Per your own memory notes, literacy only ships through the Python/Asterisk server — the Next.js AT path is numeracy-only.

## Telephony: four call lanes, one backend

`main.py` (1,294 lines) is the FastAPI app. It mounts:
- **`voice.py`** — Africa's Talking XML webhook (`<Record>`/`<Play>` loop, streaming LLM→TTS to cut time-to-first-audio)
- **`voice_twilio.py`** — Twilio XML webhook (currently the *only* provider that can reach a US-verified number on a Trial account, per your Aug 2026 work — used for text-to-call triggers)
- **`voice_asterisk.py`** — legacy FastAGI dialplan handler (fallback for older Asterisk configs) plus the shared TTS-provider chain (ElevenLabs → Chatterbox → YarnGPT) used everywhere
- **`voice_realtime.py`** (2,889 lines) — the real production path: a raw AudioSocket TCP handler that Asterisk connects to for full-duplex 8kHz PCM streaming, with barge-in detection, DTMF keypad fallback, mid-call feedback hotkey (`*`), and literacy-vs-numeracy STT routing

Three separate AudioSocket listeners run concurrently (ports 9019 production, 9020 Intron-STT canary, 9021 "original hackathon prompt" comparison lane), so provider bake-offs happen on live traffic without touching production.

**Flash-callback economics**: every inbound caller is, by default, hung up on and called back on Sabi's own line (`SABI_FLASH_CALLBACK_ALL=1`) so the child is never charged. `main.py` handles AMI-Originate through Asterisk against whichever SIP provider is configured (`SABI_SIP_PROVIDER` — Africa's Talking or Twilio), with cooldown/dedup and a retry path for calls that answer into carrier audio/voicemail instead of a real child.

## The two conversation engines

**Legacy/fallback: turn-based AudioSocket loop** (`voice_realtime.py` + `voice_asterisk.py`). Record one utterance → STT → text LLM call → TTS → play. Barge-in uses a two-stage detector (`turn_taking.py`): a cheap RMS prefilter, then Silero VAD speech-evidence scoring, then acoustic-echo-similarity rejection (so Sabi's own voice bleeding into the mic doesn't self-interrupt). A Pipecat Smart Turn v3.2 ONNX model decides whether a pause is a completed turn.

**Current production: Gemini Live persistent session** (`gemini_live.py`, 2,228 lines). One `gemini-3.1-flash-live-preview` WebSocket stays open for the whole call — Gemini itself owns VAD, turn-taking, and barge-in over native audio, streamed as raw PCM (8kHz in, 24kHz out, custom `Pcm24kTo8k` downsampler with a 3-sample moving-average anti-alias filter). Every caller defaults into this lane (`SABI_GEMINI_LIVE_ALL=1`); a Gemini setup failure falls back transparently to the AudioSocket path so no call is ever lost.

Two operating modes, both live in the code, controlled by `SABI_GEMINI_LIVE_TOOLS`:
- **"on" (deterministic deck)** — a fixed, hand-authored bank of 18 tiered equal-groups multiplication word problems (`MULTIPLICATION_PROBLEMS`), selected deterministically by a SHA-256 hash of the call UUID so it's non-repeating but reproducible. Gemini calls `get_next_numeracy_problem` / `grade_numeric_answer` / `get_lesson_progress` tools; the backend, not the model, decides correctness.
- **"ledger" mode** — Naomi's design: Sabi invents her own naira word problem and calls `register_question` with the question *and* the expected answer *before* asking it aloud, so the backend still grades deterministically but the teaching stays spontaneous (the thing you said you wanted back from the original Claude-Haiku hackathon build).
- **"off"** — no tools at all; pure prompt-driven improv teaching, closest to the hackathon original.

A server-side lesson clock (`lesson_progress()`) enforces a 5–7 minute minimum/target window and literally intercepts and blocks Gemini from wrapping up early (`is_early_wrap_text` pattern match → `_send_json` a controller correction telling it to keep teaching) — up to 3 repair attempts per call.

The tutor prompt itself lives in `prompts/sabi_tutor_prompt.md` (hot-reloadable, code has a hardcoded fallback copy) — it's "Prompt G" from `scripts/prompt_lab.py`, chosen after a blind 5-round judged comparison against the original hackathon Claude-Haiku Sabi (scored 8.8 vs 5.8 overall, 9.0 vs 5.2 on "sounds like the original Sabi"). Style directives are explicit: "very bush Nigerian accent," two-sentence ceiling, question always last, every problem framed as a Lagos-market moment (groundnuts, pure water, garri, chin-chin), scaffolds preserve the exact same numbers rather than substituting easier ones.

## STT: a 5-provider ensemble with live-call measurement

`stt.py` (1,835 lines) supports Groq Whisper, self-hosted `faster-whisper` (GPU), Gemini multimodal audio, Intron Sahara (Nigerian-accent-tuned), and Azure Speech — selectable per-mode (`general`/`literacy`) via env vars. The two interesting live mechanisms:

1. **Parallel-consensus mode** — Groq and local Whisper race simultaneously; if their transcripts (or, on a numeric-answer turn, their extracted numeric *values*) agree, that's authoritative immediately. On disagreement, an already-in-flight Gemini call tie-breaks. This is deliberately not "vote of 3" — it's race-then-verify to keep latency down.
2. **Numeric sidecar shadow measurement** (`numeric_sidecar.py`) — runs *only* on the Gemini Live production lane, *after* the turn is already answered. Groq + local Whisper re-transcribe the same clip with zero lesson context (so they can't be biased toward the expected answer) purely to check whether Gemini's own native-audio hearing was right. If both re-hearers agree and disagree with what Gemini heard, a correction message is injected into the *next* turn ("You heard X, that was wrong, go with Y — never mention transcription"). This exists because Nigerian 8kHz phone audio gets mis-heard by Gemini in specific, previously-documented ways ("thirty" → "Tati").

A VAD pre-gate (Silero) blocks dead-air/silence/crying-baby audio from ever reaching a model, because otherwise Whisper-family models hallucinate fluent captions ("Subtitles by the Amara.org community") on pure noise.

## Pedagogy: TaRL-style deterministic state machine, not vibes

`diagnostic_flow.py` defines 19 numeracy + 8 literacy diagnostic items with regex answer-matchers, each carrying an explicit `fail_module/week/lesson/tarl_level` — a first wrong answer stops the ladder and places the child at that exact prerequisite level. `learning_state.py` (1,193 lines) tracks correct/wrong streaks, a 0–3 scaffold depth, and picks from hand-authored **skill-specific scaffold ladders** (`SCAFFOLD_LADDERS`) — e.g. for multiplication, level 1 repairs with "translate back to equal groups," level 2 drops to fingers-and-counting, level 3 removes the word "times" entirely and rebuilds from one group. `curriculum_path.py` maps the full 96-lesson numeracy sequence (6 modules, week/lesson titles from "Counting 1 to 10" through "Final Challenge: Lagos Market Master") and a 6-module literacy sequence (phonemic awareness → oral vocab → listening comprehension → oral grammar → advanced phonemic awareness → print bridge), each lesson pre-tagged with an STT context hint. `curriculum_mastery.py` encodes the actual thresholds from `FOUNDATIONAL_COURSES_PLAN`: 0.85 held for 3 sessions to advance, 0.60–0.84 reinforce, below that remediate, plus per-lesson n-of-m assessment gates (Module 1 check = 7/10, Module 4 = 12/15, etc.) — not arbitrary numbers, they're the ones from your curriculum docs.

## Child safety

`guardrails.py` is a Python mirror of `curriculum-app/lib/voice/guardrails.ts` — regex-pattern layer with Nigerian-Pidgin-aware crisis phrases ("I no wan live," "make I just die," "papa dey beat my mama"), classified into crisis (self-harm/abuse/emergency → escalate with Cece Yara helpline number), inappropriate (deflect), boundary (grooming/PII/off-platform), and jailbreak/prompt-extraction categories. Runs on **every turn** on every LLM backend, because Cerebras/Groq/Ollama have weak-to-no built-in safety alignment — the guard is the actual safety constant, not the model. A crisis triggers `raise_safeguarding_incident` → `emergency_alert.py`, which fans out to Africa's Talking SMS, Twilio SMS fallback, a webhook, and a Google Calendar event, all fail-soft (an alert channel failing never blocks the child-facing turn). On the Gemini Live native-audio lane specifically, the guard runs on the *input* transcript only (native audio can't be output-filtered before the child hears it), and on trip it drains the playback queue, synthesizes the fixed crisis response through Sabi's own TTS (never paraphrased by the model), then injects a "stay quiet, let them lead" cue.

## Identity, memory, and evidence

`memory.py` (1,943 lines) is Supabase-backed. Phone-number identity resolution went through several iterations documented in your memory files — currently `SABI_ONE_PROFILE_PER_PHONE=true` by default (one learner row per calling number; the earlier shared-phone-by-spoken-name design still exists in the code but is off by default). `pilot_evidence.py`, `launch_gates.py`, and `teacher_notes.py` build the pilot-readiness reporting layer: `launch_gates.py` computes pass/watch/blocked status across baseline-capture, offline-replay, isolated-route, adult-canary, child-canary, and the full 10-child pre-pilot gate, gating on real evidence (consented children, movement in TaRL level, RCT-readiness counts) rather than a hardcoded date. `teacher_notes.py` runs one small LLM call after every substantive session to write a qualitative note (strengths/struggles/engagement/misconceptions) with a deterministic heuristic fallback if no provider is configured.

## Admin surface

`admin_review.py` (3,661 lines) serves an HTML console (`/admin/review`) for learner progress and call QA. `call_admin.py`/`feedback_admin.py` back the `/admin/calls`, `/admin/feedback`, `/admin/learners` JSON endpoints — full per-turn audio playback, STT-correction workflow with an explicit separate training-consent checkbox, and board-triage review-status (reviewed/follow-up/safety-escalation).

## The rest

`curriculum-app` also holds the RAG retrieval layer (`lib/rag/`), Cambridge-Grade-4 and foundational-literacy/numeracy content modules, standards crosswalks, the Notion-backed advisor-board dashboard, and Supabase Auth. `pilot/` holds the operational scaffolding: `SABI_SYSTEM_DESIGN_2026-06-29.md`, safeguarding/legal (DPIA, child protection policy, consent forms, an Anthropic minor-serving request), and testing docs (red-team plan, 100-fake-child harness, 5-adult-tester plan).

Here's the full picture, combining the Lagos PPP Manual I just pulled, TaRL Africa/EKOEXCEL's actual track record, and general NGO-to-government proposal practice.

## Two entirely different pathways — and EKOEXCEL took the informal one

The first thing the research makes clear: **EKOEXCEL was never a procurement.** NewGlobe didn't submit a proposal into a tender process — it became LASUBEB's *technical partner* under Governor Sanwo-Olu's THEMES agenda (2019), a political initiative, not a procurement one. TaRL Africa's national scale-ups (Botswana, Zambia, Côte d'Ivoire) follow the identical shape: a **Minister's letter of support → a Memorandum of Understanding**, not a competitive bid. This is the dominant pattern for how structured-pedagogy interventions actually enter African basic-education systems — relationship and evidence first, formal contract second.

The second pathway is the **formal PPP/procurement route** — the one governed by Lagos's actual PPP Manual (2022), which I read in full. This is built for capital-intensive infrastructure (roads, water, power) with 10–30 year concessions, Special Purpose Vehicles, and viability-gap funding — not really the shape of a $100K–$500K literacy/numeracy pilot. But it's the *only* channel with a formally defined **unsolicited proposal** process, and Lagos explicitly carves out an exception for it: unsolicited proposals are "the exception rather than the rule, limited mainly to projects that demonstrate genuine innovation and/or use of proprietary technology" — which is exactly the lane voice-AI-on-a-feature-phone sits in.

## How the formal unsolicited-proposal process actually runs (Lagos PPP Manual §8.6)

1. **Submit to the MDA or the Office of PPP** as a "suo-motu" proposal — must include CAC registration, valid tax clearance certificate, and an authorized representative's contact details.
2. The submission package must contain: **(1)** project specs, scale, scope, technical/financial/commercial detail; **(2)** your organization's technical/managerial/financial capability; **(3)** proposed risk-sharing principles and an implementation plan; **(4)** a **feasibility study** (market + technical + financial, including a strategic-needs assessment and legal framework); **(5)** the estimated cost of that feasibility study, capped at **2.5% of project value**.
3. The MDA reviews against a 7-point checklist (not already a listed priority project; no direct guarantee/subsidy required — preferred but not disqualifying; in the public interest and matches MDA scope; risk-sharing conforms to the MDA's framework; meets minimum PPP project-cost threshold; financially viable; suitable for PPP) and forwards its recommendation to the Office of PPP within **30 working days**.
4. Office of PPP forwards to the state's Executive Council (SEC) for a retain/reject decision. If retained, the Office of PPP commissions the feasibility study; **the proponent does not get an automatic advantage** — Lagos does not use a bonus/Swiss-challenge system, it moves straight into a **competitive tender** where your organization is just one of the bidders (reimbursed for the feasibility study only if you lose).
5. If it clears that gate, the actual proposal document follows the **Outline Business Case** structure: Executive Summary → Project Background → Strategic Needs/Demand Assessment → Service Standards (Output & Services) → Market Assessment → Technical Feasibility → Financial Feasibility → Environmental Impact → Legal Framework → Stakeholder Consultation Findings → Feasibility Conclusions, then a Part B on Structuring: Risk Assessment → Key Commercial Principles & Payment Mechanisms → Public Sector Comparator → Options Analysis/Value-for-Money → Private-Sector Evaluation Criteria → Implementation Plan → Resource Requirements → Conclusions.

That's the skeleton every serious government-facing proposal in this space borrows from, whether or not you're actually going through a full PPP — because it's the vocabulary the government side is trained to evaluate against (Value-for-Money, Public Sector Comparator, risk allocation, output specifications rather than input mandates).

## The realistic anatomy of a technical-partner / pilot proposal (the EKOEXCEL-style document, not the PPP one)

Cross-referencing standard NGO-to-government proposal practice (executive summary → problem statement → objectives/theory-of-change → methodology → M&E plan → budget → sustainability → organizational credibility) against what actually worked for EKOEXCEL, TaRL Africa, ConnectEd, and Rori — a realistic document has these components, roughly in this order:

1. **The evidence hook, up front** — not a general problem statement, but *your own* pre/post data. Every "what winners did" case in your own Track D notes (EKOEXCEL's 5-year evidence, ConnectEd's J-PAL evaluation, Rori's Oxford study, Viamo's MNO-verified reach) led with completed, independently-verified results, not a pitch for future ones. Governments fund what's already working somewhere, at small scale, with a credible evaluator's name attached.
2. **Alignment to the government's own stated agenda** — EKOEXCEL was framed as executing THEMES, not as a new idea NewGlobe brought. A Sabi proposal to LASUBEB needs to name-check whatever Lagos's current basic-education priority document is (successor to THEMES, the state education policy) explicitly.
3. **Theory of change / logframe** — inputs → activities → outputs → outcomes → impact, with indicators and means of verification at each level. This is the USAID/UNICEF-standard structure and it's what a PPP's "Service Standard – Output and Services" section is really asking for in different language: what you deliver, what changes because of it, how anyone will know.
4. **Cost per beneficiary, explicitly benchmarked against the incumbent** — your own Track A doc already does this ($2–5/pupil/year vs EKOEXCEL's ~$24); that comparison *is* the Value-for-Money analysis a PPP evaluator is trained to look for, just framed for a complement rather than a competitor.
5. **Risk allocation and safeguarding** — child-data protection (NDPA 2023), consent infrastructure, emergency escalation. This is the PPP manual's "Risk Assessment" section in miniature, and it's also exactly what your own memory flags as landmine #2 (NDPA) and landmine #3 (a child cohort without guardian-consent infrastructure kills applications).
6. **Implementation plan with a ramp, not a single leap** — every comparable winner scaled in stages (pilot LGAs → evaluation → statewide), matching your own Track E user-ramp (10 → 100 → 300 → 5,000 → 50,000 → 2.4M).
7. **Organizational capability and legal standing** — CAC registration, tax clearance, named local implementation lead (this is where Dr. Sonia's role as Regional Coordinator does real work — it's the "authorized representative" and local-legitimacy requirement both pathways demand).
8. **Independent measurement partner named in the proposal itself** — TEP/LEARNigeria or a university, not self-reported results. Landmine #16/#17 in your own memory (no published RCT-style data; claiming NERDC-approved before formal review) are exactly what an evaluator on either pathway is trained to catch and reject on.
9. **Sustainability / exit or scale plan** — how the government eventually takes over cost or the model becomes self-sustaining; the NGO-proposal literature treats this as make-or-break for credibility, and it maps directly onto the PPP manual's exit/hand-back phase.

## Where this leaves Sabi specifically

Your own `GOAL_2_LAGOS_STATE_STEPS.md` already has the right instinct — TEP curriculum-review packet, LASUBEB pilot proposal at $100K–$500K for 12 months across 5–10 LGAs — but it's currently a bullet list, not a document. ## Read the request first

Calibrate treatment, not whether to design. A doc deserves the same craft as a landing page - what changes is the treatment that craft is delivered in. Format is not part of this read: author HTML, and publish Markdown only when a loaded skill explicitly instructs it - a Markdown publish keeps its filename as its title and takes almost none of the craft below, and is never a way to save time.

Many requests call for a more utilitarian treatment: a plan, a memo, a demo. Make it polished: include real typographic hierarchy, considered spacing, and a proper palette, but avoid over-designing. Most pages do not need a flashy, gigantic hero. Keep flourishes tasteful and limited.

Some requests call for an editorial treatment: a landing page, a game, an app or tool they'll keep or share.

When unsure: a well-composed page is never the wrong answer; an over-designed visual identity sometimes is.

Fundamentals below apply to everything. The editorial process after that runs only when the read above says so.

## Fundamentals for every artifact

**Honor what's already there** Look for an existing design system first - CLAUDE.md, a tokens or theme file, existing component styles. When one exists, apply it; everything below fills gaps and never overrides. Precedence is always: the user's own words, then the project's existing system, then your choices.

**Ground it in the subject.** If the subject isn't already clear, pin it: one concrete subject, its audience, and the page's single job. The subject's own world - its materials, instruments, vernacular - is where distinctive choices come from. Build with real content throughout, never lorem.

**Pair typefaces** Typography carries the page even when the page isn't about typography. Google Fonts is the one font host the Artifact CSP admits - link it directly (`<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=...&display=swap">`); a face from anywhere else must be inlined as a @font-face data URI or it falls back silently. Either way, declare a real fallback stack. Keep running text near 65 characters wide; set a type scale and stay on it; give headings `text-wrap: balance`, body text room to breathe, and uppercase labels a touch of letter-spacing.

**Choose neutrals, don't default to them.** A pure mid-grey reads as unconsidered; a grey with a slight hue bias toward the page's accent reads as chosen. Pure white and near-black are fine grounds when they suit the subject - the point is that the neutral was picked, not inherited.

**Design both themes.** The page renders in the viewer's theme, and the viewer has three states, not two: an explicit choice stamps `data-theme="dark"` / `data-theme="light"` on the root element, and the default "system" setting stamps *nothing* - most viewers see the un-stamped document, where only `prefers-color-scheme` separates light from dark. Structure the CSS token-level for all three: the bare `:root` block defines the complete light palette (for a deliberately dark-first design, swap light and dark consistently through this whole pattern); `@media (prefers-color-scheme: dark)` redefines only the tokens, guarded as `:root:not([data-theme="light"])` so an explicit light choice beats a dark OS; `:root[data-theme="dark"]` redefines them again so the toggle also wins in the other direction. Style components through the tokens, never directly inside a media or `[data-theme]` block - a color whose only definition sits behind `[data-theme]` never applies in the un-stamped state, and the page renders one theme's text on the other theme's ground. Two more rules keep each theme resolving as a set: the artifact composites over a ground the viewer paints in *its* theme, so `body` must set an explicit `background` from a token - a transparent body silently borrows the host's ground; and every element that sets a color takes it from the same token set as the surface behind it, never a literal that only works in one theme. Before publishing, scan the stylesheet for any color declared only inside a media or `[data-theme]` block - that is the classic unreadable-artifact bug. Give the second theme the same care as the first - don't naively invert; keep contrast legible and the accent working on both grounds. A design that deliberately commits to one visual world (a neon arcade screen, a letterpress invitation) may stay single-theme - then skip the media query and stamps entirely but still paint the background and every color explicitly, so the page holds on either host ground; make it a choice, not an omission.

**Let layout do the spacing.** Lay out sibling groups with flex or grid and `gap`, not per-element margins that silently collapse or double. Wide content - tables, code, diagrams - gets `overflow-x: auto` on its own container so the page body never scrolls sideways. Reach for `font-variant-numeric: tabular-nums` wherever digits line up in columns.

**Avoid AI-generated design** AI-generated design currently clusters around a few looks: warm cream (#F4F1EA) with a serif display and terracotta accent; near-black with a lone acid-green or vermilion pop; broadsheet hairline rules with dense columns; a purple-to-blue gradient hero on white; Inter or Space Grotesk as the "safe" face; emoji as section markers; everything centered; `rounded-lg` everywhere; accent bar/rail on rounded cards. Where the user pins down a visual direction, follow it exactly - their words always win, including when they ask for one of these looks. Where nothing is specified, don't spend that freedom on one of these defaults.

**Build cleanly** Be cognizant of overlapping elements, cascade collisions, silent font fallbacks; visual bugs hide in the gap between source and output. Close every non-void element, double-quote attributes, give keyboard focus a visible state, respect `prefers-reduced-motion`. For generative or decorative graphics, reach for Canvas or WebGL rather than hand-authoring long SVG path data.

**CSS rules** When writing the CSS, watch your selector specificities. It is easy to generate classes that cancel each other out - a type-based selector like `.section` fighting an element-based one like `.cta` over padding and margins between sections. Structure the cascade so it doesn't silently undo your spacing.

**Writing the copy** Words are design material, not decoration. Write from the user's side of the screen - name things by what people recognize, not how the system is built (a person manages *notifications*, not *webhook config*). Active voice; a control says exactly what happens ("Publish", then a toast that says "Published"). Errors explain what went wrong and how to fix it - no apologies, no vagueness. Specific beats clever.

**Name the page like a product, not a caption.** The `<title>` is the artifact's name in the gallery and the browser tab, and it sets the reader's first impression of care. Give the page a real name: a short noun phrase, typically two to four words, specific to the subject - or, for a page that exists to answer one question, that question itself, which is then the page's name. Stop at the name - a title that carries its own explainer after a dash or colon reads as generated filler. The name must also identify the page among many: in the gallery it sits beside dozens of other artifacts, and a generic category label that could sit on any of them fails as a name just as surely as an appended explainer. When a candidate title pairs the name with a generic word - a greeting, a category, a page-type label - the name is the half to keep; a trim that drops the identity and keeps the generic word produces exactly the title that could sit on any page. And the rule removes explainers, it does not impose brevity: a multi-word title that already reads as one specific name is finished, and shortening it further only makes it generic. The one-sentence publish `description` is where the explanation belongs; the gallery shows it right under the title.

**Structure is information** Structural devices, numbering, eyebrows, dividers, labels, should encode something true about the content, not decorate it. Many generic designs use numbered markers (01 / 02 / 03), but that's only appropriate if the content actually is a sequence - like a real process or a typed timeline where order carries information the reader needs. Question if choices like numbered markers actually make sense before incorporating them.

**When it's a UI, not a document** A dashboard or tool is scanned and operated, not read top-to-bottom, so the craft shifts from typography to information design. Surface the summary before the detail; encode state in form as well as number - a pill, a chip, a severity stripe - so what needs attention reads at a glance. Semantic color (good / warning / critical) is separate from the accent hue and doesn't count as your accent. Give sparklines and charts the same care as type: an area fill, a faint grid, an emphasized endpoint. What's interactive should look interactive.



## Process

Before writing code, sketch a short design plan - a compact token system with color, type, and layout:
- **Color**: describe the palette as 4-6 named hex values.
- **Type**: typefaces for 2+ roles - a characterful display face used with restraint, a complementary body face, and a utility face for captions or data if needed.
- **Layout**: a layout concept in one or two sentences.

Then build, following the plan and deriving every color and type decision from it.

## When the request is editorial

The stance shifts: the client has already rejected proposals that felt templated, and is paying for a distinctive point of view. Make opinionated calls, and take one real aesthetic risk where it serves the work.

Review the design plan against the subject before building: if any part of it reads like the generic default you would produce for any similar page, revise that part, and note what you changed and why. Only after you've confirmed the plan's uniqueness do you write the code, following the revised plan exactly.

**Principles**

- The hero is a thesis: open with the most characteristic thing in the subject's world - headline, image, live demo, interactive moment.
- Typography carries the personality of the page. Pair the display and body faces deliberately, not the same families you would reach for on any other project, and set a clear type scale with intentional weights, widths, and spacing. Make the type treatment itself a memorable part of the design, not a neutral delivery vehicle for the content.
- Leverage motion deliberately. Think about where and if animation can serve the subject: a page-load sequence, a scroll-triggered reveal, hover micro-interactions, ambient atmosphere. An orchestrated moment usually lands harder than scattered effects; choose what the direction calls for. However, sometimes less is more, and extra animation contributes to the feeling that the design is AI-generated.
- Match complexity to the vision. Maximalist directions need elaborate execution; minimal directions need precision in spacing, type, and detail. Elegance is executing the chosen vision well.
- Spend your boldness in one place; keep everything around it quiet. If the accent fights the ground, shift it toward analogous or drop saturation rather than replacing it.
