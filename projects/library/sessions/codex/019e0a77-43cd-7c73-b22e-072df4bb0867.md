## Codex · 2026-05-09T02:06:24.706Z · final_answer

**Biggest Gaps**

- The biggest blocker is the inbox model, not the LLM. `search_inbox` only inspects the newest `limit * 2` first-chunk rows, so “long tail recovery” is mostly not real, and it treats a thread as “replied” if you ever sent anything in it, not if the latest message still needs you. That means important older items and active back-and-forth threads can disappear from the agent’s view. See [email-tools.ts](/Users/naomiivie/cortex/voice-email/lib/agent/tools/email-tools.ts:39) and [email-tools.ts](/Users/naomiivie/cortex/voice-email/lib/agent/tools/email-tools.ts:123).

- The app also reasons over fragments, not full threads. `get_email_body` and `draft_reply` fetch by `source_id` with `.single()`, while the same table clearly stores chunked emails. So long emails can fail outright or be drafted from incomplete context, and there is still no real “give me the whole thread + latest action items” tool. See [email-tools.ts](/Users/naomiivie/cortex/voice-email/lib/agent/tools/email-tools.ts:169) and [email-tools.ts](/Users/naomiivie/cortex/voice-email/lib/agent/tools/email-tools.ts:281).

- Right now this has session memory, not agent memory. The conversation and scratch state live in browser refs and reset when the session restarts; the only durable personalization is a read-only `cortex_profiles.profile_text`. That’s a smart voice session, but not yet a persistent assistant that learns, remembers, and follows up. See [voice-email-client.tsx](/Users/naomiivie/cortex/voice-email/app/voice-email-client.tsx:65) and [assistant-agent.ts](/Users/naomiivie/cortex/voice-email/lib/agent/assistant-agent.ts:136).

- It’s still on-demand, not proactive. The agent only exists when the orb triggers `/api/assistant/turn`, and the digest is just a GET route. There’s no worker, scheduler, or background loop to watch inbox changes, resurface overdue promises, or prep a queue before you arrive. See [voice-email-client.tsx](/Users/naomiivie/cortex/voice-email/app/voice-email-client.tsx:83) and [daily digest route](/Users/naomiivie/cortex/voice-email/app/api/digest/daily/route.ts:40).

- The action surface is too narrow for “highly intelligent.” The assistant can search, read, draft, send, archive, and wrap. That’s useful, but it can’t schedule, snooze, track commitments, update memory, coordinate across tools, or reason over broader life context. So even a strong model is capped by weak tools. See [assistant-agent.ts](/Users/naomiivie/cortex/voice-email/lib/agent/assistant-agent.ts:107).

- Voice quality is not the main intelligence blocker, but it is still below the vision. STT is browser `SpeechRecognition`, and TTS is ElevenLabs-or-browser fallback, not your own durable Sabi-grade voice stack. See [use-voice.ts](/Users/naomiivie/cortex/voice-email/components/use-voice.ts:56), [use-tts.ts](/Users/naomiivie/cortex/voice-email/components/use-tts.ts:163), and [tts route](/Users/naomiivie/cortex/voice-email/app/api/tts/route.ts:23).

Production build is fine: `npm run build` succeeded. Small engineering debt note: `npm run lint` is stale because [package.json](/Users/naomiivie/cortex/voice-email/package.json:5) still uses `next lint` on Next 16.

**What I’d Do Next**

1. Fix the email state model first: true thread reconstruction, latest-message reply status, full-body assembly across chunks, and a real “current thread context” tool.
2. Add durable agent memory + background jobs: persist session outcomes, skipped items, promises, and daily resurfacing logic.
3. Expand tools before touching model polish: calendar, snooze/follow-up, task memory, recipient preferences, and stronger approval/idempotency around sends.

Short version: what’s standing between this and a genuinely smart agent is not “better AI” first. It’s better state, better retrieval, better tools, and a persistent runtime. If you want, I’d start with the inbox/thread model, because everything else depends on that.
