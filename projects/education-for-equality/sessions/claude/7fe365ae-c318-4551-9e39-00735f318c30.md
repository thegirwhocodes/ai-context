# Building Production Agents — A Walkthrough

I'll teach you the way the topic actually clicks: build up from the simplest possible thing that's still an agent, then add one production concern at a time. Every layer earns its complexity. By the end you'll know exactly what Ed.it needs and what would be over-engineering.

---

## 1. An agent is a while loop. That's it.

Strip away every framework and every buzzword and what you have is this:

```python
def run_agent(user_goal, tools, llm, max_steps=30):
    messages = [{"role": "user", "content": user_goal}]
    for step in range(max_steps):
        response = llm.call(messages=messages, tools=tools)
        messages.append(response.message)

        if not response.tool_calls:
            return response.text          # agent says it's done

        tool_results = []
        for call in response.tool_calls:
            result = TOOL_REGISTRY[call.name](**call.arguments)
            tool_results.append({"id": call.id, "content": result})
        messages.append({"role": "tool", "content": tool_results})

    raise StepLimitExceeded()
```

That's the entire pattern: **perceive** (messages history) → **reason** (LLM call) → **act** (tool calls) → **observe** (tool results appended) → **repeat**. ReAct, Reflexion, Plan-and-Execute, the Claude Agent SDK, LangGraph — all are this loop with extra clothes on. The clothes matter, but the loop is what an agent *is*.

**The mental model that locks it in:** the LLM doesn't "do" anything. It emits text or a structured `tool_use` block. *You* (the harness) execute the tool and feed the result back. The agent is the dialogue, not the model.

---

## 2. Tools are the actual product

Here is the most underrated truth in agent-building:

> The model picks tools based almost entirely on the name, description, and parameter schema. It never sees your implementation.

This means **writing a tool is writing a prompt**. The Python function happens to also run, but the model reads the JSONSchema. Internalize this and your agent quality jumps.

### Bad tool
```python
{
  "name": "ffmpeg_run",
  "description": "Runs an ffmpeg command.",
  "parameters": {"args": {"type": "string"}}
}
```
You've outsourced all the reasoning to the LLM. It will synthesize a correct ffmpeg invocation maybe 80% of the time, fail silently on the other 20%, and you have no recourse.

### Good tool
```python
{
  "name": "trim_clip",
  "description": (
    "Cuts a segment from a source video between two timestamps and writes "
    "a new file. Use when the user wants to shorten, extract a highlight, "
    "or isolate a moment. Stream-copies (no re-encode) by default. "
    "Returns the output path and actual duration."
  ),
  "parameters": {
    "source_path": {"type": "string", "description": "Absolute path to input video."},
    "start_sec":   {"type": "number", "description": "Start time in seconds."},
    "end_sec":     {"type": "number", "description": "End time, must be > start_sec."},
    "output_dir":  {"type": "string", "description": "Existing directory for output."},
    "reencode":    {"type": "string", "enum": ["never","if_needed","always"], "default": "if_needed"}
  },
  "required": ["source_path", "start_sec", "end_sec", "output_dir"]
}
```

Rules to internalize:

1. **Name = verb + object.** `trim_clip`, `list_timeline_markers`, `describe_video`. Not `handler`, not `do_thing`.
2. **Description answers "when should I call this?"** Not "how does it work internally?"
3. **Every parameter gets its own description.** The schema is a contract; treat it like one.
4. **Enums everywhere a value set is known.** `"h264" | "h265" | "prores"`. The model picks from a list 10x better than it types a string.
5. **One responsibility per tool.** `trim_clip` trims. `concat_clips` concats. Don't build `video_op` god-tools.
6. **Flat params over nested.** The model handles `output_dir` + `output_filename` better than `{output: {dir, filename}}`.

### Return shapes: structured JSON, always

```python
# Good
{"status": "ok", "output_path": "/.../clip_03_trim.mp4", "duration_sec": 4.21}

# Good error
{"status": "error", "code": "file_not_found",
 "message": "Source file /clips/shot99.mp4 does not exist.",
 "hint": "Call list_media_files first to see available clips."}
```

**The error format is the most leverage you'll find anywhere.** A stack trace teaches the model nothing. A structured error with a `hint` field tells it what to try next. It will read your hint and self-correct on the next turn. Treat tool errors as prompts to your agent about what to do.

---

## 3. The harness — what you don't have to write yourself

In 2023 everyone was writing ReAct-style `Thought:/Action:/Observation:` parsers with regex. In 2026 that's a regression. Frontier models (Claude, GPT-5, Gemini 2.5) emit structured `tool_use` blocks natively, and SDKs like the Claude Agent SDK or OpenAI Agents SDK handle the loop for you.

What the harness gives you for free:

- **Structured tool-call parsing** — no regex.
- **Streaming partial JSON** — tool arguments arrive token-by-token; you can render "Claude is typing `trim_clip(start=12.5, end=...)`" before the call fires.
- **Schema-validation retries** — malformed JSON gets sent back automatically and the model self-corrects.
- **Interleaved thinking + tool use** — the model thinks, calls a tool, thinks *again after the result*, calls another. Biggest quality jump for multi-step agents since ReAct itself.
- **Prompt caching** on system prompt + tool definitions (huge — see §6).
- **Streaming interrupts** — user cancels mid-generation cleanly.

Here is what Ed.it's main loop looks like with the Claude Agent SDK:

```python
from claude_agent_sdk import ClaudeSDKClient, ClaudeAgentOptions

async with ClaudeSDKClient(
    options=ClaudeAgentOptions(
        system_prompt=EDIT_SYSTEM_PROMPT,
        allowed_tools=["trim_clip", "concat_clips", "apply_lut",
                       "describe_video", "burn_captions", "complete"],
        max_turns=40,
        extra_args={"thinking": {"type": "enabled", "budget_tokens": 8000}},
        model="claude-sonnet-4-5",
    )
) as client:
    await client.query("Cut this podcast down to a 60-second reel")
    async for msg in client.receive_response():
        render_to_ui(msg)
```

That's the agent. Ten lines. Everything else is the tools you give it.

**Anti-pattern:** writing your own ReAct loop in 2026. You're reinventing a bicycle that now has gears.

## 4. Stop conditions — how to not bankrupt yourself

Every agent needs three stop conditions running at once. Skip any of them and you'll regret it.

```python
options = ClaudeAgentOptions(
    max_turns=30,              # hard ceiling — agent can't loop forever
    cost_budget_usd=3.00,      # hard ceiling — single session can't exceed $3
    # natural end_turn is automatic — agent emits no tool_use, we return
)
```

- **`max_turns`** — kills runaway loops. Set it 2-3x your expected worst case, not 10x.
- **Cost budget** — tracks `input_tokens + output_tokens` cumulatively, multiplies by model rates, aborts on exceed. Non-negotiable. Without it a stuck agent is an unbounded API bill.
- **Natural `end_turn`** — the model stops emitting `tool_use`. The default, correct 80% of the time.
- **(Optional) `complete()` tool** — a sentinel tool the model calls when it's done, with a structured `summary` argument. Forces it to commit to "I'm done, here's what I did." Recommended for user-facing agents.

When a budget hits, **don't crash** — tell the model "budget exhausted, summarize what you did and hand back to the user." Friendlier than a silent abort and lets the user re-scope.

### Loop detection

The other failure mode is the agent calling the same tool with the same args three times. Detect it deterministically:

```python
def detect_loop(messages, window=3):
    recent_calls = [
        (m.tool_name, json.dumps(m.arguments, sort_keys=True))
        for m in messages[-window*2:]
        if m.type == "tool_use"
    ]
    return len(set(recent_calls)) == 1 and len(recent_calls) == window

if detect_loop(messages):
    inject_user_message(
        "You've called this tool with these exact arguments 3 times. "
        "Try a different approach or call complete()."
    )
```

That single check fixes 80% of "the agent froze" reports.

## 5. Memory and state

There are five tiers of agent memory. Don't build all of them. Build what your product needs and stop.

| Tier | What it holds | Where it lives |
|---|---|---|
| **Short-term** | Current conversation | LLM context window |
| **Working** | Active plan, tool outputs | Scratchpad in prompt |
| **Episodic** | "Tuesday you rejected the yellow caption" | Vector DB + timestamps |
| **Semantic** | "Naomi's preferred LUT is `Naomi_Worship_Warm`" | SQLite key-value |
| **Procedural** | "When mode=worship, captions = Cormorant 45px" | SQLite rules table |

For Ed.it v1, you need three of these:

1. **Conversation history** (free — it's the messages array).
2. **Always-loaded core memory** — a ~500-2000 token block pinned to the system prompt: user's name, current project, top 5 preferences. Cheap, massive quality win.
3. **Tool-accessible long-term memory** — `memory.recall(query)` and `memory.write(fact)` as tools. The model decides when to remember.

The architecture that won in 2026 is **MemGPT/Letta-style**: agent manages its own memory via tools, rather than you auto-RAG-injecting on every turn (which pollutes context unpredictably).

```python
# Memory as tools — the cleanest pattern
{
  "name": "memory_recall",
  "description": "Search past sessions and learned preferences for relevant context. Returns up to k snippets.",
  "parameters": {"query": {"type": "string"}, "k": {"type": "integer", "default": 5}}
}

{
  "name": "memory_write",
  "description": "Persist a durable fact about the user or project. Use only for stable preferences ('always uses warm LUT'), not transient state.",
  "parameters": {"kind": {"type": "string", "enum": ["preference", "fact", "lesson"]},
                 "text": {"type": "string"}}
}
```

### Storage

For a single-user desktop app: **one SQLite file with sqlite-vec loaded**. That's it. Vector + structured data in one file. Backup = copy one file. The schema in [03_memory_systems.md](Social%20Media/Ed.it/docs/03_memory_systems.md) is exactly what you want — `user_profile`, `preferences` (with `supersedes`/`superseded_by` for contradiction handling), `events`, and a `vec0` virtual table.

Embedding model: **BGE-small-en-v1.5** (384-dim, 130MB, CPU-fast, no API calls). Bundle it via ONNX Runtime. Local, private, offline.

### Memory write policy

This is where most people screw up. Don't write every turn. You'll end up with 10k noisy entries that poison retrieval. Three legitimate write triggers:

1. **Explicit** — user says "remember that," "from now on," "I prefer X." Always write.
2. **Salience-judged** — after each turn, a cheap Haiku call asks "is this worth remembering?" returning JSON `{remember: bool, type, text}`. Threshold ~0.7.
3. **Behavioral** — deterministic: user accepts/rejects, applies a LUT, starts a project. Logged as structured events.

Aim for **less than 1 memory write per 10 user turns.**

## 6. Prompt caching — the biggest cost lever you have

If you do nothing else from this guide, do this. Prompt caching is a 5-10x cost reduction on any agent with a stable prefix.

The shape: Ed.it's system prompt + tool catalog + few-shot examples is easily 10-15k tokens. Without caching you pay for them on every turn. With caching, ~10% of that on turns 2+.

```python
SYSTEM = [
    {"type": "text", "text": ED_IT_SYSTEM_PROMPT},      # ~3k tokens, stable
    {"type": "text", "text": FEW_SHOT_EXAMPLES,         # ~5k tokens, stable
     "cache_control": {"type": "ephemeral"}}            # ← cache breakpoint 1
]

resp = client.messages.create(
    model="claude-sonnet-4-5",
    system=SYSTEM,
    tools=TOOLS,                                        # tools cached as part of prefix
    messages=[
        *prior_turns[:-1],
        {**prior_turns[-1],
         "cache_control": {"type": "ephemeral"}},       # ← cache breakpoint 2
        {"role": "user", "content": new_user_message},  # ← outside cache
    ],
)
print(f"Cache read: {resp.usage.cache_read_input_tokens}")
print(f"Cache hit rate: {resp.usage.cache_read_input_tokens / resp.usage.input_tokens}")
```

Order matters: **most stable first** (system → tools → examples → cached conversation → fresh user turn).

The gotcha: **any change to any byte before a breakpoint busts the cache.** Don't interpolate `datetime.now()` into your system prompt. Don't reorder tools. Don't add a stray newline. If your hit rate is 0%, diff the raw request payload across two consecutive turns. Target >80% hit rate on turns 2+.

## 7. Model routing — don't use Opus for everything

Cost-quality math (Anthropic Jan 2026 list prices, per million tokens):

- **Haiku 4.5** — ~$1 / $5
- **Sonnet 4.5** — ~$3 / $15
- **Opus 4.7** — ~$15 / $75

A 20-turn editing session on Opus-only costs **5x** the Sonnet version for maybe a 10-15% quality lift on non-planning turns. Route by **decision value**, not task type:

- **Haiku** → classifiers, salience judges, tool-argument formatting, "is this clip talking-head or B-roll?"
- **Sonnet** → the default worker, 90% of turns, tool-calling and plan execution.
- **Opus** → planning, judging variations, high-leverage one-shot decisions. Few turns, big impact.

Make this a per-call-site decision in code, not a config layer. You want to read a call and see what it costs.

## 8. Streaming UX is not optional

There's a perceived-latency cliff at ~3 seconds. Under 3s users wait. Over 3s they think the app froze. Agent turns with tool use routinely take 15-60s. Streaming is what keeps the UI alive.

Stream four things:

1. **Text deltas** as the model generates them.
2. **Tool-call deltas** — render the tool name the moment it's chosen, then the arguments as they stream.
3. **Thinking blocks** (Claude extended thinking) — render dimmed, collapsible.
4. **Backend status events** — "Trimming B-roll clip 7…" / "Gemini analyzing 240MB clip…" / "FFmpeg 37% done."

The narration pattern is critical:

```python
# Bad UX
"[spinner for 45 seconds]"

# Good UX
"Watching the clip…
 → Detected low-energy section at 00:12–00:17
 → Trimming
 → Applying Warm LUT
 → Burning captions
 → Done. ✓"
```

Every action narrated. This is why Cursor and Claude Code feel "alive" — visible reasoning + visible tool use builds trust. Users distrust an agent they can't see; they trust one that talks to them while it works.

```python
async for event in stream:
    if event.type == "content_block_start" and event.content_block.type == "tool_use":
        await ui.emit("tool_start", {
            "name": event.content_block.name,
            "narration": HUMAN_NARRATIONS[event.content_block.name]
        })
    elif event.type == "content_block_delta":
        if event.delta.type == "text_delta":
            await ui.emit("text", {"delta": event.delta.text})
```

First-token latency is what users feel. If your backend buffers even 500ms before flushing, streaming feels broken. Disable Nagle, disable proxy buffering, `flush=True`.

## 9. Observability from day one

You cannot debug what you don't trace. Every tool call logs:

```python
{
  "tool_name": "trim_clip",
  "arguments": {"source_path": "...", "start_sec": 12.4, "end_sec": 18.1},
  "session_id": "sess_abc",
  "turn_id": 7,
  "started_at": "2026-05-22T16:33:01Z",
  "duration_ms": 1240,
  "status": "ok",
  "cost_usd": 0.0042,   # for tools that hit paid APIs
  "error_code": null
}
```

One line per call, structured JSON. Ship to local SQLite during dev; **Langfuse** (self-hosted, OpenTelemetry-native, open source) is my pick for staging/prod. Run it in a Docker container next to your app. No vendor lock-in, no sending creator footage to a third-party dashboard.

The killer feature this unlocks: **trace replay.** Given a recorded trace, replay it against a different prompt or model and see what changes. This is how you iterate on prompts without re-recording video test cases every time.

Sample 100% of errored turns, 100% of thumbs-downed turns, 10% of successful turns. Never log raw video frames — transcript and metadata only.

## 10. Safety: sandboxing and approval gates

Ed.it runs shell commands, touches the filesystem, talks to Resolve. The threat model is real. A malformed FFmpeg filter could corrupt media. A Resolve tool could blow away a project.

Three layers, non-optional:

**1. Sandboxed paths.** Every filesystem tool resolves paths against a project-root allowlist. Reject `../` traversal. Reject absolute paths outside the project unless explicitly allowed. Enforce in the *tool wrapper*, not in the prompt. The model will forget. The wrapper won't.

```python
def safe_path(path: str, project_root: str) -> str:
    resolved = Path(path).resolve()
    root = Path(project_root).resolve()
    if not resolved.is_relative_to(root):
        raise ToolError(
            code="path_outside_project",
            message=f"Path {resolved} is outside project root {root}.",
            hint="All file operations must stay inside the current project."
        )
    return str(resolved)
```

**2. Approval gates on destructive tools.** Tag tools with `destructive: true`. The Claude Agent SDK exposes a `canUseTool(toolName, args) => "allow" | "deny" | "ask_user"` hook. Ed.it's policy:

- `probe_*`, `list_*`, `describe_*` → allow.
- `trim_clip`, `concat_clips` → allow if output is inside the project; ask otherwise.
- `delete_clip`, `overwrite_project` → ask every time for the first few sessions, then let the user toggle "trust this tool."

**3. No `shell=True`.** Use `subprocess.run([...])` with argument lists, never strings. The model will sometimes try to inject shell metacharacters into a filename field; arg-list exec neutralizes it.

**4. Dry-run mode.** Every destructive tool takes an optional `dry_run: bool`. The agent can preview, surface to user, then re-call without it. Best HITL pattern there is.

## 11. Long-horizon: when your context fills up

Ed.it editing a 45-minute podcast hits dozens of tool calls and hundreds of thousands of tokens of intermediate output. Four strategies, in order of when to reach for them:

1. **Do nothing** (context < 100k). Sonnet's 200k is genuinely usable. Don't over-engineer.
2. **Compaction** (100k–800k). Summarize older turns into a "session summary" block, drop the raw turns. Claude Agent SDK has a `compact` hook. Use it.
3. **Offload to files** (any size). Don't keep state in messages — write it to disk. Gemini scene analysis → `/tmp/scene_analysis.json`. Claude reads via a `Read` tool when needed. This is how Claude Code handles repos 10x the context window. The model doesn't need everything in context; it needs the *ability to find* everything.
4. **Subagent with fresh context.** When a subtask needs 50k tokens of intermediate reasoning the parent doesn't need to see — e.g. "find the 5 best moments in this 2-hour video" — launch a subagent. It runs its own loop, returns just a JSON list of timestamps. Parent stays clean.

**Pick a hierarchy, not a single strategy.** Ed.it should use all four.

## 12. Evaluation — three layers

A pyramid, cheap-to-expensive:

**Unit** — every tool tested in isolation. `trim_clip(input, 0, 5.2)` produces a 5.2-second file. Pytest, deterministic, sub-second. Green CI gate on every PR.

**Trajectory** — given a brief, did the agent pick the right tools in the right order? Capture full traces (prompts, tool calls, results), assert invariants:

```python
def test_caption_workflow():
    trace = run_agent("Add captions to this clip")
    assert any(c.tool == "describe_video" for c in trace.tool_calls)
    assert any(c.tool == "burn_captions" for c in trace.tool_calls)
    # Captions must come AFTER analysis
    describe_idx = next(i for i,c in enumerate(trace.tool_calls) if c.tool == "describe_video")
    burn_idx = next(i for i,c in enumerate(trace.tool_calls) if c.tool == "burn_captions")
    assert describe_idx < burn_idx
```

**Outcome** — did the user's task actually get done? Use LLM-as-judge with a structured rubric. Critical: **validate the judge first.** Hand-rate 30 outputs yourself, check correlation with the judge. 60% agreement means noise. 85% means you can trust the judge for regression detection but not absolute quality.

For Ed.it: 20-task hand-written golden set + rubric scoring `{pacing, captions, color, music, brief_fidelity}` each 0-5.

```python
JUDGE_RUBRIC = {
    "pacing": "Cuts feel intentional; no dead air; no rushed transitions.",
    "captions": "Accurate to audio; readable on mobile; not overlapping faces.",
    "color_lut": "Requested look applied consistently; skin tones plausible.",
    "music": "Matches brief's mood; ducks under speech.",
    "brief_fidelity": "Duration within 10% of requested; all named elements present."
}
```

The judge grades a structured summary (transcript + Gemini keyframe descriptions + metadata), not the video directly. Cheaper, more deterministic, easier to debug.

CI gate: PR fails if golden-set pass rate drops or any judge dimension regresses >0.3 points.

## 13. Multi-agent: usually, no

The 2024 multi-agent craze produced brittle, hard-to-debug systems. By 2026, consensus swung back: **one smart agent > five dumb agents.** 80% of production agents are single-agent.

Multi-agent earns its keep in exactly four situations:

1. **Parallelism** — three variations generated at once (real wall-clock savings, user-visible).
2. **Fresh context per task** — research subagents that read 40 files, return a 500-token summary. The parent never sees the 80k of raw research. This is the killer use case for Claude Agent SDK's `Task` tool.
3. **Specialized prompts** that would conflict if stuffed into one agent ("safety reviewer" vs "creative generator").
4. **Different model tiers** for different roles.

For Ed.it, **the only multi-agent pattern in v1 is variation generation**:

```python
# Parent has footage analysis. Spawns 3 parallel Task planners.
plans = await asyncio.gather(
    parent.Task(subagent="planner_safe",    prompt=f"Plan a safe edit. Analysis: {analysis_path}"),
    parent.Task(subagent="planner_stretch", prompt=f"Plan a bolder edit (one unconventional choice). {analysis_path}"),
    parent.Task(subagent="planner_wild",    prompt=f"Plan a rule-breaking edit. {analysis_path}"),
)
# Then one judge turn (Opus) picks the winner against learned style memory.
winner = await parent.judge(plans, style_memory)
```

Three planners in parallel = wall-clock same as one. ~3.5x cost, worth it for iteration quality. Anything else (handoffs, debate, swarm) → don't.

## 16. The mental model to walk away with

If you forget every code snippet above, keep these:

1. **Agents are while loops.** Frameworks are convenience. Understand the loop and you can debug any of them.
2. **Tools are the product.** The model picks based on the schema, not the implementation. Write tools like you're writing prompts.
3. **Errors are prompts.** Return structured errors with hints. The model self-corrects from a good error message; it loops on a stack trace.
4. **Three stop conditions, always.** `max_turns`, cost budget, natural end. Skip any one and you'll regret it.
5. **Prompt caching is free money.** 5-10x cost reduction with stable-prefix discipline.
6. **Stream everything.** Users distrust agents they can't see. Narrate every action.
7. **One agent, good tools.** Multi-agent only when you have a *specific* reason (parallelism, fresh context, role separation).
8. **Observability from day one.** Traces > debugger. Replay > rerunning the user's task.
9. **Reversibility > approval.** Every destructive action should be undoable; only require approval when it isn't.
10. **Eval before iteration.** You cannot improve what you cannot measure. Golden set + judge rubric *before* prompt tuning.

Ed.it doesn't need to be different from any other production agent. It needs to be a single Claude Agent SDK session with 15-20 well-designed tools, three subagents for variation generation, one SQLite file for memory, Langfuse for traces, and prompt caching turned on. Everything else is over-engineering until proven otherwise.
