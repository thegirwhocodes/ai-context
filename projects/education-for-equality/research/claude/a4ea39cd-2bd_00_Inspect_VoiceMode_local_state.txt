# VoiceMode Mic Throttling Investigation — Findings

## Bottom line: the "throttle" is the **conch lock**, working exactly as designed

There is no OS-level mic permission problem, no PortAudio/CoreAudio crash, no Whisper/Kokoro failure. The lock-file throttle is a deliberate cross-session mutex that VoiceMode created at `~/.voicemode/conch` to serialize the single mic across concurrent voice sessions. When a second session calls `converse` while the first holds the conch, the second session is **immediately refused** with a status string — unless the caller passed `wait_for_conch=true`, in which case it queues for up to `VOICEMODE_CONCH_TIMEOUT=45s` (per current config; logs show old default was 60s).

## The throttle code path (the smoking gun)

`/Users/naomiivie/.claude/plugins/marketplaces/voicemode/voice_mode/tools/converse.py` lines 1399–1440:

```
acquired = conch.try_acquire()
...
holder = Conch.get_holder()
holder_agent = holder.get('agent', 'unknown') if holder else 'unknown'
event_logger.log_event("CONCH_BLOCKED", {... "wait_for_conch": wait_for_conch})
if not wait_for_conch:
    return (f"User is currently speaking with {holder_agent}. "
            "Use wait_for_conch=true to queue, or try again later.")
# Wait mode - poll with atomic retry
event_logger.log_event("CONCH_WAIT_START", {... "timeout": CONCH_TIMEOUT})
while not conch.try_acquire() and waited < CONCH_TIMEOUT:
    ...
return f"Timed out waiting for conch ({CONCH_TIMEOUT}s). {holder_agent} is still speaking."
```

Lock implementation: `/Users/naomiivie/.claude/plugins/marketplaces/voicemode/voice_mode/conch.py` — uses `fcntl.flock(LOCK_EX | LOCK_NB)`. Stale-lock GC at `_check_and_clear_stale_lock()` removes the file if older than `CONCH_LOCK_EXPIRY`. Note that this **deletes the path but the stuck process keeps its flock on the old inode** (see comment at lines 156–159) — a known limitation if a session ever wedges.
