## Implementation

Use the `voicemode:converse` tool with the user's message. All parameters have sensible defaults.

## If MCP Connection Fails

If the MCP server isn't connected or the tool isn't available:

1. **Run the install command:**
   ```
   /voicemode:install
   ```
   This installs VoiceMode CLI, FFmpeg, and local voice services.

2. **Or install manually via CLI:**
   ```bash
   uvx voice-mode-install --yes
   voicemode whisper service install
   voicemode kokoro install
   ```

3. **Check service status:**
   ```bash
   voicemode whisper service status
   voicemode kokoro status
   ```

4. **Reconnect MCP server after install:**
   Run `/mcp`, select voicemode, click "Reconnect" (or restart Claude Code)

For complete documentation, load the `voicemode` skill.

## Problem 1: Auto-debit / penalty payments (~290 words)

**How the incumbents actually charge.** Beeminder uses Stripe cards almost exclusively — when you "derail," they create a PaymentIntent against the card saved on the pledge ladder ($5 → $10 → $30 → $90 → $270…). They explicitly do *not* send a friendly pre-charge confirmation; that would defeat the commitment device. They *do* send a derail email immediately after, with a one-click "legit check" link that lets you dispute *within the app* before contesting with the bank — this is their key anti-chargeback move. StickK historically used a similar card-on-file model via a third-party processor; users sign a "Commitment Contract" with explicit forfeiture language, which serves as the dispute-defense exhibit. Forfeit (the newer iOS app) uses Apple Pay + Stripe and similarly charges silently on failure. *Verify Beeminder/StickK current processor details before quoting publicly.*

**The Stripe pattern (verified).** For Class on Time, the right shape is: `Customer` + `SetupIntent` with `payment_method_types=['us_bank_account','card']` and `payment_method_options.us_bank_account.verification_method='automatic'` (Financial Connections + microdeposit fallback). On a late arrival, create a `PaymentIntent` with `customer`, `payment_method`, `off_session=true`, `confirm=true`. ACH via Financial Connections is the dispute-resistant rail: Stripe records bank-verified ownership, and ACH disputes have a tight 60-day window with documented "authorization" defenses. Cards (including Apple Pay tokens) live on the same `Customer` as a fallback `PaymentMethod` — Apple Pay sits behind the card rail, so the merchant ID is independent of Financial Connections; both just produce PaymentMethod IDs attached to one Customer.

**Anti-dispute stack.** (1) Show a modal pre-commit that captures explicit "charge me $100 if I'm late" consent with timestamp + IP + user-agent, store in your DB and surface in Stripe `payment_intent.metadata`. (2) Use `mandate` parameters on the SetupIntent for ACH — Stripe stores a Nacha-compliant authorization record. (3) Email a receipt + GPS-stamped "you were late" evidence on every charge; this is your `evidence` payload if disputed. (4) Charge ACH first (low dispute rate, ~3-day settlement), fall back to card if ACH fails with `insufficient_funds` (Stripe surfaces this as `payment_intent.payment_failed` with `failure_code`).

**Failure modes.** `insufficient_funds` on ACH: retry once after 3 days, then fall back to the card PaymentMethod on the Customer. `card_declined`: Stripe Smart Retries on (configurable in Dashboard). User removes payment method: detach via `payment_method.detached` webhook, then *lock the app* until they re-attach — that's your anti-escape lever and the whole reason users tolerate it.

**If you only do one thing:** wire `SetupIntent` with both `us_bank_account` (Financial Connections) and `card` on a single Stripe `Customer`, and capture the consent string into `payment_intent.metadata` on every off-session charge.
